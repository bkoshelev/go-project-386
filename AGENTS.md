# Правила работы с репозиторием

## Использование скиллов

- Скиллы установлены локально в `.agents/skills/`.
- Используйте скилл, если пользователь явно назвал его в текущем запросе, например `$tdd` или `@tdd`, либо его вызов предусмотрен инструкциями другого скилла, разрешённого по этому правилу.
- Разрешены цепочки вызовов скиллов любой глубины, если первый скилл явно указан пользователем. Для таких вызовов не требуется отдельно перечислять каждый скилл в запросе.
- Не ищите, не выбирайте, не загружайте и не запускайте скиллы автоматически по описанию или совпадению с задачей. Без явного имени или вызова по разрешённой цепочке выполняйте задачу без скиллов.

## Структура проекта и организация модулей

Проект календарного бронирования состоит из двух независимых приложений:

- `backend/`: самостоятельный модуль Go/Gin; точка входа — `cmd/server/`, тесты рядом с исходными файлами.
- `frontend/`: React, TypeScript, Vite и Mantine; код приложения и CSS находятся в `src/`, а тесты Playwright — в `tests/`.
- `api/`: отдельный пакет с контрактом TypeSpec в `main.tsp` и генерацией OpenAPI и Fetch-клиента Hey API.
- Архитектурные решения — в `docs/adr/`, требования — в `specs/`, CI — в `.github/workflows/`.

## Архитектурные правила

Разработку frontend и backend ведите в соответствии с правилами и принципами из
`docs/architecture/`. Перед проектированием и изменением кода изучайте документы,
относящиеся к задаче:

- [Feature-Based Architecture](docs/architecture/feature-based-architecture.md) — организация кода по функциям продукта.
- [Vertical Slice Architecture](docs/architecture/vertical-slice-architecture.md) — реализация сквозных сценариев.
- [Event-Driven Architecture с FSM](docs/architecture/event-driven-architecture-fsm.md) — события, состояния и допустимые переходы.
- [Workflow-based architecture](docs/architecture/workflow-based-architecture.md) — координация шагов и обработка результатов.

Применяйте эти принципы с учётом описанных в документах границ применимости,
требований задачи и принятых решений в `docs/adr/`.

## Запуск и чтение контекста

Основной вход для подготовки окружения, запуска и проверок — [корневой README](README.md#установка).
Определения команд находятся в [Makefile](Makefile) (только backend) и
[frontend/package.json](frontend/package.json); подробности браузерного окружения — в
[frontend/README.md](frontend/README.md#браузерная-проверка).

При чтении задач, больших спецификаций и ответов GitHub следуйте
[правилам адресного чтения](docs/agents/context-reading.md): получайте законченные разделы
без усечения, сохраняя полноту обязательных источников.

## Стиль кода и правила именования

Используйте стандартное форматирование Go с табуляцией, имена пакетов в нижнем регистре и комментарии для экспортируемых идентификаторов. Следуйте принятому шаблону именования тестов `TestXxx`.

Для форматирования клиентской части используется Oxfmt с настройками из
[frontend/.oxfmtrc.jsonc](frontend/.oxfmtrc.jsonc). Именуйте компоненты React в PascalCase,
например `App.tsx`. Сохраняйте порядок импортов CSS: он влияет на каскад Mantine и локальных
стилей. Подавляйте только конкретное правило линтера на минимальном участке и объясняйте
каждое исключение комментарием с причиной.

## Правила тестирования

Тесты серверной части используют пакет Go `testing`, Testify и `httptest`; именуйте файлы по шаблону `*_test.go`. Для обнаружения гонок данных запускайте `make test`. Браузерные тесты клиентской части используют Playwright и находятся в `tests/*.spec.ts`. При внесении изменений добавляйте тесты поведения; числовой порог покрытия не задан. Перед созданием PR запускайте соответствующие проверки качества.

## Правила коммитов и запросов на слияние

Используйте Conventional Commits в соответствии с историей репозитория: `feat(frontend): ...`, `fix(backend): ...` или `chore: ...`. Предпочитайте слияние с объединением коммитов (squash), а заголовок PR оформляйте по Conventional Commits. Описывайте изменения поведения и выполненные проверки; добавляйте ссылки на связанные задачи, а при изменениях интерфейса — снимки экрана. Release-please управляет общей версией проекта и журналами изменений; согласовывайте с командой изменения, нарушающие обратную совместимость.
