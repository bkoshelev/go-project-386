# Окружение БД для backend

Статус: утверждено пользователем 19 октября 2026 года как основа реализации.
Реализовано 19 октября 2026 года.

## Согласованные решения

- СУБД — PostgreSQL 18; тестовый образ закрепляется на конкретной patch-версии.
- sqlc генерирует внутренний Go-пакет для типизированного выполнения SQL-запросов.
- Для миграций используется goose, для подключения — pgx/v5.
- Временная БД запускается через testcontainers-go только на время тестов.
  Постоянная локальная БД и Docker Compose не добавляются.
- Для проверок используется существующий testify.
- Первое внедрение включает инфраструктуру и один простой сквозной пример:
  миграция, генерация кода, запись и чтение данных из настоящей БД.
  Полная схема бронирования добавляется вместе с соответствующими функциями.
- Сгенерированный Go-код хранится в Git; CI проверяет актуальность генерации.
- `make test` и CI включают все тесты, в том числе тесты БД, с детектором гонок.
  Недоступность Docker или ошибка запуска БД считается ошибкой проверки.
- `make test-unit` запускает тесты, которым Docker не нужен.
- Пример — техническая таблица `example_records`: `id UUID` с
  `DEFAULT uuidv7()` на стороне PostgreSQL и `value TEXT NOT NULL`.
  Запросы sqlc создают запись и читают её по ID; бизнес-правил бронирования нет.
- SQL-миграции goose — единственный источник схемы для sqlc; отдельный
  `schema.sql` не поддерживается. Имена последовательные, с ведущими нулями:
  `00001_create_example_records.sql`, затем `00002_…`; каждый файл содержит
  `Up` и `Down`.
- Общий Go-пакет миграций встраивает SQL-файлы. Тесты вызывают его напрямую,
  а `cmd/migrate` предоставляет `up`, `down` и `status` для явно указанного
  подключения. Эти операции также доступны через цели корневого Makefile.
- HTTP-сервер в рамках этой задачи не подключается к БД.
- На интеграционный тестовый пакет запускается один общий контейнер PostgreSQL.
  Перед тестами применяется схема и один раз загружается общий YAML-набор
  через testfixtures; после тестов закрываются подключения
  и удаляется контейнер. Контейнер на каждый тест не создаётся.
- Обычный тест выполняет все запросы в собственной транзакции. sqlc получает
  транзакцию вместо пула. В конце теста `t.Cleanup` явно вызывает `Rollback`
  с отдельным, ещё не отменённым контекстом с ограничением времени.
  Запросы используют контекст теста; отмена этого контекста сама по себе
  не считается откатом транзакции.
- Проверки самих миграций составляют исключение: цикл
  `up → повторный up → down → up` выполняется в отдельной временной базе
  внутри общего контейнера, без внешней тестовой транзакции. После проверки
  эта база удаляется; схема обычных тестов не изменяется.

## Команды и воспроизводимость

Корневой Makefile предоставляет генерацию и проверку актуальности кода sqlc,
а также применение, откат последней миграции и просмотр состояния миграций.
Команда миграций получает явно указанное подключение; постоянная БД для этих
команд автоматически не запускается. Версии инструментов закрепляются
по принятой политике backend; зависимости закрепляются в Go-модуле.

`make test` сохраняет назначение полного запуска тестов с детектором гонок,
а `make check` включает эту проверку вместе с существующими проверками качества
backend. `make test-unit` явно выбирает тесты без Docker. CI выполняет полные
тесты и проверяет, что повторная генерация sqlc не расходится с файлами в Git.
Генерация не должна требовать предварительного запуска тестовой БД.

## Критерии приёмки

1. Из миграций и SQL-запросов воспроизводимо генерируется внутренний Go-пакет;
   результат хранится в Git, обычная сборка backend не требует sqlc.
2. На чистой временной PostgreSQL успешно выполняется цикл
   `up → повторный up → down → up`; повторный `up` не применяет миграцию заново.
   Пакет миграций и `cmd/migrate` используют одинаковые встроенные SQL-файлы.
3. В тестовой транзакции запись создаётся через sqlc без переданного ID,
   получает UUIDv7 от БД и читается по полученному ID с исходным `value`.
4. После отката вставленная запись отсутствует при чтении из новой транзакции.
   Очистка вызывается и при неуспешном завершении теста; откат не использует
   уже отменённый контекст запросов.
5. Тесты миграций не меняют базу обычных тестов. После завершения освобождены
   временные базы, подключения и контейнеры; ошибки подготовки или очистки
   не выдаются за успешное прохождение проверки.
6. `make test-unit` работает без Docker; полный `make test` при недоступной БД
   или Docker завершается ошибкой. В CI выполняются полные тесты с `-race`
   и проверка актуальности генерации.
7. Документация описывает требования к Docker, команды генерации и миграций,
   полный и сокращённый запуск тестов. HTTP-сервер сохраняет текущий запуск,
   а `/healthz` — смысл liveness, установленный ADR-0008.
8. `TestExampleRecordFixtureCanBeRead` читает исходную запись из YAML-фикстуры
   через sqlc и проверяет ID и значение. Ошибка загрузки общего набора
   завершает интеграционные тесты неуспешно.

## Границы

В объём не входят полная предметная схема, HTTP API для работы с данными,
подключение БД к HTTP-серверу, постоянная локальная БД и инфраструктура деплоя.
`example_records` — технический пример; термины предметного глоссария
не изменяются. Транзакционная изоляция выбрана для текущего примера; будущие
сценарии с реальным `COMMIT` и несколькими соединениями потребуют отдельного
способа изоляции.

Архитектурное решение: [ADR-0014](../docs/adr/0014-postgresql-and-sqlc.md).

Техническое основание явного отката:
[документация pgxpool.BeginTx](https://pkg.go.dev/github.com/jackc/pgx/v5/pgxpool#Pool.BeginTx).
