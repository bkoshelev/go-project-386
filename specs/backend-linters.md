# Линтеры для Go backend

Статус: спецификация по результатам интервью; реализация ещё не начата.
Дата: 2026-09-17. Учтены замечания ревью о комментариях правил и корневом Makefile.

## Цель и границы

Добавить воспроизводимые локальные и CI-проверки дефектов, безопасности и
единого стиля для всего Go backend, включая тесты. Целевая версия проекта —
Go 1.26.8: актуальный стабильный patch ветки 1.26 на дату интервью.

Успех означает, что разработчик может установить закреплённые инструменты,
запустить проверки из корня репозитория и получить те же проверки в CI.
Все замечания существующего backend устраняются сразу, без накопления baseline.

Публичный HTTP API и поведение приложения сохраняются. Frontend, изменения
защиты веток, обновления версий зависимостей приложения и несовместимые миграции
не входят в задачу. Если зависимости блокируют совместимость или безопасность,
зафиксировать блокер для отдельной задачи, не отключая проверки.

## Исходное состояние

- Backend — самостоятельный Go-модуль в `backend/`, HTTP-фреймворк Gin,
  тесты используют стандартный testing и Testify.
- В `backend/go.mod` и README сейчас указана Go 1.27.1. CI получает версию из
  `go.mod`. Это необходимо согласованно изменить на Go 1.26.8.
- Backend-workflow выполняет `gofmt`, `go vet`, `go test -race` и `go build`
  на событиях push и pull_request. По умолчанию Go-шаги работают из `backend/`.
- Makefile и конфигурации golangci-lint пока нет. `backend/bin/` уже игнорируется.
- В тестах есть намеренно игнорируемые ошибки закрытия ресурсов, глобальные
  настройки Gin и переменные окружения. Общая обязательная параллельность тестов
  поэтому не вводится.
- Найденные в PATH golangci-lint 2.9.0 и govulncheck 1.4.0 не определяют выбор
  версий. Пробный запуск установленного govulncheck на текущем Go 1.27.1
  завершился ошибкой загрузки пакетов из-за несовместимости анализатора.
  Это не результат проверки уязвимостей. Полная проверка на целевой Go 1.26.8
  ещё не выполнена.

Новая спецификация изменяет прежнее ограничение backend-bootstrap «не добавлять
golangci-lint»: оно относилось только к первоначальной задаче запуска backend.

## Go и версии инструментов

Закрепить следующие версии, без `latest` в командах установки или CI:

| Компонент | Версия | Роль |
|---|---|---|
| Go | 1.26.8 | Сборка и проверка приложения |
| golangci-lint | 2.13.2 | Запуск выбранных линтеров и форматтеров |
| govulncheck | 1.8.0 | Проверка известных уязвимостей |

Go указывается в `backend/go.mod`; CI читает это значение. README документирует
ту же версию. Не менять системную установку Go пользователя автоматически.
Проверки приложения выполняются именно на закреплённой версии; запрещается
незаметное переключение на новый toolchain, в частности через `GOTOOLCHAIN=local`.

Версии инструментов хранятся в корневом Makefile как единственном источнике для
установки локально и в CI. Обновления выполняются явными изменениями проекта с
проверкой совместимости, без бота обновлений в этой задаче. Версия Go, которой
собран официальный бинарник линтера, может отличаться от целевой версии приложения.

Существующие версии зависимостей приложения сохраняются. Разрешено необходимое
согласование файлов модуля при переходе на Go 1.26.8, но не обновление или понижение
версий зависимостей ради совместимости или устранения уязвимостей.

## Конфигурация анализа

Разместить конфигурацию v2 в `backend/.golangci.yml`. Отключить набор линтеров по
умолчанию (`linters.default: none`) и перечислить выбранные проверки явно.

| Линтер | Описание |
|---|---|
| staticcheck | Статические проверки дефектов и некорректных конструкций Go |
| ineffassign | Присваивания, результат которых не используется |
| unused | Неиспользуемый код |
| errcheck | Игнорирование возвращаемых ошибок |
| errorlint | Ошибки оборачивания, сравнения и проверки Go errors |
| gosec | Потенциально небезопасные конструкции исходного кода |
| bodyclose | Незакрытые тела HTTP-ответов |
| noctx | Исходящие HTTP-запросы без передачи context |
| sqlclosecheck | Незакрытые SQL-ресурсы поддерживаемых библиотек |
| rowserrcheck | Пропущенная проверка ошибки SQL-итерации |
| testifylint | Некорректное использование Testify |
| revive | Согласованные правила именования, стиля и документации |
| nolintlint | Корректность и обоснованность подавлений |

SQL-проверки включаются сразу, хотя БД в приложении пока нет. Их включение не
означает добавление БД или универсальную поддержку всех будущих SQL-библиотек.
`go vet` остаётся отдельной проверкой; `govet` в агрегаторе не дублируется.

### Комментарии к правилам

Для каждого явно включённого линтера, форматтера, правила revive и настроенного
параметра добавить рядом комментарий на русском: что проверяется и зачем это
выбрано. Каждое исключение также объяснить. YAML допускает такие комментарии.
В других форматах использовать комментарии, если синтаксис позволяет; иначе
перенести пояснение в README. Внутренние правила инструментов, оставленные по
умолчанию, отдельно не перечислять.

Каждую цель и значимую настройку Makefile снабдить поясняющим комментарием.

### Стиль и документация

Для revive явно включить только следующие правила:

| Правило | Назначение |
|---|---|
| exported | Комментарии к экспортируемым именам, включая internal |
| var-naming | Соглашения об именовании переменных и пакетов |
| receiver-naming | Согласованные имена получателей методов |
| error-naming | Соглашения об именах переменных ошибок |
| error-strings | Соглашения о тексте ошибок |
| error-return | Положение error в возвращаемых значениях |
| context-as-argument | Положение context в аргументах |
| context-keys-type | Корректный тип ключей context |
| increment-decrement | Идиоматичные операции увеличения и уменьшения |
| indent-error-flow | Упрощение ветвления при обработке ошибок |

Использовать gofmt и goimports. Импорты текущего модуля
`github.com/bkoshelev/go-project-386/backend` выделять после сторонних импортов.
Не вводить ограничения сложности, длины функций и строк, обязательные t.Parallel
или отдельные тестовые пакеты.

### Ошибки, тесты и исключения

- В errcheck включить `check-blank: true`: `_ = операция()` не обходит проверку.
  Остальные настройки errcheck — стандартные для закреплённой версии.
- Проверять весь backend и тесты (`run.tests: true`). Не исключать тестовые файлы
  целиком и не отключать для них общим правилом проверки безопасности или стиля.
- Допускать только точечные подавления с конкретным линтером и содержательной
  причиной. Это относится и к намеренному игнорированию ошибок cleanup.
- Для nolintlint включить `require-specific`, `require-explanation` и отключить
  `allow-unused`. Причину нельзя заменять формальным текстом вроде «ignore».
- Исключать сгенерированный код по стандартному маркеру генерации; не вводить
  широких исключений каталогов и не маскировать отсутствие документации экспортов
  стандартными наборами исключений агрегатора.
- Проверять весь код, без baseline и фильтрации только изменённых строк.
  Таймаут golangci-lint — 5 минут. Любая диагностика выбранных правил делает
  проверку неуспешной.

## Корневой Makefile и установка

Makefile располагается в корне проекта. Команды ниже запускаются из корня;
рецепты переходят в `backend/` для Go-команд. Пути вычисляются относительно
расположения Makefile. Все добавляемые цели относятся только к backend.

| Команда | Контракт |
|---|---|
| make tools | Установить закреплённые инструменты в backend/bin/tools/ |
| make lint | Проверить конфигурацию, форматирование, импорты и линтеры без исправлений |
| make fmt | Применить gofmt и goimports |
| make lint-fix | Применить доступные автоисправления линтера; затем просмотреть diff |
| make vuln | Выполнить govulncheck ./... из backend |
| make check | Выполнить lint, vet, race-тесты, сборку и проверку уязвимостей |

Объявить служебные цели phony. Команды используют именно бинарники проекта,
проверяют их версии и при отсутствии или несовпадении предлагают `make tools`.
Обычная проверка не должна незаметно устанавливать инструменты или менять исходники.

Поддержать macOS и Linux на amd64/arm64, Windows — через WSL. Нужны Go, make,
Unix shell, curl и средства распаковки/проверки контрольных сумм. Установщик
выбирает официальный архив golangci-lint под платформу, проверяет SHA-256 до
использования бинарника и завершается ошибкой для неподдерживаемой платформы.
Повторный `make tools` должен быть безопасен.

Govulncheck устанавливается через `go install` с точной версией и отдельным GOBIN,
под Go 1.26.8. Инструменты не добавляются в зависимости приложения и не заменяют
бинарники в глобальном PATH. Установка не требует root или Docker.

`make lint` проверяет и форматирование, и линтеры. Проверка форматирования должна
действительно возвращать ненулевой код при наличии diff, а не только печатать его.
`make fmt` и `make lint-fix` — явные изменяющие команды; в CI их не запускать.

## CI и проверка уязвимостей

Изменить только backend-workflow:

- Сохранить события push и pull_request, существующее имя job с тестами,
  отдельный go vet, тесты с детектором гонок и сборку.
- Добавить отдельные jobs для lint и govulncheck. Установка и запуск выполняются
  через корневой Makefile. Явно задать корень как working-directory шагов make,
  чтобы не наследовать существующий defaults.run.working-directory: backend.
- Для всех Go-проверок получать версию из backend/go.mod, не использовать
  frontend, БД или другие прикладные сервисы.
- Перенести ответственность за проверку форматирования в make lint, не оставляя
  расходящиеся локальную и CI-реализации.
- Не добавлять continue-on-error. Нарушение, ошибка запуска, таймаут или сбой
  получения базы уязвимостей делает соответствующий job красным.
- Другие workflows, включая hexlet-check, frontend и release-please, не менять.

Gosec проверяет исходники, а govulncheck — известные уязвимости с учётом использования
кода. Govulncheck запускается отдельной блокирующей проверкой на push и PR,
не только по расписанию. Использовать стандартный анализ `govulncheck ./...`;
не превращать любое упоминание уязвимого, но не вызываемого модуля в отдельное
самодельное правило отказа.

Новая запись в базе может сделать CI красным без изменения кода. При недоступности
базы нельзя выдавать успешный результат: сообщить об инфраструктурном сбое,
после восстановления доступности workflow можно перезапустить.

Если выявлена уязвимость, записать её идентификатор, затронутый компонент и
предлагаемое исправление из отчёта. Исправления зависимостей выполняются отдельной
задачей. Реализация проверки может быть готова, но внедрение не считается успешно
проверенным при сохраняющемся блокере. Настройки required checks в GitHub не менять.

## Изменения кода и документация

Исправить все замечания текущего backend, сохраняя API и поведение:
документировать экспорты, обработать ошибки либо обосновать точечные подавления,
передать context в HTTP-тестах и корректно закрыть ресурсы. Не добавлять БД и
не переписывать архитектуру для удовлетворения линтеров.

Обновить README: Go 1.26.8, подготовка окружения, установка инструментов,
команды make из корня, различие lint/fmt/lint-fix, политика подавлений и обновлений.
Сохранить прямые Go-команды с явным указанием запуска из backend/. Объяснить
различие дефекта кода, уязвимости и ошибки инфраструктуры.

## Проверка и критерии приёмки

1. Приложение собирается, проходит go vet и go test -race на Go 1.26.8
   с текущими версиями зависимостей и без автоматического перехода на Go 1.27.
2. Установка работает в чистом окружении поддерживаемых ОС и архитектур;
   устаревшие инструменты в PATH не влияют на результат. Если платформа не была
   фактически проверена, это явно указать в отчёте реализации.
3. Все цели корневого Makefile работают; CI запускает make из корня, а Go-анализ
   ограничивается backend. Frontend не меняется.
4. Конфигурация проходит проверку схемы. Фактический список линтеров совпадает
   с согласованным, а явно настроенные правила имеют поясняющие комментарии.
5. make lint не меняет исходники или файлы модуля. Повторное форматирование
   не создаёт diff. make check проходит полностью при отсутствии блокеров.
6. На изолированных временных примерах проверить обнаружение пропущенной ошибки,
   ошибки через _, незакрытого HTTP-ответа, отсутствия context, SQL-ошибки итерации,
   недокументированного экспорта и подавления без причины. Каждый пример должен
   вызывать ненулевой код соответствующей проверки. Не оставлять дефектные
   примеры в приложении и не создавать тестовый фреймворк для сторонних линтеров.
7. Проверить ненулевой код при недоступности базы govulncheck; не выдавать это
   за найденную уязвимость или чистый результат сканирования.
8. Все существующие замечания устранены. При проблемах зависимостей зафиксированы
   конкретные блокеры; зависимости не обновлены и проверки не отключены.

## Порядок реализации

1. Согласовать Go 1.26.8 в модуле, документации и CI; проверить текущие зависимости.
2. Добавить корневой Makefile, установку инструментов и комментированную конфигурацию.
3. Запустить анализ, исправить текущий код и проверить отсутствие изменения поведения.
4. Подключить отдельные CI jobs, обновить README и выполнить критерии приёмки.
5. Отчитаться о выполненных проверках и реальных блокерах, не заявляя успех
   невыполненных проверок.
