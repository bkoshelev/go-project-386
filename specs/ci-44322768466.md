## Фактическое поведение и причина

Сборка frontend и backend в исходном CI завершилась успешно. Затем внешний
стенд запустил приложение командой:

```sh
docker run --rm --name calendar-slot-code --network container:$HOSTNAME -e PORT=8080 calendar-slot-code:local
```

Контейнер записал `load configuration` / `DATABASE_URL is required` и завершился
с кодом 1. Внешняя цель `code-run-compose` завершилась с ошибкой, Compose сообщил
`dependency failed to start: container source-app-1 exited (2)`; тесты не начались.
Причина — отсутствие обязательного подключения к PostgreSQL во внешнем запуске.
Это не ошибка сборки и не предупреждение Vite о размере bundle.

Внешний `hexlet/project-action@release` использован на SHA
`ac939f85f5a7764c5bf0f3beb1fe2b3f6c4e19be`. Его `prepareProject` копирует стенд
из образа Hexlet, а пользовательский репозиторий — во вложенный `code/`.
Поэтому `/project/Makefile` и `/project/docker-compose.yml` из лога не являются
файлами этого репозитория; его `compose.yaml` не управляет упавшим запуском.

Read-only просмотр публичного образа
`hexletprojects/ai_assisted_development_calendar_slot_project_ru:latest`
с digest `sha256:82cc122933c4854fb8c69a75b8889686d87ce019a15400613acbc534e1358503`
подтвердил ту же команду `code-run-compose`, только сервисы `app`/`test`
и описанный в README стенда контракт «PORT=8080, GET / -> 200».
Digest именно использованного CI образа в доступном логе не опубликован;
просмотренный `latest` — дополнительное подтверждение команды, а не доказательство
неизменности всех файлов стенда на момент запуска.

Предыдущий [зелёный Hexlet run на том же SHA](https://github.com/bkoshelev/go-project-386/actions/runs/44150564538)
записал `Tests will run during review step`: он не выполнял эти тесты.
Собственный контейнерный workflow на том же SHA прошёл с внешней PostgreSQL.
В текущем `main` нет последующего исправления данного запуска.

Дополнительно текущая конфигурация расходится с уточнённым контрактом:

- Без `PORT` применяется `127.0.0.1:8080`.
- `HTTP_ADDR` имеет приоритет над `PORT`, позволяет не задавать его и даже
  игнорировать невалидное значение `PORT`.
- Dockerfile задаёт `ENV PORT=8080`; Compose подставляет `${PORT:-8080}`.
- Dev launcher, браузерная фикстура и второй экземпляр smoke используют `HTTP_ADDR`.

## Ожидаемое поведение

1. HTTP-сервер требует непустые `PORT` и `DATABASE_URL`. Отсутствие, пустота
   или значение только из пробелов любой переменной прекращает запуск с кодом 1
   и понятным именем переменной в диагностике, до подключения к БД и открытия HTTP.
2. `PORT` — десятичное целое от 1 до 65535. Некорректные значения, включая 0,
   отрицательные, превышение диапазона, дробь, текст и `host:port`, отклоняются.
3. Сервер слушает `0.0.0.0:<PORT>` и доступен на этом порту из контейнерной сети.
   HTTP-порт отличается от внутреннего порта подключения PostgreSQL.
4. `HTTP_ADDR` больше не является входом конфигурации. Его наличие, пустота
   или некорректное значение не обходят обязательность `PORT` и не меняют адрес.
   Внутреннее поле `Config.HTTPAddr` допустимо сохранить как вычисленный адрес.
5. `DATABASE_URL` явно задаёт внешнюю PostgreSQL, включая параметры TLS.
   Некорректный DSN даёт ошибку конфигурации без утечки DSN/пароля.
   Недоступный DSN не переключает хранилище: остаются существующие ограниченные
   повторы, бюджет подготовки до пяти минут и ненулевой выход при его исчерпании.
   SIGTERM/SIGINT отменяют подготовку. До успешной подготовки HTTP не открывается.
6. Сохраняются PostgreSQL, pgx/sqlc, все существующие миграции goose, UUID БД,
   атомарность бронирования, общая пауза, расписание и защита от пересечений.
   Автономного режима, SQLite, встроенной PostgreSQL и хранения в памяти нет.
7. После успешного старта остаются прежние `/healthz`, `/readyz`, поведение
   при потере и восстановлении БД, same-origin frontend/API и штатное завершение.
8. Контракт относится к HTTP-серверу. Отдельная утилита `/app/migrate` не начинает
   требовать HTTP-порт; её существующий `-dsn`/`DATABASE_URL` сохраняется.

Собственный Compose может предоставлять DSN явно создаваемой им внешней БД;
это не fallback приложения. Независимый `APP_HOST_PORT` — порт публикации Docker
на хосте, его прежний default не заменяет обязательный `PORT` внутри контейнера.

Render уже передаёт `PORT`, Blueprint задаёт `DATABASE_URL`; менять `render.yaml`
или создавать ресурсы не требуется. Оставшиеся внешние переменные `HTTP_ADDR`
теряют действие. В dev и браузерных тестах сервер начнёт слушать все интерфейсы
вместо loopback; это прямое следствие единого адреса `0.0.0.0:<PORT>`.
Публикация ручного Compose на хосте остаётся ограничена `127.0.0.1`.

## Подключение Web Service к БД на Render

Текущий `render.yaml` уже задаёт для Web Service `calendar-demo` переменную
`DATABASE_URL` через `fromDatabase: {name: calendar-demo-db, property: connectionString}`.
Оба ресурса находятся в `frankfurt`; Blueprint хранит ссылку на ресурс, а не пароль.
Render подставляет внутренний PostgreSQL DSN во время развёртывания;
значение секрета коммитить не нужно.
См. [Blueprint: connectionString](https://render.com/docs/blueprint-spec#connectionstring).

Для ресурсов, созданных вручную, будущая инструкция должна описать следующий путь:
открыть нужную БД в том же workspace и регионе, скопировать **Internal Database URL**
из её параметров подключения и задать его значением `DATABASE_URL` в **Environment
Web Service**, обслуживающего frontend и backend.
Это строка PostgreSQL вида `postgresql://user:password@host:port/database`,
а не ссылка на карточку БД в Dashboard и не публичный HTTPS URL приложения.
См. [Render Postgres: внутреннее подключение](https://render.com/docs/postgresql-creating-connecting#internal-connections).

DSN получает только серверный процесс: не передавать его браузеру, в `VITE_*`
или в сборку frontend. Frontend обращается к относительным `/api/...` на том же
origin, а backend подключается к БД. Отдельный URL БД в клиентском конфиге не нужен.

HTTP-сервер должен слушать `0.0.0.0:$PORT`; Render предоставляет `PORT`,
его стандартное значение — `10000`. Это HTTP-порт, не порт PostgreSQL из DSN.
Blueprint уже использует `/readyz` как health check: успешный ответ должен
подтверждать доступ backend к БД после миграций.
См. [Render Web Services: port binding](https://render.com/docs/web-services#port-binding).

В рамках будущей проверки провалидировать существующий Blueprint без создания
ресурсов, например `render blueprints validate render.yaml` либо по официальной
JSON Schema, и проверить готовый контейнер с `PORT=10000` и тестовой внешней БД.
Схема Blueprint проверяет конфигурацию, а локальный `/readyz` — связку приложения
с тестовой БД; ни одна проверка не подтверждает настройки реального Dashboard.
На диагностическом этапе проверены только конфигурация репозитория и официальные
документы Render; наличие ресурсов, их Environment, деплой и реальное подключение
в аккаунте Render не проверялись и не изменялись.

## ADR и границы

Смена архитектуры хранения не нужна: ADR-0014, ADR-0015 и ADR-0016 сохраняют
внешнюю PostgreSQL, один процесс приложения, миграции до HTTP и readiness.
Они не закрепляют `HTTP_ADDR` как обязательный выбор; менять их решения не требуется.
Достаточно обновить текущий контракт в связанной production-спецификации и отметить
замену исторического bootstrap-контракта. ADR-0018 по-прежнему задаёт mise
как источник команд; меняется только передаваемая dev launcher переменная.

Вне объёма: миграции данных, новые хранилища/драйверы, API/frontend-функции,
новые startup retries, смена таймаутов, зависимости, изменение внешних тестов,
отключение проверок, GitHub labels/issues/comments, публикация, коммиты и PR.

## Внешний prerequisite исходного CI

**Локальная реализация этого контракта не исправит исходный Hexlet run.**
Невозможно одновременно требовать `DATABASE_URL` и успешно запустить тот же
HTTP-сервер командой, которая его не передаёт.

Владелец внешнего стенда должен предоставить доступную PostgreSQL и передать
её DSN непосредственно вложенному `docker run`, например через `-e DATABASE_URL`,
с обеспечением сетевой доступности БД из namespace контейнера приложения.
Одного окружения GitHub runner без передачи в этот `docker run` недостаточно.
Изменение локального `compose.yaml` не меняет внешний стенд.
До выполнения prerequisite исходный CI остаётся заблокирован; повторный запуск
без изменения стенда не считается проверкой исправления.

## Критерии приёмки

- AC-01: unset, пустой и whitespace-only `PORT` при корректном DSN дают отказ
  конфигурации и код 1; `HTTP_ADDR` не позволяет запуститься.
- AC-02: unset, пустой и whitespace-only `DATABASE_URL` при корректном PORT дают
  отказ конфигурации и код 1. Отсутствие обеих переменных тоже отклоняется.
- AC-03: невалидный PORT и некорректный DSN отклоняются с безопасной диагностикой;
  чужой `HTTP_ADDR` не скрывает ошибку PORT.
- AC-04: с обеими переменными и реальной PostgreSQL экземпляры доступны на 10000
  и 8091 из контейнерной сети; `/`, API и `/readyz` успешны. Значение `HTTP_ADDR`,
  указывающее иной порт, не меняет результат; на этом ином порту сервер не слушает.
- AC-05: готовый образ не содержит ENV default PORT. Его запуск без PORT/DSN
  действительно завершается ошибкой; Compose без PORT отклоняет конфигурацию.
- AC-06: явно заданный недоступный DSN не создаёт локальную БД и не открывает HTTP;
  подготовка ограничена прежним бюджетом/контекстом и отменяется сигналом.
  Дедлайн проверяется существующим тестом с коротким контекстом;
  контейнерный сценарий подтверждает отсутствие HTTP и отмену подготовки.
- AC-07: миграции, сохранность данных, конкурентное бронирование, настройки,
  браузерные сценарии и восстановление readiness продолжают проходить.
- AC-08: dev launcher и браузерная фикстура передают PORT и DSN; инструкции
  ручного запуска показывают обе переменные. Миграционный CLI не требует PORT.
- AC-09: исходный Hexlet CI отмечается исправленным только после отдельного
  подтверждения передачи DSN/доступной PostgreSQL внешним стендом и успешного run.
- AC-10: существующий Blueprint проходит проверку без создания ресурсов;
  `DATABASE_URL` Web Service ссылается на `calendar-demo-db.connectionString`,
  оба ресурса находятся в одном регионе, секрет не записан в Git.
- AC-11: документация ручного сценария указывает **Environment Web Service →
  DATABASE_URL = Internal Database URL** нужной БД в том же workspace/регионе;
  различает PostgreSQL DSN, Dashboard URL и публичный URL приложения.
  Frontend использует same-origin API и не получает DSN.
- AC-12: локальный smoke с `PORT=10000` подтверждает доступность HTTP и успешный
  `/readyz` с тестовой внешней PostgreSQL; результат не объявляется проверкой
  реального Dashboard или фактического деплоя Render.

## Результат реализации и проверки 18 ноября 2026 года

HTTP-сервер требует обе переменные, игнорирует `HTTP_ADDR` и слушает
`0.0.0.0:PORT`; отдельная команда миграций не требует `PORT`. Обновлены
Compose, dev launcher, браузерная фикстура, контейнерный smoke и инструкции.
