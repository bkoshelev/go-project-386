# HTTP API приложения бронирования

Статус: **HTTP-контракт принят пользователем**. Согласованы операции, модели
запросов и ответов, статусы и ошибки. Полная спецификация MVP утверждена
пользователем 19 октября 2026 года; схема также принята.

Каноническая [спецификация приложения](https://github.com/bkoshelev/go-project-386/issues/31).
Исходный контракт — [`api/main.tsp`](../api/main.tsp), OpenAPI и клиент генерируются
принятыми инструментами проекта. Backend и frontend этим документом не реализуются.
Сводные требования и критерии приёмки — в [спецификации MVP](booking.md).

## Общие правила

- Все операции, кроме существующего `/healthz`, находятся под `/api` и используют JSON.
- Один заранее заданный владелец; операции не принимают `ownerId`. Авторизации нет.
  Префикс `/admin` обозначает административный сценарий.
- ID типов событий и бронирований — строки UUID; их генерирует БД.
- Моменты времени (абсолютные точки на временной шкале, однозначно заданные датой, временем и смещением относительно UTC, в отличие от местных часов расписания) передаются в RFC 3339. Ответы с конкретными моментами нормализуются в UTC
  с суффиксом `Z`. Для начала встречи секунды и доли секунды должны быть нулевыми.
  Валидный входной момент с числовым смещением нормализуется в UTC перед проверками.
- Часы расписания — местные `HH:mm`, окончание допускает `24:00`. Даты исключений —
  местные даты владельца `YYYY-MM-DD`. Все они относятся к сохранённому `timeZone`.
- Границы интервалов — `[начало, конец)`. Соприкасающиеся интервалы дают непрерывное
  доступное время; окончание встречи ровно на границе допускается.
- Длительность и пауза — прошедшие целые минуты. Сезонные переходы отложены
  в [отдельную задачу после MVP](https://github.com/bkoshelev/go-project-386/issues/32).
- Чтение актуальной доступности и проверка ручного времени не резервируют интервал.
  Создание всегда повторно проверяет доступность и сохраняет результат атомарно.
- Неизвестные поля запросов отклоняются с ошибкой валидации, чтобы опечатки и попытки
  изменить неизменяемые данные не игнорировались молча.

## Операции

| Метод и путь | Описание | Запрос | Успешный ответ |
| --- | --- | --- | --- |
| `GET /healthz` | Проверяет работоспособность backend без обращения к внешним зависимостям. | — | `200 HealthStatus`, существующее поведение сохранено |
| `GET /api/owner` | Возвращает профиль владельца с полным именем для заголовка записи. | — | `200 CalendarOwnerProfile` |
| `GET /api/event-types` | Возвращает весь каталог типов событий для выбора гостем и просмотра владельцем. | — | `200 EventTypes { items }`, все типы |
| `GET /api/event-types/{eventTypeId}` | Возвращает данные выбранного типа события для wizard. | UUID типа | `200 EventType` |
| `GET /api/event-types/{eventTypeId}/availability` | Рассчитывает предложенные свободные слоты выбранного типа на всё окно из 14 дат UTC. | UUID типа | `200 EventAvailability`, всё окно 14 дат |
| `POST /api/event-types/{eventTypeId}/availability/check` | Проверяет введённое вручную начало встречи без создания бронирования и резервирования слота. | `CheckAvailabilityRequest { startsAt }` | `200 AvailableStart` либо `UnavailableStart` |
| `POST /api/bookings` | Повторно проверяет доступность и атомарно создаёт бронирование с данными гостя. | `CreateBookingRequest` | `201 BookingConfirmation` |
| `POST /api/admin/event-types` | Создаёт тип события с названием, описанием и длительностью; UUID генерирует БД. | `CreateEventTypeRequest` | `201 EventType` |
| `GET /api/admin/bookings` | Возвращает все текущие и будущие встречи владельца вместе с именами и email гостей. | — | `200 OwnerBookings { asOf, items }` |
| `GET /api/admin/scheduling-settings` | Возвращает общую паузу и сохранённый часовой пояс, если он уже инициализирован. | — | `200 SchedulingSettings` |
| `POST /api/admin/scheduling-settings/time-zone` | Однократно сохраняет первый часовой пояс владельца; при повторе возвращает уже сохранённый. | `InitializeScheduleTimeZoneRequest` | `200 SchedulingSettings` с сохранённым поясом |
| `PUT /api/admin/scheduling-settings` | Изменяет общую паузу между встречами, сохраняя прежний часовой пояс. | `UpdateSchedulingSettingsRequest` | `200 SchedulingSettings` |
| `GET /api/admin/availability/weekly` | Возвращает интервалы и флаги блокировки всех семи дней недели. | — | `200 WeeklyAvailability` |
| `PUT /api/admin/availability/weekly` | Атомарно заменяет недельное расписание: интервалы и блокировки всех семи дней. | `WeeklyAvailability` | `200 WeeklyAvailability` |
| `GET /api/admin/availability/dates/{date}` | Возвращает собственную настройку местной даты либо признак наследования недельного расписания. | Местная дата | `200 DateAvailability` |
| `PUT /api/admin/availability/dates/{date}` | Заменяет настройку местной даты: задаёт собственные интервалы, блокировку либо наследование недельных интервалов. | `UpdateDateAvailabilityRequest` | `200 DateAvailability` |

Коллекции не имеют скрытого ограничения числа элементов. Каталог возвращается
в стабильном порядке по UUID; список владельца — по `startsAt` по возрастанию,
при совпадении — по UUID. В текущей модели встречи одного владельца не пересекаются.
Пустая коллекция — успешный ответ с `items: []`.

## Доступность и ручной ввод

`EventAvailability` содержит:

- `eventTypeId` — выбранный тип;
- `generatedAt` — момент расчёта по серверным часам;
- `windowStartsAt` — начало сегодняшних суток UTC;
- `windowEndsAt` — начало суток UTC после последней из 14 дат;
- `slots` — предложенные интервалы выбранной длительности, отсортированные по началу.

Предложенные начала привязаны к `:00/:15/:30/:45 UTC`, строго будущие и учитывают
полную длительность, рабочие интервалы, местные блокировки, все бронирования и паузу.
Вся встреча должна завершиться не позже `windowEndsAt`. До настройки расписания
либо при отсутствии подходящего времени возвращается `slots: []`.

Гость группирует полученные UTC-интервалы по местным датам своего браузера. Backend
не получает пояс гостя для изменения правил расписания. Данные других гостей,
ID и подробности чужих бронирований в публичную доступность не входят.

Для ручного начала, например 10:07, UI преобразует введённую местную дату и время
в абсолютный момент и вызывает `/availability/check`. Ответ:

```json
{
  "available": true,
  "slot": {
    "startsAt": "2026-10-20T07:07:00Z",
    "endsAt": "2026-10-20T07:37:00Z"
  }
}
```

Или `available: false` с причиной: `time_occupied`, `starts_in_past`,
`outside_booking_window`, `outside_working_hours`, `schedule_not_initialized`.
Это успешная проверка с HTTP 200. Неверный формат/точность начала — HTTP 422.
Сама встреча при проверке не создаётся. Ответы доступности не кешируются:
`Cache-Control: no-store`.

## Создание и повторная отправка

Пример для встречи длительностью 30 минут:

```json
{
  "eventTypeId": "2d3d609d-bcbf-4ff4-99bd-580688c0c4a4",
  "startsAt": "2026-10-20T07:07:00Z",
  "guest": { "name": "Анна", "email": "anna@example.com" }
}
```

Backend вычисляет окончание по длительности типа. Имя и email обрезаются по краям
до валидации и сохранения; имя — 1–100 символов, корректный email — до 254 символов.
Имя типа также обрезается по краям и не может быть пустым; одинаковые названия
разрешены. Длительность типа ограничена ранее согласованными нормализованными значениями.

При создании проверка доступности и вставка сериализуются для одного владельца;
конкурирующие пересекающиеся запросы не могут оба завершиться созданием. Изменения
расписания и паузы согласуются с этой проверкой, чтобы запись использовала целостные
актуальные настройки. Выбор СУБД и механизм блокировок остаются задачами реализации.

Успешное создание — `201 BookingConfirmation` с UUID бронирования, `status: confirmed`,
ID и названием типа, началом и окончанием. Имя и email гостя возвращаются владельцу
в `OwnerBooking`; публичное подтверждение не требует повторного раскрытия этих полей.

Первое сохранённое бронирование занимает время. Повторный запрос после сохранения
возвращает `409 time_occupied`, включая случай потери первого успешного ответа.
Ключ идемпотентности и воспроизведение прошлого успеха не вводятся. При неизвестном
результате UI не повторяет запись автоматически.

Для списка владельца `asOf` — серверный момент, по которому применён фильтр
`endsAt > asOf`; `items` содержит все текущие и будущие встречи.

## Настройки и их начальное состояние

До инициализации `GET scheduling-settings` возвращает `meetingPauseMinutes: 0`,
поле `timeZone` отсутствует. Недельное расписание содержит семь заблокированных дней
с пустыми интервалами. Доступных слотов нет.

Административная часть передаёт первый определённый браузером IANA-пояс. Backend
проверяет его и атомарно сохраняет, только если пояс ещё не задан. Повторные вызовы
инициализации с валидным входом возвращают фактически сохранённые настройки;
пояс не изменяется, даже если браузер сообщает другое значение. Пояс сервера не
используется вместо неизвестного пояса владельца. Браузер гостя его не инициализирует.

`PUT scheduling-settings` заменяет значение паузы, не принимает `timeZone`.
Недельные и датированные настройки нельзя записывать до инициализации пояса;
возвращается `409 schedule_not_initialized`.

`PUT weekly` атомарно заменяет все семь дней: каждый день присутствует ровно один раз.
Для интервалов требуется начало раньше окончания, отсутствие пересечений; касание
разрешено. Порядок ответа — понедельник–воскресенье, интервалы — по началу.
При блокировке дня редактор отправляет сохранённые интервалы вместе с новым флагом.

`GET dates/{date}` возвращает явную настройку, а не объединённые часы доступности.
Если настройки даты нет, ответ — указанная дата, `isBlocked: false`, без `intervals`:
используется недельный шаблон. Такой ответ не открывает заблокированный день недели.

`PUT dates/{date}`:

- `isBlocked: true` закрывает дату и удаляет её собственные интервалы;
- `isBlocked: false` без `intervals` снимает блокировку и возвращает наследование;
- `isBlocked: false` с `intervals` задаёт собственные интервалы вместо недельных;
- явный пустой `intervals: []` означает отсутствие часов работы, без установки флага;
- настройки даты по-прежнему не обходят недельную блокировку.

Изменения влияют на новые бронирования. Уже созданные встречи не отменяются
и не переносятся; при новых записях их интервалы остаются занятыми.

## Ошибки

Ошибки содержат машинный `code` и понятный пользователю `message`. Клиент выбирает
сценарий по коду, а не разбирает текст сообщения. В JSON нет HTTP-поля `statusCode`.

| HTTP | Код | Значение для клиента |
| --- | --- | --- |
| 400 | `bad_request` | Неразбираемый JSON либо неверный формат параметра пути |
| 422 | `validation_error` | Ошибки полей; `fields` содержит путь, код и сообщение |
| 404 | `event_type_not_found` | Вернуться к выбору типа события |
| 409 | `time_occupied` | «Время уже занято», обновить календарь и выбрать время |
| 409 | `time_unavailable` | Время стало недопустимым; `reason` объясняет причину |
| 409 | `schedule_not_initialized` | Завершить однократное сохранение пояса владельца |
| 500 | `internal_error` | Показать общую ошибку; запись автоматически не повторять |
| 503 | `service_unavailable` | Сервис временно недоступен; чтение можно повторить |

`time_unavailable.reason` — прошедшее начало, выход за окно, выход из рабочих часов
или отсутствие инициализации. Занятость и нарушение обязательной паузы дают
`time_occupied`. Для бронирования проверка полей предшествует проверке доступности;
при нескольких причинах используется порядок: инициализация → будущее начало →
окно → рабочие часы/блокировки → занятость/пауза.

Пример ошибки полей:

```json
{
  "code": "validation_error",
  "message": "Проверьте данные формы",
  "fields": [
    { "field": "/guest/email", "code": "invalid_format", "message": "Введите email" }
  ]
}
```

Пути полей используют JSON Pointer, например `/days/0/intervals/1/end`.
Неуспешная запись не означает для клиента успешного создания: при потере ответа
результат может остаться неизвестным, как описано в согласованных состояниях экранов.

## Граница текущей работы

Проверяются форматирование и компиляция TypeSpec, структура OpenAPI, генерация
клиента и совместимость с TypeScript frontend. Это проверка описания API;
серверные обработчики, миграции БД и интерфейс ещё предстоит реализовать.
