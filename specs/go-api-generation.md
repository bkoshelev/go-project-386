# Генерация HTTP-слоя Go

Статус: принято пользователем 19 октября 2026 года.
Первый этап реализован: генерация, адаптер валидации и strict-обработчик `/healthz`.

Архитектурное решение — [ADR-0013](../docs/adr/0013-go-api-generation.md).
Поведение HTTP API определяет [принятый контракт](booking-api.md), исходную схему —
[`api/main.tsp`](../api/main.tsp). Генерация не меняет предметную семантику контракта.

## Граница первого этапа

Сохранить Gin и подключить `oapi-codegen v2.8.0`. Генерировать модели, встроенную
OpenAPI-схему, интерфейсы обработчиков, регистрацию маршрутов, разбор запросов
и сериализацию типизированных HTTP-ответов. Hey API для frontend сохраняется.

Перевести существующий `GET /healthz` на сгенерированный strict-интерфейс, сохранив
его статус, JSON-ответ, логирование, обработку паник и отсутствие обращений
к внешним зависимостям. Бронирование, расписание, хранение данных и другие операции
подключаются вместе с реализацией соответствующих сценариев.

## Поэтапная генерация

Сгенерированные файлы размещаются в одном внутреннем пакете backend.
Две конфигурации разделяют полный контракт и реализованные операции.

Модели и полная встроенная схема:

```yaml
package: api
generate:
  models: true
  embedded-spec: true
output-options:
  skip-prune: true
output: internal/api/models.gen.go
```

HTTP-сервер для реализованных операций:

```yaml
package: api
generate:
  gin-server: true
  strict-server: true
output-options:
  include-operation-ids:
    - getHealth
output: internal/api/server.gen.go
```

Пути `output` указаны относительно каталога `backend/`. Обе конфигурации используют
один OpenAPI-документ. Серверный список `include-operation-ids` дополняется по мере
готовности обработчиков. Полная схема встраивается конфигурацией моделей, поскольку
фильтрация серверных операций до встраивания урезала бы также встроенную схему.

## Валидация запросов

Сначала отличить повреждённый JSON от корректного JSON с ошибками полей. До проверки
ограничений обрезать пробелы по краям только у предусмотренных контрактом строк:
названия типа события, имени гостя и email гостя. Отсутствующие поля, `null`, пустые
массивы и неизвестные поля сохранять для проверки; нормализация не должна менять
их смысл или скрывать ошибки типов.

Нормализованный запрос проверять через `kin-openapi` по полной встроенной схеме,
затем передавать нормализованное тело сгенерированному обработчику для декодирования.
Предварительная проверка выполняется до generated binding: strict middleware,
вызываемое после `ShouldBindJSON`, уже не видит потерянные неизвестные поля и может
не получить управление при ошибке декодирования UUID или времени.

Проверки форматов UUID, email, календарной даты и RFC 3339 настроить явно и согласовать
с используемыми Go-парсерами. Не ограничивать UUID версиями 1–5: HTTP-контракт
не закрепляет конкретную версию. Значения с числовым смещением принимать
и нормализовать в UTC до проверок времени; ответы с моментами возвращать с `Z`.

Правила, не выраженные в схеме, проверять в Go: точность начала до минуты,
уникальность дней недели, порядок и пересечения интервалов, корректность IANA-пояса
и правила доступности. Проверка полей предшествует проверке доступности.
Атомарность бронирования обеспечивается при реализации хранения данных.

Адаптер ошибок сохраняет принятый контракт:

- повреждённый JSON или неверный формат параметра пути — `400 bad_request`;
- ошибки полей корректного JSON, включая форматы UUID/времени в теле и неизвестные
  поля, — `422 validation_error` с JSON Pointer, кодом и сообщением в `fields`;
- внутренние ошибки — `500 internal_error` без раскрытия внутренней диагностики.

Стандартные callbacks генератора возвращают другой формат тела ошибки; переопределить
обработку ошибок параметров пути, декодирования запроса, приложения и сериализации.

## Воспроизводимость и проверки

Закрепить версии генератора и необходимых Go-зависимостей. Результат генерации
со встроенной схемой хранить в Git, сгенерированные файлы вручную не изменять.
Обновление выполнять отдельной командой из TypeSpec. Обычные Go-сборка, тесты
и `make check` не запускают TypeSpec и не требуют Node.js или frontend.

Отдельная задача CI воспроизводит генерацию закреплёнными инструментами
и проверяет отсутствие расхождений с сохранённым результатом. Прежние проверки
TypeSpec и Hey API сохраняются.

Для первого этапа проверить:

- две генерации создают компилируемый Go-пакет; встроенная схема содержит полный
  контракт, серверный интерфейс и регистрация — только `getHealth`;
- `/healthz` сохраняет прежнее поведение через общий Gin-роутер; операции,
  ещё не подключённые к серверу, не получают временных обработчиков;
- сериализация объединений в ответах и наследование моделей сохраняют структуру JSON;
- отсутствующий `intervals` отличается от `[]`, а недопустимый `null` отклоняется;
- валидация различает ошибки JSON, параметров пути и полей тела, сохраняет неизвестные
  поля для диагностики и учитывает нормализацию до ограничений длины/формата;
- регенерация воспроизводима, а обычные проверки backend работают без Node.js.

Проверки будущих операций не требуют реализации их бизнес-логики: для адаптера
валидации используются запросы и схемы, для сериализации — сгенерированные типы.

Проверка заголовка `Content-Type` у `/healthz` сравнивает media type
`application/json`, допуская наличие или отсутствие параметра `charset`.
Это учитывает стандартный JSON-ответ strict-server и сохраняет смысл проверки
существующего Gin-обработчика.
