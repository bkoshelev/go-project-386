# Контейнерный запуск приложения с внешней БД

Статус: реализовано 20 октября 2026 года. Инструкция запуска —
[production-environment](../docs/runbooks/production-environment.md).

## Согласовано

- Приложение поставляется одним Docker-образом, содержащим собранные frontend
  и backend. PostgreSQL запускается отдельно от контейнера приложения.
- Подключение к БД передаётся при запуске через `DATABASE_URL`.
- Обычный запуск контейнера автоматически применяет миграции перед запуском
  приложения. Применение защищается блокировкой в PostgreSQL и ограничивается
  по времени. При ошибке миграции приложение не запускается.
- Отдельная команда миграций остаётся доступной для ручного запуска
  и сценариев платформы.
- Объём работы включает Dockerfile, инструкцию запуска и проверку готового
  образа. Публикация образа в registry и автоматический деплой обсуждаются
  отдельно.
- Нужно локально воспроизводить схему запуска на Render или аналогичной
  платформе: создание отдельной БД, запуск образа приложения в контейнере
  и проверка совместной работы frontend, backend и БД.
- Локальный сценарий не является проверкой самой платформы Render.
- Frontend и API обслуживает один Go-сервер. Caddy и управление несколькими
  серверными процессами в одном контейнере не добавляются.
- Для локального окружения используется Docker Compose: PostgreSQL 18
  и контейнер приложения. Нужны команда ручного запуска и отдельная
  автоматическая проверка с очисткой созданных ею ресурсов.
- Миграции должны сохранять совместимость с предыдущей версией приложения.
  Откат образа не запускает `down`; удаление старых структур выполняется
  последующим отдельным выпуском после перевода кода на новую схему.

## Образ и конфигурация

Dockerfile собирает frontend и backend отдельными стадиями. Сборка frontend
включает установку зависимостей `api/` и генерацию клиента из TypeSpec.
Используются закреплённые проектом версии Go, Node.js и pnpm и существующие
lock-файлы. Сборка образа не требует доступной БД и не применяет миграции.
Итоговый образ содержит готовую статику, сервер и отдельную команду миграций;
Node.js и инструменты сборки для запуска не нужны.

| Переменная | Контракт |
| --- | --- |
| `DATABASE_URL` | Обязательная строка подключения к внешней PostgreSQL, включая параметры TLS. |
| `PORT` | Внешний HTTP-порт. В образе по умолчанию `8080`; сервер слушает `0.0.0.0`. |
| `HTTP_ADDR` | Существующее явное переопределение адреса; имеет приоритет над `PORT`. |

При прямом запуске backend без `HTTP_ADDR` и `PORT` сохраняется существующий
адрес `127.0.0.1:8080`. Неверная конфигурация завершает запуск с понятной
ошибкой; пароли и полная строка подключения не попадают в диагностику.
Настройки и секреты передаются при запуске, а не встраиваются в образ.

Для Render инструкция описывает внешний `PORT`, настройку HTTP-проверки
`/readyz` и подключение к отдельно размещённой БД. Образ поддерживает сборку
для `linux/amd64`, требуемой для готовых образов Render; публикация в registry
в этот этап не входит.

## HTTP и маршрутизация

- Frontend и API доступны на одном origin. Клиент использует относительные
  адреса `/api/...`; адрес платформы не встраивается при сборке frontend.
- Статика раздаётся из собранных ресурсов frontend. Для страниц SPA
  предусмотрен возврат `index.html`, включая прямое открытие вложенного URL.
- Неизвестный маршрут `/api` или `/api/...` возвращает `404`, а не HTML SPA.
  Отсутствующий статический ресурс также возвращает `404`.
- `/healthz` и `/readyz` обрабатываются отдельно от SPA.
- `/healthz` сохраняет существующий ответ и не проверяет БД.
- `/readyz` возвращает `200` при доступной БД и `503`, когда проверка
  подключения или простой запрос завершаются ошибкой либо превышают таймаут
  2 секунды. Ответ не раскрывает параметры подключения.
- Новый readiness-контракт добавляется в TypeSpec с последующей генерацией
  серверных типов и клиента по принятому процессу проекта.

## Запуск и временная недоступность БД

Перед запуском HTTP-сервера проверяется конфигурация, устанавливается
подключение к БД и применяются миграции. При временной недоступности БД
попытки подключения повторяются в пределах общего бюджета подготовки.
Ошибки конфигурации и миграций не маскируются бесконечными повторами.

Подключение, ожидание блокировки и применение миграций вместе ограничены
5 минутами. При ошибке или истечении срока процесс завершается с ненулевым
кодом, HTTP-сервер не запускается. Сигналы остановки обрабатываются также
на этапе подготовки.

После запуска временная недоступность БД делает `/readyz` неуспешным,
но сама по себе не завершает Go-процесс и не меняет смысл `/healthz`.
После возвращения БД готовность восстанавливается без обязательного
перезапуска приложения. Платформа может самостоятельно перезапускать
экземпляры по результатам своих health checks.

При SIGTERM сервер корректно завершает обслуживание запросов в пределах
существующего таймаута 10 секунд и освобождает подключения к БД.
Диагностика приложения направляется в stdout/stderr.

## Локальное окружение и CI

Docker Compose поднимает отдельную PostgreSQL 18 с закреплённой patch-версией
и контейнер собранного приложения. Ручное окружение позволяет сохранять БД
при перезапуске приложения. Автоматическая проверка использует изолированные
ресурсы и чистую БД; удаляет только созданные ею контейнеры, сеть и данные,
в том числе после ошибки, и не затрагивает ручное окружение разработчика.

Одна команда запускает контейнерный smoke-сценарий локально и в отдельном
workflow GitHub Actions на push и pull request. При сбое сохраняются
диагностические логи с исключением секретов. Существующие проверки frontend
и backend сохраняются. Недоступность Docker или ошибка запуска БД делает
проверку неуспешной, а не пропущенной.

## Согласованный smoke-сценарий

1. Собрать образ и запустить его с отдельной чистой БД через Docker Compose.
2. Открыть frontend из образа в Chromium и проверить загрузку приложения.
3. Из контекста страницы выполнить запрос к backend на том же origin.
4. Отдельный `/readyz` проверяет доступ к БД. `/healthz` сохраняет liveness-смысл.
5. Через SQL подтвердить применение миграции.
6. Перезапустить приложение с той же БД и проверить успешный повторный запуск
   и сохранность данных.

Дополнительно проверяются:

- Порт, заданный через `PORT`, и явное переопределение `HTTP_ADDR`.
- Корректная обработка SPA-маршрутов, отсутствующих ресурсов и API `404`.
- Отсутствующая или неверная конфигурация БД, временная недоступность БД
  при старте, ошибка миграции и ограничение общего времени подготовки.
- Одновременный запуск двух экземпляров с одной чистой БД: миграции
  сериализуются и применяются один раз, оба экземпляра могут запуститься.
- Недоступность БД после запуска: `/readyz` возвращает `503`, `/healthz`
  остаётся успешным; после возвращения БД `/readyz` восстанавливается.
- Корректная обработка SIGTERM и завершение процесса, в том числе во время
  подготовки приложения.

Сохранность данных при перезапуске можно проверить существующей технической
таблицей через SQL, не добавляя публичных диагностических CRUD-операций.
Контейнерный smoke-сценарий дополняется проверками соответствующего уровня
для ошибок и таймаутов; каждый сценарий не обязан повторять полную сборку.

Полноценный сценарий создания бронирования в этот этап не входит:
бизнес-операции ещё не реализованы. Временный демонстрационный CRUD
для проверки инфраструктуры не добавляется.

Архитектура зафиксирована в
[ADR-0015](../docs/adr/0015-unified-application-container.md), а порядок
миграций и совместимость версий — в
[ADR-0016](../docs/adr/0016-migrations-at-container-startup.md).

## Исходное состояние на момент проектирования

- HTTP-сервер читает только `HTTP_ADDR`, по умолчанию `127.0.0.1:8080`;
  подключение к БД в нём пока отсутствует.
- `cmd/migrate` выполняет встроенные миграции goose, принимает `-dsn`,
  ограничивает выполнение пятью минутами и обрабатывает SIGTERM/SIGINT.
  Блокировка конкурентных запусков миграций пока не настроена.
- Выбран PostgreSQL 18; существующая миграция создаёт техническую таблицу
  `example_records` с использованием `uuidv7()`.
- `/healthz` проверяет жизнь HTTP-процесса без обращения к БД.
  Его смысл закреплён в [ADR-0008](../docs/adr/0008-backend-liveness-endpoint.md).
- Сейчас frontend не вызывает API, а backend реализует только `/healthz`.
  Бизнес-операции описаны контрактом, но ещё не реализованы.
- Независимые приложения и отложенная интеграция описаны в
  [ADR-0001](../docs/adr/0001-standalone-frontend.md) и
  [ADR-0006](../docs/adr/0006-standalone-backend.md).
  Совместный контейнерный запуск теперь описан в ADR-0015.

## Границы задачи

В пределах описанного локального окружения открытых проектных решений
не осталось. Публикация образов, автоматический деплой и фактическое
развёртывание на Render обсуждаются отдельно. Для публичного запуска
с реальными данными отдельно определяются защита административной части,
резервное копирование и восстановление БД.
