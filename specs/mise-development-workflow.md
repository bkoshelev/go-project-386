# Окружение разработки через mise и hk

Статус: реализована; старт явно одобрен пользователем 7 ноября 2026 года.
Результаты и границы проверки: [отчёт](../docs/mise-workflow-validation.md).
Документ фиксирует решения интервью, начатого 7 ноября 2026 года.
Внедрение заменяет перечисленные ниже решения прежнего окружения
в соответствующей части.

## Цель

Согласовать использование mise hooks, Git hooks через hk и управление
сервисами разработки. Команды должны быть доступны разработчику и агенту.

## Согласованные решения

### Экспериментальные daemons — Q1

Пользователь согласовал экспериментальный режим, поскольку он обязателен
для mise daemons. Используется штатная интеграция mise с pitchfork;
его версия закрепляется как версия внутренней зависимости управления процессами.
Отдельный пользовательский интерфейс управления pitchfork не вводится.

### Переменные окружения — Q2

Пользователь согласовал отказ от direnv и перенос загрузки необязательного
`.env.local` текущего worktree в mise. Ручные команды и подготовка Orca
должны использовать одинаковое окружение без обязательной активации shell.
Это согласование требований, а не разрешение начать реализацию.

### Источник команд — Q3

Задачи mise становятся основным источником команд. Существующие сценарии
переносятся из Makefile и package scripts; ставшие ненужными определения
и обёртки удаляются. Разработчик, агент, CI и hk вызывают задачи mise.
Зависимости приложений и собственные конфигурации инструментов остаются
в предназначенных для них файлах. Состав переносимых сценариев и затронутых
потребителей определён разделом «Объём реализации».

### Источники версий — Q4

Mise читает Go из `backend/go.mod`, Node.js из `frontend/.nvmrc`,
pnpm из `frontend/package.json` (`packageManager`). Эти файлы не генерируются
из mise. Остальные версии инструментов закрепляются в `mise.toml`.

### Автоматическая подготовка — Q5

После установки инструментов mise hooks запускают повторяемую подготовку
зависимостей и установку согласованных hk hooks. При входе в проект выполняется
только лёгкая диагностика. Явная задача `setup` для Orca проверяет успешность
подготовки и завершается ошибкой при сбое. Подготовка браузерного окружения
включает Chromium. Назначение hk определено в Q10.

### Проверки Git — Q6

Пользователь исключил `pre-commit` и `pre-push`. Автоматические проверки
на этих событиях не устанавливаются.

### Назначение hk — Q10

Единственный Git hook — `commit-msg`. Он проверяет Conventional Commits
со списком типов, согласованным с текущей политикой release-please,
через общую задачу mise. Проверка не изменяет сообщение коммита.

### Заголовки PR — Q12

В CI добавляется отдельная проверка Conventional Commit-заголовка PR.
Она использует общий список типов и задачу mise проверки сообщений.
Проверка повторяется после изменения заголовка PR. Release-please workflow
сохраняет своё назначение подготовки релизов после push в main.
Изменение защиты ветки или настроек слияния GitHub этим решением не разрешено.

### Сервисы и их жизненный цикл — Q7, Q8

Mise daemons описывают PostgreSQL разработки, backend и frontend. Каждый
сервис можно запускать отдельно; также доступен запуск всего стека.
Запуск и остановка явные; вход и выход из каталога не меняют состояние сервисов.
Временные БД и процессы существующих тестов сохраняют собственный жизненный цикл.

### Изоляция worktree — Q9

Каждый worktree получает собственные процессы, данные PostgreSQL и порты.
Frontend проксирует запросы к backend своего worktree. Фиксированную привязку
Vite к backend на `127.0.0.1:8080` требуется заменить настройкой окружения.

### PostgreSQL разработки — Q11

Используется нативный пресет PostgreSQL в mise daemons. Данные каждого
worktree сохраняются после остановки; их удаление выполняется только
отдельной явной командой. Контейнеры существующих тестов и production Compose
сохраняют свои сценарии.

### Область установки hk — Q13

Hk устанавливается для Git-репозитория обычной локальной установкой
с интеграцией mise. Глобальная установка hk и изменение глобальных настроек
Git не выполняются. Каталог хуков репозитория общий для его worktree;
launcher использует конфигурацию и окружение того worktree, где вызван Git.
Отдельная изоляция Git hooks по worktree не требуется. Изоляция сервисов,
портов и данных из Q9 сохраняется независимо от области установки Git hooks.

### Режим подготовки и проверки — Q14

Обычный setup устанавливает инструменты, зависимости, Chromium и Git hook,
генерирует необходимые API-артефакты и проверяет готовность окружения.
`SETUP_VERIFY=1` дополнительно запускает полный набор backend/frontend-проверок,
как в существующем setup; другие значения, кроме 0 и 1, являются ошибкой.
При входе в каталог диагностика проверяет доступность и версии инструментов
и наличие hook launcher, сообщает о проблемах. Она не устанавливает зависимости,
не изменяет исходники, не запускает проверки приложения и сервисы.
Явная подготовка Orca сохраняет автоматическое доверие конфигурации текущего
worktree, уже принятое в спецификации существующего окружения.

## Объём реализации

1. Расширить корневой `mise.toml`: версии служебных инструментов, окружение,
   задачи, hooks, daemons и группа полного dev-стека. Короткие задачи хранить
   в TOML, длинные shell-сценарии — в файловых задачах `mise-tasks/`.
   Закрепить совместимые версии mise и pitchfork; не обновлять зависимости
   приложения попутно. Использовать штатный `mise.lock` для воспроизводимых
   установок на поддерживаемых платформах.
2. Перенести команды Makefile и scripts пакетов `api/` и `frontend/` в задачи
   mise. Установка backend-инструментов также управляется mise вместо
   самостоятельной загрузки архивов Makefile. Сохранить все существующие
   проверки, генераторы, миграции, сборку и контейнерный smoke-сценарий.
   Удалить лишние определения команд и обновить их потребителей.
3. Удалить `.envrc` и зависимость подготовки от direnv. Загружать необязательный
   `.env.local` текущего worktree через mise. Секреты и данные worktree не
   включать в Git и не копировать между рабочими деревьями.
4. Перевести `scripts/setup-worktree.sh` на минимальный bootstrap mise
   для существующего входа Orca. Собственно подготовка принадлежит задаче
   mise и доступна отдельно от Orca. Повторные запуски поддерживаются.
   `postinstall` и явный setup используют общие шаги без рекурсии;
   явный setup проверяет результат и возвращает ненулевой код при сбое.
5. Добавить `hk.pkl` только с `commit-msg`, установку hook launcher в setup
   и задачу проверки сообщения. Список допустимых типов брать из текущей
   release-политики, включая `feature` и `deps`, без второго списка типов.
   Не добавлять верхнеуровневые hk steps, создающие ненужный `pre-commit`.
6. Добавить проверку заголовка PR в CI на события открытия, переименования,
   обновления ветки и повторного открытия. Использовать общую задачу и
   валидатор сообщений; служебные исключения локального Git вроде `fixup!`
   и autogenerated merge messages не считать Conventional Commit-заголовками PR.
   Заголовок читать как данные из события GitHub, не вставлять в shell-код.
7. Описать нативный PostgreSQL 18, backend и frontend через mise daemons.
   Настроить готовность БД и backend (`/readyz`), передачу подключения и адресов
   между зависимыми сервисами. Порты и namespace выделяются по worktree.
   Vite использует адрес соответствующего backend из окружения.
   Запуск любого сервиса поднимает необходимые ему зависимости.
8. Предоставить явное управление стеком через mise daemons: запуск,
   остановка, перезапуск, состояние и логи; отдельно — очистку данных
   PostgreSQL только текущего worktree. Остановка не удаляет данные.
   Занятый порт приводит к понятной ошибке, а не к остановке чужого процесса.
9. Перевести существующие backend/frontend/container workflows и builder-стадии
   Dockerfile на задачи mise. В CI и контейнерной сборке отключать локальные
   автоматические действия hooks; явно готовить только нужные конкретной
   проверке зависимости. Hk не устанавливает Git hooks в CI и сборке.
   В конечный production-образ mise, hk и pitchfork не добавляются.
10. Обновить README, инструкции frontend, AGENTS и актуальные спецификации
    с новыми командами. Отметить заменённые решения ADR, сохранив их историю.

## Границы

- Поддерживаемые среды: macOS и Linux на amd64/arm64; Windows через WSL,
  как в существующем окружении. Нативный Windows не добавляется.
- Не сохраняется совместимость с прежними командами Makefile/package scripts.
  `scripts/setup-worktree.sh` остаётся bootstrap входом действующей интеграции Orca.
- Runtime production-контейнера, release-please и единая версия продукта
  сохраняют назначение. Обновление builder-стадий не меняет схему деплоя.
- Конфигурация защиты ветки и настроек слияния GitHub, внешние сервисы
  и workflow `hexlet-check.yml` не изменяются.
- Тестовые PostgreSQL-контейнеры и backend-процессы не заменяются dev-daemons.
  Полные тесты по-прежнему требуют Docker; unit-тесты работают без него.
- Отсутствие shell activation не мешает setup, задачам, Git hooks и явному
  управлению daemons. Только автоматическая диагностика `enter` требует
  активации shell; её настройка описывается в документации.
- Предметный `GLOSSARY.md` не меняется: инструменты окружения не являются
  терминами предметной области бронирования встреч.

## Критерии приёмки

| ID | Ожидаемое поведение |
| --- | --- |
| AC-01 | Все команды подготовки, запуска, сборки, генерации и проверок доступны через mise; потребителей удалённых команд не осталось. |
| AC-02 | Go, Node.js и pnpm соответствуют согласованным источникам версий; остальные инструменты закреплены, Go не переключает toolchain автоматически. |
| AC-03 | Чистый setup и повторный setup успешны без direnv и shell activation; отсутствие `.env.local` допустимо; значения worktree не смешиваются. |
| AC-04 | Сбой подготовки приводит к ошибке явного setup; `SETUP_VERIFY=1` выполняет полный прежний набор проверок, режим по умолчанию его не запускает. |
| AC-05 | `enter` только диагностирует окружение; `postinstall` выполняет повторяемую подготовку без рекурсии; CI и Docker не устанавливают локальные хуки. |
| AC-06 | Единственный Git hook проекта — `commit-msg`; корректные сообщения, scope, breaking marker и разрешённые типы принимаются, некорректные отклоняются без изменения сообщения. |
| AC-07 | PR title проверяется в CI, включая `edited`; некорректные и служебные Git-заголовки отклоняются. Данные заголовка не выполняются как команды. |
| AC-08 | Каждый daemon и весь стек можно явно запустить, остановить и перезапустить; состояние и логи доступны; backend ожидает готовность БД. |
| AC-09 | Два worktree одновременно запускают независимые стеки с разными портами и БД; frontend каждого обращается к своему backend. |
| AC-10 | После остановки и повторного запуска записи dev-БД сохраняются; явная очистка затрагивает только выбранный worktree. |
| AC-11 | Полные backend-тесты с race detector, генерация, frontend-проверки, браузерные и контейнерные smoke-тесты сохраняют прежние гарантии. |
| AC-12 | Установка hk не меняет глобальные Git-настройки и не устанавливает хуки для других репозиториев; production-образ запускается без mise/hk/pitchfork. |

## Способ проверки

- Проверить TOML и дерево задач средствами mise, конфигурацию hk — `hk validate`.
- Во временных конфигурационных каталогах проверить установку версий,
  чистую/повторную подготовку, отсутствие env-файла, ошибки подготовки
  и отсутствие рекурсивного запуска hooks.
- В отдельном временном Git-репозитории проверить фактический `commit-msg`,
  список устанавливаемых hooks и отсутствие изменений глобального конфига.
  Проверить разрешённые типы, scope, `!`, некорректные заголовки, пути с пробелами
  и специальные символы. Отдельно проверить строгий режим заголовков PR.
- Запустить два изолированных dev-worktree, проверить `/readyz`, прокси Vite,
  разделение данных, остановку/повторный запуск и очистку одной dev-БД.
  Проверочные данные создавать только в тестовых рабочих деревьях.
- Выполнить перенесённые backend quality gates и frontend quality/build/smoke,
  включая unit-тесты с недоступным Docker и полные тесты с доступным Docker.
- Собрать production-контейнер и выполнить существующий контейнерный smoke-тест.
  Выполнить соответствующие проверки workflows и проверить обработку события
  переименования PR. Проверки на GitHub после публикации отдельно отразить
  в отчёте, не выдавая локальную проверку за выполненный запуск Actions.

## Проверенные ограничения

- Штатные mise daemons требуют `experimental = true` либо
  `MISE_EXPERIMENTAL=1` и используют pitchfork. Переменная окружения
  не переводит функцию в стабильный режим.
- Официальное руководство разрешает оборачивать существующие команды
  пакетного менеджера задачами mise. Полная миграция команд не обязательна.
- У текущего репозитория общий каталог Git hooks для worktree;
  принята обычная локальная установка для репозитория (Q13).
- `hk util check-conventional-commit` совместим с форматом сообщений,
  используемым release-please. Для текущей политики проекта список типов
  должен включать `feature` и `deps` из `release-please-config.json`:
  в стандартном списке hk их нет. Проверка заголовка не проверяет смысл
  release-футеров в теле сообщения.
- При squash merge GitHub создаёт новое сообщение коммита, которое можно
  отредактировать независимо от локально проверенных сообщений. Локальный
  `commit-msg` не обеспечивает проверку заголовка PR или итогового squash-коммита.
