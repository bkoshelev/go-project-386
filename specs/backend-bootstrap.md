# Минимальный backend на Go и Gin

Статус: спецификация по результатам интервью; реализация ещё не начата.

## Цель

Подготовить самостоятельный backend сервиса бронирования календаря: сервер на
Go и Gin, минимальный эндпоинт проверки жизни процесса, сохраняемый smoke-тест
и проверки в GitHub Actions. Разработчик должен иметь возможность подготовить
окружение, запустить сервер и проверить его обычными Go-командами.

## Исходное состояние

- В репозитории есть самостоятельный frontend на React, TypeScript и Vite.
- Go-модуля и backend-кода пока нет.
- Есть workflows фронтенда, Хекслета и release-please.
- У продукта общая версия в корневом `version.txt`; отдельный поток релизов
  backend не требуется.

## Согласованные требования

### Границы и структура

- Backend размещается в самостоятельной папке `backend/` относительно корня
  репозитория. Установка, запуск, тесты и сборка выполняются из этой папки.
- Go-модуль: `github.com/bkoshelev/go-project-386/backend`.
- Точка входа — `cmd/server`; конфигурация, HTTP-роутер и управление жизненным
  циклом сервера находятся в `internal`.
- Структура компактная: слои service/repository и интерфейсы появляются вместе
  с реальными потребителями, а не создаются пустыми заранее.
- Конструктор роутера общий для приложения и тестов. Тест не должен дублировать
  регистрацию маршрута или подменять обработчик собственной реализацией.
- Backend запускается независимо от frontend. Интеграция с браузером,
  совместная команда запуска и раздача frontend сервером в задачу не входят.

### Инструменты и версии

- Язык — Go, HTTP-фреймворк — Gin, assertions в тестах — testify.
- Перед реализацией проверить актуальные стабильные версии по официальным
  источникам, выбрать совместимые версии и закрепить их в проекте.
- Установленная на машине версия Go сама по себе не определяет выбор версии.
- Хранить `go.mod` и `go.sum`. CI получает версию Go из `go.mod`; обновления
  Go и зависимостей выполняются явными изменениями проекта.
- Не добавлять другой тестовый фреймворк или сторонний конфигурационный пакет
  для возможностей, которые покрывает стандартная библиотека.

### Минимальный эндпоинт

- `GET /healthz` доступен без авторизации.
- Ответ: HTTP `200`, `Content-Type: application/json; charset=utf-8`,
  JSON `{"status":"ok"}`.
- Ответ фиксирован: без времени, версии продукта и сведений об окружении.
- Успех означает, что процесс обслуживает HTTP-запросы. Он не подтверждает
  доступность БД или готовность выполнять будущие операции календаря.
- При появлении внешних зависимостей не превращать этот эндпоинт в readiness
  без отдельного решения; отдельная readiness-проверка сейчас не нужна.
- Для других запросов оставить стандартное поведение Gin: ошибки,
  неподдерживаемые методы и перенаправление завершающего слеша.
- Не включать отдельную обработку 405 и не вводить единый JSON-контракт ошибок.
  JSON гарантируется только для успешного `/healthz`.

### Конфигурация и запуск

- Создавать роутер через `gin.New()` и явно подключать middleware логирования
  и восстановления после panic.
- Приложение работает в release mode; тесты — в test mode.
- Отключить доверие proxy-заголовкам через `SetTrustedProxies(nil)`.
- Использовать явный `http.Server` с таймаутами, а не ограничиваться `router.Run`.
- Единственная прикладная переменная окружения — `HTTP_ADDR`.
- При отсутствии `HTTP_ADDR` слушать `127.0.0.1:8080`. Для доступа из сети адрес
  меняется явно. Заданное пустое значение считается ошибкой.
- `.env` автоматически не загружается.
- Ошибка адреса и занятый порт приводят к понятному сообщению в логах и
  ненулевому коду завершения; сервер не переключается на другой порт молча.
- Таймауты фиксируются в коде: `ReadHeaderTimeout=5s`, `ReadTimeout=10s`,
  `WriteTimeout=10s`, `IdleTimeout=60s`.

### Остановка и восстановление после ошибок

- Обрабатывать SIGINT и SIGTERM: остановить приём новых соединений и дать
  текущим запросам до 10 секунд на завершение.
- Если срок истёк, принудительно закрыть соединения, записать ошибку и вернуть
  ненулевой код завершения. Штатная остановка возвращает ноль.
- Ожидаемое закрытие HTTP-сервера при штатной остановке не считать ошибкой запуска.
- Panic в обработчике перехватывается middleware: клиент получает стандартный
  для Gin ответ 500 без внутренних подробностей, процесс продолжает работать.
- Не добавлять публичный маршрут для искусственного вызова panic.

### Логи и удобство разработки

- Использовать `log/slog` с JSON-выводом в stdout.
- Записывать события запуска, остановки и ошибки, включая диагностику panic.
- Логировать каждый запрос, включая успешный `/healthz`: метод, путь без
  query-параметров, статус и длительность.
- Не записывать тела запросов и заголовки. Не создавать параллельный текстовый
  access-log Gin поверх структурированных логов.
- Для обычного запуска достаточно Go-команд; Makefile, task runner и hot reload
  не являются требованиями этой задачи.

### Smoke-тест и дополнительные проверки

- Smoke-тест использует `testing`, `net/http/httptest` и `testify`.
- Создать общий роутер приложения, подготовить запрос к `/healthz`, передать его
  через `ServeHTTP` и получить ответ через `httptest.NewRecorder`.
- Проверять статус, Content-Type и JSON семантически, без зависимости от
  пробелов и порядка полей.
- Smoke выполняется без сети, открытого порта, заранее запущенного сервиса и
  отдельного процесса. Он проверяет маршрут и middleware, но не запуск бинарника.
- Имя проверки — `TestSmokeHealth`. Она входит в `go test ./...`; отдельный
  запуск: `go test ./... -run TestSmokeHealth -count=1`.
- Дополнительно проверить ошибочную конфигурацию, отказ запуска на занятом порту
  и корректную остановку HTTP-сервера, включая истечение срока ожидания.
- Для тестов жизненного цикла использовать свободные локальные порты,
  контролируемые обработчики и синхронизацию без фиксированных задержек.
  Тесты не должны оставлять серверы и фоновые задачи после завершения.
- Восстановление после panic проверить обработчиком, зарегистрированным только
  в тесте; проверить ответ 500 и возможность обслужить следующий запрос.
- При реализации отдельно проверить запуск собранного бинарника, ответ по HTTP
  и остановку по сигналу. Эта проверка дополняет smoke, не меняя его границу.

### GitHub Actions

- Добавить отдельный backend-workflow на `push` и `pull_request`.
- Все Go-команды выполняются из `backend/`.
- Использовать выбранную версию Go из `go.mod` и зависимости из `go.mod`/`go.sum`.
- Обязательные проверки: `gofmt` без перезаписи файлов, `go vet ./...`,
  `go test -race ./...`, `go build ./...`.
- Несоответствие форматированию или сбой любой проверки делает workflow
  неуспешным. Не добавлять golangci-lint в рамках этой задачи.
- Workflow должен работать в чистом окружении без frontend и прикладных сервисов.
- Существующие workflows, включая `.github/workflows/hexlet-check.yml`,
  не изменять. Механизм общей версии и релизов продукта сохраняется.

### Документация и артефакты

Обновить корневой README: требования к Go, подготовка окружения, запуск,
`HTTP_ADDR`, пример `curl`, сборка, тесты и смысл проверки жизни процесса.

Команды из `backend/`:

```bash
go mod download
go run ./cmd/server
go test ./...
go test ./... -run TestSmokeHealth -count=1
go vet ./...
go test -race ./...
go build -o bin/server ./cmd/server
```

Проверка запущенного сервера:

```bash
curl -i http://127.0.0.1:8080/healthz
```

Исключить `backend/bin/` из Git. Исходники, тесты, `go.mod`, `go.sum`, workflow
и инструкции должны храниться в репозитории.

## Не входит в задачу

- Бизнес-логика календаря, БД, миграции, авторизация и прикладной API.
- Frontend-интеграция, CORS и совместный запуск компонентов.
- Docker, хостинг, TLS, настройка reverse proxy и deployment.
- Readiness, метрики, request ID, трассировка и передача версии в бинарник.
- Унификация ошибок API и дополнительные конфигурационные форматы.

## Критерии приёмки

1. После чистого клонирования можно подготовить указанный Go, установить
   зависимости и запустить backend по README независимо от frontend.
2. Сервер по умолчанию доступен на `127.0.0.1:8080`; `HTTP_ADDR` меняет адрес.
   Пустая настройка, неверный адрес и занятый порт дают понятную ошибку запуска.
3. `/healthz` соблюдает согласованный контракт и не раскрывает внутренние данные.
4. Smoke использует тот же роутер, что приложение, запускается стандартной
   командой и проверяет статус, тип содержимого и JSON.
5. Есть проверяемые таймауты и корректная остановка по сигналам с пределом
   ожидания 10 секунд; panic обработчика не завершает процесс.
6. Диагностические и access-логи имеют согласованный JSON-формат, не включают
   query-параметры, заголовки или тела запросов.
7. Проверки форматирования, vet, race-тесты и сборка проходят локально;
   отдельный workflow воспроизводит их в чистом окружении.
8. Собранный бинарник отдельно проверен на запуск, HTTP-ответ и остановку.
9. Документация и зависимости сохранены, артефакты сборки исключены из Git,
   существующие frontend и release-процессы не изменены.

При завершении реализации перечислить фактически выполненные проверки.
Локальный успех не считать подтверждением успешного запуска GitHub Actions:
если workflow ещё не запускался на GitHub, отметить это отдельно.

## Происхождение решений и defaults

Go и Gin — исходные требования пользователя. В интервью выбраны самостоятельный
backend, компактная структура, liveness-эндпоинт, httptest с testify, localhost
по умолчанию, стандартные ошибки Gin, slog JSON для всех запросов, минимальный
env, остановка за 10 секунд, базовый набор CI и актуальные стабильные версии.

Точные пути пакетов, имя Go-модуля, тело и заголовок успешного ответа, значения
HTTP-таймаутов, трактовка пустого `HTTP_ADDR` и имена команд конкретизированы
в итоговом плане. Они являются defaults реализации, а не отдельными решениями
пользователя по результатам сравнения альтернатив.
