# Автоматизация релизов с release-please

Статус: реализовано.

## Цель

Настроить release-please для подготовки единого SemVer-релиза продукта. После
изменений в основной ветке инструмент должен создавать или обновлять release PR,
а после его ручного слияния — создавать Git-тег и GitHub Release.

Решение должно:

- поддерживать один номер версии для frontend и будущего Go-backend;
- хранить доступную при локальной сборке версию в корневом `version.txt`;
- формировать `CHANGELOG.md` из Conventional Commits;
- не публиковать пакеты, контейнеры и приложение автоматически;
- оставлять решение о выпуске релиза и любого нового major за командой.

## Контекст и исходное состояние

- Основная ветка репозитория — `main`.
- Опубликованных Git-тегов и GitHub Releases пока нет.
- Фронтенд находится в `frontend/`, является приватным приложением и содержит
  техническую версию `0.0.0` в `frontend/package.json`.
- Go-backend будет добавлен отдельно.
- Репозиторий уже содержит workflow release-please, manifest, конфигурацию и
  `CHANGELOG.md`.
- Action закреплён на полном SHA версии `v4.4.1` и использует release-please
  `17.3.0`.
- Исходная конфигурация использовала `release-type: generic`. Такого release
  type нет: `generic` является updater для `extra-files`, а не релизной
  стратегией. До первого реального запуска конфигурация исправлена на `simple`.
- В `.github/workflows/hexlet-check.yml` находится защищённая проверка Хекслета,
  которую нельзя изменять.

## Как должен работать релиз

1. Изменения попадают в `main`.
2. Release-please анализирует Conventional Commits после предыдущего релиза.
3. Инструмент создаёт или обновляет единый release PR.
4. Release PR обновляет `.release-please-manifest.json`, `version.txt` и
   `CHANGELOG.md`.
5. Команда вручную решает, когда слить release PR.
6. После слияния workflow создаёт тег `vX.Y.Z` и GitHub Release.

Само наличие release PR не означает выпуск версии. Release-please не выполняет
deployment, не публикует npm-пакет, Go-модуль, контейнер или бинарный файл и не
проверяет формат сообщений коммитов.

## Единица релиза

- Репозиторий имеет одну общую версию продукта.
- Корневой путь `.` является единственным компонентом release-please.
- Frontend и будущий backend входят в один release PR и один changelog.
- Теги имеют вид `vX.Y.Z` без имени компонента.
- Первый релиз имеет версию `0.1.0`.
- Независимые циклы релизов компонентов не создаются.

Решение зафиксировано в
[ADR-0004](../docs/adr/0004-single-product-release.md).

## Хранение версии

### Корневой `version.txt`

В корне репозитория необходимо создать `version.txt` с первоначальным
содержимым:

```text
0.0.0
```

Release-please должен обновить его до `0.1.0` в первом release PR и затем
обновлять при каждом релизе. Файл содержит только SemVer-версию и завершающий
перевод строки.

`version.txt` — доступное из checkout представление версии продукта. Его можно
использовать при локальной сборке, а в будущем читать или встраивать во frontend,
Go-backend, диагностические ответы, логи и метаданные контейнера без обязательной
зависимости от Git или CI.

Commit SHA при необходимости передаётся сборкой отдельно. Он дополняет номер
релиза, но не заменяет его.

Выбор репозиторного файла версии зафиксирован в
[ADR-0005](../docs/adr/0005-repository-product-version.md).

### `frontend/package.json`

- `frontend/package.json` не является источником версии продукта.
- Его поле `version` остаётся техническим значением `0.0.0`.
- Файл не добавляется в `extra-files` и не обновляется release-please.
- Наличие общей версии в `version.txt` не превращает frontend в публикуемый
  npm-пакет.

## Выбранные стратегии release-please

### Release type

Используется `release-type: simple` с явным `version-file: version.txt`.

`simple` выбран вместо рассмотренных вариантов:

- `generic` недопустим как release type;
- `go` без `version-file` обновлял бы только changelog и не обеспечивал бы
  локально доступную версию;
- `node` потребовал бы использовать и обновлять `package.json`, что не
  соответствует единой версии продукта и приватному frontend-приложению.

### Versioning

Используется встроенная стратегия `versioning: default` с параметром
`bump-minor-pre-major: true`.

`bump-patch-for-minor-pre-major` не включается. Prerelease-стратегия не
используется.

Правила вычисления версии:

| Условие | До `1.0.0` | Начиная с `1.0.0` |
| --- | --- | --- |
| `fix` | patch | patch |
| `feat` | minor | minor |
| Breaking marker | minor | major по механике `default` |

До `1.0.0` обычная новая возможность и несовместимое изменение оба повышают
minor. Тип и несовместимость изменения всё равно должны быть видны в сообщении
коммита и changelog.

### Ручное решение о major

Любой переход на новый major выполняется только после отдельного решения
команды. Встроенная стратегия `default` не умеет одновременно сохранять
`fix → patch`, `feat → minor` и запрещать автоматический major, поэтому правило
обеспечивается командной договорённостью:

- `!` и футер `BREAKING CHANGE:` не должны попадать в `main` без согласованного
  major-релиза;
- отдельная CI-проверка этого правила не добавляется;
- после принятия решения точная версия задаётся явно футером коммита, например:

  ```text
  Release-As: 1.0.0
  ```

Команда принимает риск того, что случайный breaking marker после `1.0.0`
заставит `default` предложить major-релиз. Release PR остаётся ручной точкой
контроля и не должен сливаться без проверки номера версии.

### Changelog

Используется стандартный `changelog-type: default` (его можно не указывать
явно). Release notes и `CHANGELOG.md` формируются release-please из Conventional
Commits. Генерация notes средствами GitHub не используется.

## Conventional Commits

Значимый заголовок имеет вид:

```text
<type>(<optional scope>): <description>
```

Примеры:

| Сообщение | Значение |
| --- | --- |
| `fix: исправить отображение даты` | Исправление, patch-релиз |
| `feat: добавить повторяющиеся встречи` | Возможность, minor-релиз |
| `feat(frontend): добавить календарную сетку` | Возможность с необязательным scope |
| `docs: уточнить запуск проекта` | Само по себе релиз не инициирует |

Breaking markers используются только в соответствии с политикой ручного major.
До `1.0.0` они допустимы для согласованных несовместимых изменений и благодаря
`bump-minor-pre-major` повышают minor.

Для обычных pull request рекомендуется squash merge с Conventional Commit в
заголовке PR. Тогда в `main` попадает один понятный коммит, а в changelog — одна
запись на завершённое изменение. При другом способе merge все анализируемые
release-please сообщения всё равно должны соответствовать Conventional Commits.

Commitlint, Git hooks, branch protection и CI-проверка заголовков в эту задачу не
входят.

## Требуемая конфигурация

`release-please-config.json` должен иметь следующий смысл:

Параметры конфигурации и причины выбора значений:

| Параметр | Выбранное значение | Назначение и причина выбора |
| --- | --- | --- |
| `$schema` | URL официальной схемы release-please | Включает проверку структуры и подсказки параметров в редакторе. |
| `packages` | Объект с конфигурациями компонентов | Переводит release-please в manifest mode и объединяет настройки релизных компонентов. |
| `packages["."]` | Корневой компонент | Задаёт один общий релиз для всего продукта, включая frontend и будущий backend. |
| `release-type` | `simple` | Использует простую релизную стратегию с changelog и отдельным файлом версии без привязки к менеджеру пакетов. |
| `versioning` | `default` | Вычисляет следующее значение SemVer по Conventional Commits: `fix` повышает patch, `feat` — minor, а breaking change после `1.0.0` — major. |
| `version-file` | `version.txt` | Делает общую версию продукта доступной из checkout и позволяет использовать её при локальной сборке. |
| `initial-version` | `0.1.0` | Задаёт номер первого выпуска, пока в manifest ещё нет ранее выпущенной версии. |
| `bump-minor-pre-major` | `true` | До `1.0.0` ограничивает breaking change повышением minor вместо major. |
| `include-component-in-tag` | `false` | Исключает имя компонента из тега, поскольку продукт выпускается как единое целое. |
| `include-v-in-tag` | `true` | Формирует теги в принятом формате `vX.Y.Z`. |
| `changelog-path` | `CHANGELOG.md` | Указывает общий журнал изменений в корне репозитория. |

Явные `versioning` и `version-file` сохраняются, хотя совпадают со стандартным
поведением `simple`: они документируют принятые решения и не заставляют читателя
знать неочевидные defaults.

До первого выпуска `.release-please-manifest.json` остаётся пустым объектом:

```json
{}
```

После слияния первого release PR release-please запишет в manifest текущую
выпущенную версию корневого компонента, например:

```json
{
  ".": "0.1.0"
}
```

Ключ `.` обозначает корневой компонент, а значение `0.1.0` — его последнюю
выпущенную версию. Manifest является состоянием release-please и обычно
обновляется самим инструментом, а не вручную.

## GitHub Actions

Workflow запускается только при push в `main` и использует manifest mode: input
`release-type` в самом workflow не задаётся, конфигурация читается из
`release-please-config.json` и `.release-please-manifest.json`.

Необходимые разрешения:

- `contents: write` — для тегов и GitHub Releases;
- `pull-requests: write` — для release PR.

Action остаётся закреплён полным commit SHA:

```yaml
uses: googleapis/release-please-action@5c625bfb5d1ff62eadeeb3772007f7f66fdcf071 # v4.4.1
```

Workflow использует `secrets.GITHUB_TOKEN`. Отдельный PAT не добавляется. В
настройках GitHub Actions репозитория должны быть разрешены write-доступ и
создание pull request.

## Документация

README должен кратко описывать:

- цепочку `commit → release PR → manual merge → tag and GitHub Release`;
- назначение корневого `version.txt`;
- правила `fix` и `feat`;
- особое поведение breaking changes до `1.0.0`;
- правило ручного решения о major;
- рекомендацию squash merge;
- отсутствие deployment и публикации пакетов в release-please workflow;
- ссылки на эту спецификацию, ADR-0004 и ADR-0005.

Полные детали процесса остаются в этой спецификации.

## Изменения в рамках задачи

Необходимо:

1. Заменить `release-type: generic` на `release-type: simple`.
2. Явно настроить `versioning`, `version-file` и
   `bump-minor-pre-major` согласно этой спецификации.
3. Создать корневой `version.txt` со значением `0.0.0`.
4. Актуализировать README и документацию, не описывая автоматический major как
   безусловно разрешённое поведение.
5. Сохранить существующий manifest, workflow и общий `CHANGELOG.md`, изменяя их
   только там, где это требуется настоящей спецификацией.

## Не входит в задачу

- Независимое версионирование frontend и backend.
- Изменение версии в `frontend/package.json`.
- Подключение `version.txt` к ещё не существующему backend.
- Отображение версии в текущем UI; файл лишь создаёт стабильный источник для
  последующей интеграции.
- Добавление commit SHA к версии сборки.
- Публикация npm-пакета, Go-модуля, контейнера или бинарного файла.
- Deployment.
- Автоматическое слияние release PR.
- Prerelease-, nightly-, maintenance- и backport-ветки.
- Commitlint, Git hooks, branch protection и отдельная CI-проверка breaking
  markers.
- Изменение `.github/workflows/hexlet-check.yml`.

## Проверка реализации

Необходимо выполнить и зафиксировать результат следующих проверок:

1. Проверить синтаксис JSON и YAML.
2. Провалидировать `release-please-config.json` по официальной JSON Schema.
3. Отдельно проверить, что `simple` зарегистрирован как release type в версии
   release-please, которую запускает закреплённый Action. Одной JSON Schema для
   этого недостаточно, поскольку поле `release-type` допускает строку.
4. Проверить, что `version.txt` содержит ровно валидный SemVer `0.0.0` и перевод
   строки.
5. Убедиться, что настроен один корневой компонент и теги не включают его имя.
6. Убедиться, что `frontend/package.json` не указан как обновляемый файл.
7. Убедиться, что workflow слушает только push в `main`, использует полный SHA и
   запрашивает только необходимые разрешения.
8. Проверить ссылки между README, спецификацией и ADR.
9. Запустить существующие локальные проверки проекта для выявления регрессий.

В рамках проверки нельзя создавать пробные коммиты, теги, release PR или GitHub
Release. Локальная проверка не является подтверждением успешной работы GitHub
Actions до первого реального запуска.

## Критерии приёмки

1. Конфигурация использует допустимый `release-type: simple`.
2. В корне существует `version.txt` с исходным значением `0.0.0`.
3. Первый release PR будет подготовлен с версией `0.1.0`.
4. Последующие `fix` повышают patch, а `feat` повышают minor.
5. Breaking change до `1.0.0` повышает minor.
6. Документация явно говорит, что major требует отдельного решения команды, и
   описывает использование `Release-As`.
7. Release PR обновляет одну общую версию, manifest, `version.txt` и
   `CHANGELOG.md`, не меняя `frontend/package.json`.
8. Теги имеют формат `vX.Y.Z` без имени компонента.
9. Релиз создаётся только после ручного слияния release PR.
10. Workflow не публикует и не развёртывает приложение или пакеты.
11. Существующие frontend- и Hexlet-workflow сохранены.
12. Спецификация, README и ADR не противоречат друг другу.
