# Автоматизация релизов с release-please

Статус: реализовано.

## Цель

Добавить release-please для автоматической подготовки SemVer-релизов проекта.
Инструмент должен анализировать Conventional Commits в основной ветке,
поддерживать release PR с changelog и после ручного слияния этого PR создавать
Git-тег и GitHub Release.

Автоматическая публикация приложения или пакета в registry в эту задачу не
входит.

## Исходное состояние

- Основная ветка репозитория — `main`.
- Опубликованных Git-тегов и GitHub Releases пока нет.
- В корне нет файла `CHANGELOG.md` и конфигурации release-please.
- Фронтенд находится в `frontend/`; его `package.json` содержит `private: true`
  и техническую версию `0.0.0`.
- Go-бэкенд будет добавлен отдельно.
- В `.github/workflows/hexlet-check.yml` находится защищённая проверка Хекслета,
  которую нельзя изменять.

## Зачем нужен release-please

Release-please превращает историю изменений в управляемый процесс релиза:

1. После изменений в `main` читает сообщения новых коммитов.
2. По Conventional Commits определяет следующую SemVer-версию и содержание
   release notes.
3. Создаёт или обновляет один release PR с новой версией и `CHANGELOG.md`.
4. Не выпускает версию, пока release PR не объединён вручную.
5. После его слияния создаёт тег `vX.Y.Z` и соответствующий GitHub Release.

Release-please не развёртывает приложение, не публикует npm-пакет и сам по себе
не отклоняет неправильно оформленные коммиты.

## Связь с Conventional Commits и SemVer

Conventional Commits — машиночитаемый формат сообщений, а release-please —
потребитель этих сообщений. Значимый заголовок имеет вид
`<type>(<optional scope>): <description>`.

| Сообщение | Значение | Изменение версии |
| --- | --- | --- |
| `fix: исправить отображение даты` | Исправление ошибки | patch |
| `feat: добавить повторяющиеся встречи` | Новая совместимая возможность | minor |
| `feat!: изменить формат календарного API` | Несовместимое изменение | major |
| `feat: изменить API` с `BREAKING CHANGE:` в теле | Несовместимое изменение | major |
| `docs:`, `test:`, `chore:` | Сопутствующие изменения | Сами по себе релиз не инициируют |

Текст после префикса должен описывать изменение для пользователя или
разработчика. Scope допустим, например `fix(frontend): ...`, но не обязателен.

До версии `1.0.0` поведение повышения версии определяется стандартной стратегией
release-please. Первый релиз проекта явно фиксируется как `0.1.0`, поэтому он не
зависит от автоматически вычисленной стартовой версии.

## Согласованные требования

### Единица релиза

- Репозиторий имеет одну общую версию продукта.
- Фронтенд и будущий Go-бэкенд не получают независимые циклы релизов.
- Теги имеют формат `vX.Y.Z` без имени компонента.
- Первый релиз имеет версию `0.1.0`.
- Prerelease-версии в этой задаче не настраиваются.

Решение о единой версии зафиксировано отдельно в
[ADR-0004](../docs/adr/0004-single-product-release.md).

### Версия приватного фронтенда

- `frontend/package.json` не является источником релизной версии продукта.
- Поле `version` остаётся равным `0.0.0` и не добавляется в `extra-files`.
- Актуальная релизная версия хранится в manifest release-please, Git-тегах и
  GitHub Releases.
- Решение можно пересмотреть отдельно, если версия понадобится внутри сборки,
  интерфейса приложения или диагностических данных.

### Конфигурация release-please

Необходимо добавить:

- `release-please-config.json` — конфигурацию одного корневого компонента;
- `.release-please-manifest.json` — manifest с текущей выпущенной версией;
- `.github/workflows/release-please.yml` — отдельный workflow;
- корневой `CHANGELOG.md`, который будет создавать и обновлять release PR.

Конфигурация должна:

- использовать корневой путь `.` и стратегию `generic`;
- задавать начальный релиз `0.1.0`;
- отключать имя компонента в теге;
- использовать стандартное SemVer-определение последующих версий;
- не обновлять `frontend/package.json` или другие прикладные файлы версии.

JSON-конфигурация должна ссылаться на официальную schema release-please, чтобы
редакторы и автоматические проверки могли валидировать доступные параметры.

### GitHub Actions

Workflow запускается только при push в `main`. Он получает минимально необходимые
разрешения:

- `contents: write` — для тегов и GitHub Releases;
- `pull-requests: write` — для создания и обновления release PR.

Action закрепляется полным commit SHA, а читаемая версия указывается комментарием:

```yaml
uses: googleapis/release-please-action@5c625bfb5d1ff62eadeeb3772007f7f66fdcf071 # v4.4.1
```

Плавающий тег `@v4` не используется: полный SHA исключает незаметную подмену
исполняемого кода при перемещении тега.

Workflow использует стандартный `GITHUB_TOKEN`; отдельный PAT в рамках задачи не
добавляется. В настройках репозитория для GitHub Actions должны быть разрешены
write-доступ и создание pull request. Существующие workflow не изменяются.

### Работа с pull request

Для обычных pull request рекомендуется squash merge и Conventional Commit в
заголовке PR. При squash GitHub создаёт в `main` один коммит, основанный на
заголовке PR. Именно этот итоговый коммит анализирует release-please, поэтому:

- тип изменения однозначно определяет повышение версии;
- в changelog появляется одна понятная запись на завершённое изменение;
- промежуточные сообщения из рабочей ветки не загрязняют release notes.

Например, заголовок `feat: добавить создание встречи` приведёт к minor-изменению,
а `fix: учитывать часовой пояс пользователя` — к patch-изменению.

Squash merge является рекомендацией, а не технически принуждаемой политикой.
Настройка branch protection, commitlint и отдельная проверка заголовков PR в эту
задачу не входят. Если используется другой способ merge, попавшие в `main`
сообщения всё равно должны соответствовать Conventional Commits.

### Управление релизом

- Release PR создаётся и затем обновляется по мере появления подходящих изменений
  в `main`.
- Само наличие release PR не означает выпуск версии.
- Решение о моменте выпуска принимает человек, вручную объединяя release PR.
- Автоматический merge не настраивается.
- После первого релиза следующие версии вычисляются из Conventional Commits после
  предыдущего релиза.

## Документация проекта

README необходимо дополнить кратким разделом о релизах:

- назначение release-please;
- схема `коммит → release PR → merge → тег и GitHub Release`;
- примеры `fix:`, `feat:` и breaking change;
- рекомендация squash merge и причина этой рекомендации;
- указание, что release-please не проверяет формат коммитов и не публикует
  приложение.

Полные детали остаются в этой спецификации, чтобы не перегружать README.

## Не входит в задачу

- Независимые версии frontend и backend.
- Изменение версии в `frontend/package.json`.
- Публикация npm-пакета, контейнера, бинарного файла или deployment.
- Автоматический merge release PR.
- Commitlint, git hooks и CI-проверка заголовков PR или сообщений коммитов.
- Настройка branch protection и правил GitHub repository.
- Prerelease-, nightly- и maintenance-ветки.
- Изменение существующих frontend- и Hexlet-workflow.

## Проверка реализации

- Проверить синтаксис нового YAML и JSON-файлов.
- Провалидировать конфигурацию по официальной JSON Schema release-please.
- Убедиться, что workflow слушает только push в `main`, использует полный SHA
  action и содержит только необходимые разрешения.
- Проверить, что конфигурация описывает один корневой компонент, общий changelog и
  теги без имени компонента.
- Убедиться, что `frontend/package.json` не указан как обновляемый файл.
- Проверить ссылки между README, спецификацией и ADR.
- Запустить существующие локальные проверки проекта для выявления регрессий.
- Не создавать в рамках проверки пробные коммиты, теги, release PR или GitHub
  Release.

## Критерии приёмки

1. В репозитории есть синтаксически корректные workflow, config и manifest
   release-please.
2. Action закреплён полным SHA версии `v4.4.1` и запускается при push в `main`.
3. Workflow запрашивает только `contents: write` и `pull-requests: write`.
4. Настроен один общий релиз продукта с первым номером `0.1.0` и тегами
   `vX.Y.Z`.
5. Release PR управляет корневым `CHANGELOG.md`, но не меняет версию приватного
   frontend-приложения.
6. README объясняет назначение инструмента, Conventional Commits, SemVer и
   рекомендуемый способ merge.
7. Существующие workflow и проверки проекта сохранены.
8. Спецификация и ADR содержат взаимные ссылки.

При завершении реализации необходимо перечислить фактически выполненные проверки.
Локальная валидация конфигурации не считается подтверждением успешной работы
GitHub Actions до первого реального запуска workflow.
