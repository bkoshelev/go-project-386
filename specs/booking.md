# Спецификация приложения бронирования — MVP

Ревизия требований: **1**. Статус: **утверждена пользователем 19 октября 2026 года**.
Спецификация, экраны, HTTP-контракт и схема приняты как основа для декомпозиции
на реализационные тикеты.

Каноническая [спецификация в GitHub](https://github.com/bkoshelev/go-project-386/issues/31).
Этот файл — локальный снимок полного комплекта требований. Точные версии артефактов
зафиксированы в [манифесте](booking-spec-manifest.json) контрольными суммами SHA-256.

## Участники и первая версия

В системе один заранее заданный профиль владельца календаря. Он автоматически
используется административной частью. Профиль содержит `fullName` для заголовка
«Создать встречу с [Full Name владельца]»; публичный API возвращает его из данных
единственного профиля. Начальное заполнение профиля относится к реализации,
его редактирование через интерфейс не требуется.

Гость выбирает тип встречи и время, вводит имя и email и создаёт бронирование.
Регистрации, авторизации и аккаунтов гостей нет. Владелец создаёт типы событий,
настраивает доступность и общую паузу, видит единый список предстоящих встреч.

Один календарь обслуживает все типы событий: занятость и пауза общие.

## Типы событий и идентификаторы

Тип события содержит UUID, название, необязательное описание и `durationMinutes`.
UUID генерируется на уровне таблицы БД при создании. Владелец его не вводит;
frontend и backend не подменяют генерацию на уровне БД. В HTTP это строка UUID.
Названия могут совпадать: различие определяется по ID. Название после удаления
пробелов по краям должно быть непустым. Описание можно опустить или оставить пустым.

При создании интерфейс содержит положительное целое число и переключатель единицы:

| Единица ввода | Допустимое значение | Значение в API и БД |
| --- | --- | --- |
| Минуты | 1–60 включительно | То же число минут |
| Часы | 1–23 включительно | Число часов × 60 |

Исходная единица не сохраняется: 60 минут и 1 час равнозначны. Допустимые хранимые
значения — целые 1–60 и 120, 180, …, 1380. При таком вводе 61 и 90 минут не задаются.

Выбор UUID принят пользователем после сравнения с автоинкрементным целым:

| Вариант | Преимущества | Цена выбора |
| --- | --- | --- |
| Автоинкрементное целое | Компактное хранение и индексы; простота для одной БД | Идентификаторы зависят от числовой последовательности конкретной базы |
| UUID | Не зависит от общего счётчика; удобен как публичный идентификатор и при объединении независимых наборов данных | Больше размер идентификатора и индекса; случайные UUID могут иметь худшую локальность вставок |

UUID не выбран ради обещания более высокой скорости. Для одной БД числовой ID
также был бы достаточным; UUID соответствует явно выбранному формату и снижает
зависимость идентификаторов от последовательности одной базы. Бинарный UUID занимает
128 бит; конкретная версия генератора и SQL-выражение определяются после выбора СУБД.
При этом можно оценить UUIDv7 для упорядоченности вставок; обязательной версии UUID
спецификация не задаёт. Определение UUID и UUIDv7 — [RFC 9562](https://www.rfc-editor.org/rfc/rfc9562.html).
ID бронирования также генерируется БД как UUID по принятому контракту.

## Модель времени

Различаются местные часы расписания и абсолютные моменты встреч:

- Расписание — местные дни недели, даты и часы `HH:mm` в сохранённом IANA-поясе владельца.
- Первый корректный пояс, определённый браузером владельца, однократно сохраняется
  для календаря. Поездки, другой браузер и повторное сохранение настроек его не меняют.
  Ручной смены пояса в MVP нет. Инициализация атомарна; браузер гостя её не выполняет.
- Редактор расписания явно подписывает сохранённый пояс. Конкретные встречи каждый
  пользователь видит в текущем автоматически определённом поясе своего браузера.
- Начало и окончание бронирований хранятся как UTC-моменты. HTTP передаёт RFC 3339;
  ответы нормализованы в UTC с `Z`, входной момент с числовым смещением нормализуется в UTC.
- Начало встречи задаётся с точностью до целой минуты: секунды и доли секунды равны нулю.
  Длительность встречи и пауза измеряются прошедшими минутами.
- Границы интервалов — `[начало, конец)`. `24:00` допускается только как окончание
  интервала местной даты и означает начало следующих местных суток.

Сезонный перевод часов целиком отложен после MVP: требования и проверки для
изменения смещения, отсутствующих и повторяющихся местных часов находятся
в [отдельной задаче](https://github.com/bkoshelev/go-project-386/issues/32).
Это не отменяет обычного преобразования между местным временем и UTC и не заменяет
IANA-пояс постоянным числовым смещением.

## Расписание и блокировки

В недельном расписании ровно семь записей, каждый день указан один раз. Для дня
задаются `isBlocked` и несколько интервалов с началом раньше окончания. Интервалы
в пределах дня не пересекаются; касание разрешено и даёт непрерывную доступность.

Для конкретной местной даты задаётся отдельный флаг блокировки и необязательные
собственные интервалы. Приоритеты и последствия:

| Состояние | Доступность и сохранённые данные |
| --- | --- |
| День недели заблокирован | День закрыт, настройкой конкретной даты открыть его нельзя; недельные интервалы сохраняются |
| День недели разблокирован | Сохранённые недельные интервалы снова действуют с учётом настройки даты |
| Конкретная дата заблокирована | Весь местный день закрыт; собственные интервалы этой даты удаляются |
| Дата разблокирована без собственных интервалов | Наследует недельные интервалы, если день недели открыт |
| День недели и дата открыты, собственные интервалы заданы | Интервалы даты полностью заменяют недельные, а не дополняют их |
| Собственные интервалы отсутствуют | Используются недельные; копии для каждой календарной даты не хранятся |
| Явный список `intervals: []` при `isBlocked: false` | Рабочих часов нет; флаг блокировки при этом не устанавливается автоматически |

До настройки все дни заблокированы, интервалы пусты, общая пауза равна 0.
Владелец самостоятельно открывает дни и задаёт интервалы. До успешной инициализации
пояса доступных слотов нет; ошибки определения и сохранения пояса показываются явно.

## Правила свободного времени

Backend вычисляет доступность по выбранному типу, расписанию, блокировкам,
существующим бронированиям всех типов и общей паузе.

1. Начало строго позже серверного текущего момента; дополнительного минимального ожидания нет.
2. Окно — сегодня и следующие 13 календарных дат **UTC**. Вся встреча должна быть
   внутри окна. Начало окна включено, полночь после последней даты — исключённая
   граница интервала; окончание встречи ровно в этой границе допускается.
3. Встреча целиком помещается в непрерывное доступное время. Переход через полночь
   разрешён; проверяются все затронутые местные даты владельца.
4. Предлагаемые начала идут по `:00/:15/:30/:45 UTC`. Вручную гость может задать
   любую целую минуту, например 10:07, при соблюдении остальных правил.
5. Встреча не пересекается с существующими бронированиями любого типа.
6. Между соседними встречами выдерживается одна общая пауза: целое число 0–60 минут.
   Она проверяется и до, и после нового бронирования, в том числе через полночь.
   При паузе 0 встречи могут соприкасаться.

Расписание переводится в UTC для расчёта конкретных интервалов. Перевод окна в пояс
гостя может затронуть части дополнительных местных дат; его UTC-границы не меняются.
Владельцу показывается весь список будущих/текущих встреч, без ограничения этим окном.

Изменения расписания, блокировки или паузы действуют на новые бронирования.
Уже созданные встречи не отменяются и не переносятся; их интервалы остаются занятыми.

## Создание, конкуренция и повтор

Запрос содержит `eventTypeId`, `startsAt`, `guest { name, email }`. Окончание вычисляет
backend по длительности типа, а не по присланной гостем длительности.

Имя и email обязательны; пробелы по краям удаляются до проверки и сохранения.
Имя — 1–100 символов, email — корректный адрес длиной до 254 символов. Владение
почтой не проверяется. Телефона и комментария в форме нет.

Выбор слота и проверка ручного начала ничего не резервируют. При создании проверка
актуальной доступности и сохранение выполняются атомарно для одного календаря,
включая конфликты разных типов событий и обязательную паузу. Настройки должны
читаться в целостном состоянии относительно их изменения. Из конкурирующих
конфликтующих запросов успешно сохраняется первый; остальные получают отказ.

Бронирование создано после успешного сохранения в БД. Подтверждение владельцем
не требуется. Гость по успешному ответу видит название, дату, начало, окончание
и часовой пояс. Имя и email дополнительно видны владельцу в списке встреч.

Повторная отправка — новая проверка доступности. После ранее сохранённой встречи
повтор возвращает «Время уже занято», а не прежнее подтверждение. Если сохранения
не было и время доступно, повтор может создать встречу. Ключ идемпотентности не вводится.

При потере ответа результат неизвестен. Интерфейс не заявляет ни успех, ни отсутствие
записи и не повторяет её автоматически. Ручной повтор допустим; последующее сообщение
о занятости само по себе не подтверждает, кому принадлежит существующее бронирование.

## Экраны, состояния и список владельца

Главная → «Записаться» → тип события → календарь/время → имя/email → подтверждение.
Это пошаговый wizard. Возврат сохраняет имя/email; смена типа сбрасывает время.
После перезагрузки страницы wizard начинается заново. При конфликте обновляются
слоты, гость возвращается к календарю с сохранёнными именем и email.

В nav bar главной есть ссылка на `/admin`. В административной части разделы
«Типы событий», «Доступность», «Предстоящие встречи». Доступ не требует входа.
Все встречи с `endsAt > asOf` выводятся по `startsAt` по возрастанию; `asOf` задают
серверные часы. Текущая встреча остаётся до окончания, при равенстве `endsAt == asOf`
уже исключается. Пагинации и скрытого ограничения количества записей нет.

Есть отдельные состояния загрузки, отсутствующих типов, отсутствия слотов на дату
или всё окно, пустого списка встреч, ошибки чтения с «Повторить», ошибок полей
и сохранения. Ошибка не подменяется пустым списком. Во время записи повторное нажатие
недоступно; введённые данные при ошибках сохраняются. Успех показывается только
после успешного ответа. Полное поведение — в [описании экранов](booking-screens.md).

Интерфейс работает от 320 px без наложений и горизонтальной прокрутки страницы,
доступен с клавиатуры, имеет видимый фокус, подписи полей и доступные сообщения
о состояниях и ошибках. Используются компоненты существующего frontend на Mantine.
Главная развивается согласно уточнениям [спецификации главной](home-page.md)
и [ADR-0012](../docs/adr/0012-application-home-page.md).

## Контракт, данные и взаимодействие слоёв

Принятый [TypeSpec](../api/main.tsp) описывает 16 HTTP-операций; все методы имеют
[описания](booking-api.md#операции). Новые операции находятся под `/api`,
существующий `GET /healthz` сохранён. В JSON не передаётся `ownerId`.

Создание типа и бронирования возвращает 201; ошибки полей — 422 с `fields`,
отсутствующий тип — 404, конфликт — 409, неверный формат запроса/пути — 400,
ошибки сервиса — 500/503. Ошибки имеют `code` и `message`; клиент опирается на код.
Неизвестные поля запросов отклоняются. Ручная проверка корректного, но недоступного
начала возвращает 200 с `available: false` и причиной; при создании доступность
повторно проверяется и может дать 409.

Публичная доступность содержит `generatedAt`, границы UTC-окна и `slots`,
не раскрывает других гостей и их бронирования, не кешируется. Административный
список содержит `asOf` и все подходящие `items` с данными гостей.

Первый пояс сохраняется отдельной атомарной инициализацией. Пока он не задан,
`SchedulingSettings.timeZone` отсутствует. Обновление паузы не принимает `timeZone`.
Недельная запись атомарно заменяет все семь дней. Настройка даты возвращается явно,
без объединения с недельными интервалами; отсутствие настройки означает наследование.

Принятая [схема](../docs/diagrams/application.excalidraw) показывает пять потоков:
типы/профиль, настройки, поиск/проверка времени, создание, список владельца.
Frontend отвечает за wizard, ввод и отображение; backend — за правила и HTTP;
БД — за хранение и генерацию UUID с требуемой атомарностью. Данные показаны логически:
выбор СУБД, физических таблиц и механизма блокировок относится к реализации.

## Проверяемые критерии приёмки

Каждая строка — ожидаемое поведение будущей реализации, а не заявление о наличии
готового приложения. Примеры времени ниже не охватывают отложенные сезонные переходы.

| ID | Условие и ожидаемый результат |
| --- | --- |
| AC-01 | Гость проходит запись без аккаунта и входа; `/admin` использует один заранее заданный профиль. |
| AC-02 | Создание типа без ID даёт UUID БД; два типа с одинаковым названием допустимы и имеют разные ID. Пустое после обрезки название отклоняется; описание можно не задавать. |
| AC-03 | 60 минут и 1 час сохраняются как 60; 2 часа — как 120. Принимаются границы 1 минуты и 23 часов; 0, дробные значения, 61 и 90 нормализованных минут отклоняются. |
| AC-04 | До настройки все семь дней заблокированы, интервалы пусты, пауза 0; свободных слотов нет. |
| AC-05 | Первая успешная инициализация сохраняет пояс браузера владельца; вызов с другим корректным поясом возвращает прежний. Обновление паузы с полем `timeZone` отклоняется. |
| AC-06 | При смещении +03:00 блокировка местного понедельника закрывает интервал от воскресенья 21:00 до понедельника 21:00 UTC. |
| AC-07 | Блокировка и разблокировка недельного дня восстанавливает его прежние интервалы. Настройка даты не открывает заблокированный день недели. |
| AC-08 | При недельных 09:00–18:00 и собственных 12:00–14:00 дата работает только 12:00–14:00. Блокировка даты удаляет её собственные интервалы; разблокировка без них возвращает 09:00–18:00. |
| AC-09 | Отсутствие `intervals` даты наследует неделю; явные `intervals: []` при открытой дате дают отсутствие рабочих часов без автоматического изменения флага. |
| AC-10 | Недельная запись требует ровно семь разных дней. Интервалы с началом не раньше окончания или пересечением отклоняются; 09:00–12:00 и 12:00–18:00 допустимы и непрерывны. |
| AC-11 | При серверной дате 2026-10-19 окно — `[2026-10-19T00:00Z, 2026-11-02T00:00Z)`, независимо от пояса гостя. |
| AC-12 | При текущем времени 10:02 и доступном интервале ручное начало 10:07 допустимо; начало не позже текущего момента отклоняется. Предложения идут по четвертям часа UTC. |
| AC-13 | Выбор слота и проверка ручного начала не создают бронирование и не резервируют время; свободный результат проверки не гарантирует успех последующего создания. |

## Границы MVP и отложенная работа

Не входят: регистрация/авторизация, аккаунты гостей, несколько владельцев, отмена
и перенос встреч, уведомления, подтверждение email, редактирование и удаление типов
событий, смена сохранённого пояса, постоянный черновик wizard между посещениями.

[Поддержка переходов на летнее и зимнее время](https://github.com/bkoshelev/go-project-386/issues/32)
выделена в отдельную отложенную задачу: сохранение местных рабочих часов при изменении
смещения, отсутствующие и повторяющиеся часы, их ввод/отображение, интервалы и блокировки
на переходах и соответствующие проверки. Она не блокирует утверждение MVP.

Реализация может использовать стандартные библиотеки часовых поясов; спецификация
не требует намеренно отключать их поведение. Однако корректность сценариев,
затрагивающих сезонный перевод, пока не является критерием приёмки MVP.
