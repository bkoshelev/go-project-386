## Ожидаемое поведение

Владелец в существующем разделе `/admin/availability` читает и сохраняет одну
общую паузу между встречами всех типов. Допустимо любое целое число от 0 до 60
минут включительно. Начальное сохранённое значение — 0. Нулевое значение
означает возможность поставить встречи вплотную.

Пауза сохраняется отдельным действием, независимо от редактирования недели
и исключений дат. Неотправленные изменения других форм не теряются и не
сохраняются этой операцией. Показывается сохранённое сервером значение;
сообщение об успехе появляется только после корректного успешного ответа.
Пояс расписания остаётся первым сохранённым IANA-поясом. Изменение паузы
не передаёт `timeZone`, не меняет и не инициализирует его.

Форма имеет видимую подпись, пояснение диапазона и действия паузы до и после
любой соседней встречи. Пустое, дробное и выходящее за диапазон значение
отклоняется с ошибкой у поля, фокусом на поле и сохранением ввода. Чтение
различает загрузку, успешное значение 0 и ошибку с ручным повтором. Для
скалярной настройки нет отдельного «пустого списка»: 0 является данными.
Сохранение блокирует повторную отправку и редактирование до результата.
Отказ и неизвестный исход сохраняют черновик; автоматического повтора нет.
Потерянный ответ не показывает успех и не объявляет запись несостоявшейся.

Гостевой календарь и атомарное создание применяют одну и ту же актуальную
паузу в прошедших минутах к занятости всех типов. Для нового интервала
`[start, end)` и существующего `[busyStart, busyEnd)` конфликт есть тогда,
когда `start < busyEnd + pause` и `end + pause > busyStart`. Равенство
граничных моментов допустимо. Пауза применяется один раз между встречами,
а не как сумма двух пауз.

При встрече 10:00–10:30 и паузе 15 новая встреча после неё начинается
не раньше 10:45; предыдущая заканчивается не позже 09:45. 10:44 и окончание
09:46 недопустимы. Те же правила действуют через местную/UTC-полночь,
между разными типами и у границ окна бронирования: соседняя запись вне
окна также влияет на промежуток внутри окна. Сама пауза не обязана
помещаться в рабочие часы; в них должна помещаться встреча.

Изменение паузы действует на новые записи. Уже созданные встречи, в том числе
оказавшиеся ближе новой паузы, не переносятся, не отменяются и продолжают
занимать свои интервалы. Ранее выбранное время повторно проверяется при
создании. Нарушение паузы возвращает `409 time_occupied`, с существующим
сценарием «Время уже занято», обновлением календаря и сохранением имени/email.

Конкурирующие новые записи, которые нарушили бы паузу друг относительно
друга, не могут обе сохраниться. Проверка и вставка сериализованы одной
блокировкой календаря с изменением настроек. Если обновление завершилось
до начала проверки записи, используется новое значение; при перекрывающихся
операциях допустим любой последовательный порядок. Новая пауза не должна
ретроспективно отклонять встречу, записанную раньше обновления.

## Конкретный объём изменений

1. Добавить самостоятельный frontend feature `manage-meeting-pause`
   с публичным компонентом, XState-моделью состояний и функциями чтения/записи
   через сгенерированный Hey API. Подключить к композиции `AvailabilityPage`.
   Оформление выбрать из пяти прототипов; доступность и сохранение одинаковы
   для всех вариантов. Использовать Mantine и текущую зелёную тему.
2. Сохранить существующий контракт `GET/PUT /api/admin/scheduling-settings`:
   запрос только `{ meetingPauseMinutes }`, ответ `SchedulingSettings`.
   Неверные значения и неизвестные поля — `422 validation_error` с JSON Pointer.
   Новые HTTP-операции и изменения TypeSpec для продуктового поведения не нужны.
3. Использовать существующие `scheduling.UpdatePause`, SQL UPDATE singleton-строки,
   `availability.Snapshot.Check` и `booking.Create` с `FOR UPDATE` той же строки.
   Хранение, расчёт и атомарность уже реализованы предыдущими задачами;
   менять их только при подтверждённом несоответствии проверкам #39.
   Новые таблицы, миграции и инфраструктурный рефакторинг не планируются.
4. Дополнить проверки поведения на согласованных публичных границах
   и краткую документацию текущей возможности. Сохранить существующие проверки.
5. После реализации выполнить review по цепочке `implement`, исправить
   подтверждённые замечания, сделать Conventional Commit в текущей ветке,
   записать реальную демонстрацию и выполнить Plannotator review.

Архитектура: feature-based композиция frontend; FSM отделяет допустимые
состояния от I/O workflow; существующие backend-срезы владеют своими правилами.
Применяются ADR-0013, ADR-0014, ADR-0017 и четыре обзора `docs/architecture/`.
Решения не требуют пересмотра этих ADR или добавления workflow engine/брокера.

## Критерии приёмки и проверка

Границы уже согласованы в #33 и #39: публичный HTTP и production UI с настоящим
backend и изолированной PostgreSQL. Внутренние сервисы и SQL отдельно не тестируются.
При реализации использовать разрешённую цепочку `tdd`: один наблюдаемый сценарий,
падающий тест, минимальная реализация, следующий сценарий. Для уже реализованных
гарантий проверки могут сразу подтвердить существующее поведение.

| Проверка | Наблюдаемый результат |
| --- | --- |
| Начало и валидация HTTP | GET возвращает 0, PUT принимает 0/15/60; пустое, null, дроби, строки, −1, 61 и неизвестные поля дают принятые ошибки; сохранённое значение после отказа прежнее. |
| Неизменяемый пояс | PUT не принимает `timeZone`; изменение паузы до и после инициализации не меняет/не инициализирует пояс, включая другой браузер. |
| Две стороны и типы | Для пауз 0/15/60 доступность и POST совпадают на точной границе и за минуту до неё с обеих сторон встречи; одинаковые и разные типы. |
| Полночь и окно | Соседние встречи по разные стороны полуночи; учитываются соседние записи за границей окна, если их пауза затрагивает новое время. |
| Актуальная пауза | Получить слот, увеличить паузу, отправить старый выбор: 409; GET слотов отражает новое значение, гостевые контакты сохранены при возврате. Уменьшение открывает допустимые новые слоты. |
| Существующие записи | Создать встречи при 0, увеличить паузу: GET списка показывает те же ID/начала/окончания/контакты, интервалы по-прежнему заняты. |
| Конкурентные записи | Два непересекающихся интервала с недостаточным промежутком: один 201, второй 409 time_occupied; в публичном списке одна новая запись. Проверить разные типы. |
| Конкурентное обновление | Перекрывающиеся PUT паузы и POST записи дают состояние, совместимое с последовательным выполнением; запись после подтверждённого PUT использует новую паузу. Наблюдать через HTTP, без SQL-проверок/локов из теста. |
| Сохранение через UI | Владелец задаёт 15, сохраняет, перезагружает страницу и видит 15; гость выбирает допустимый слот и получает реальное подтверждение. Проверяется публичный результат в списке встреч. |
| Ошибки UI | Неверный ввод сохраняется; ошибка GET имеет ручной повтор; ошибка PUT/потеря ответа сохраняет черновик без успеха и автоотправки; во время записи повтор отключён. Сетевые сбои допускаются на границе доставки при настоящем backend. |
| Независимые формы | Изменение паузы не сохраняет/не сбрасывает черновики недели и исключений, соответствующие серверные данные остаются прежними. |
| Нет времени | Пауза может убрать все подходящие слоты: явный пустой результат отличим от загрузки/ошибки; ручное обновление календаря работает. |
| Responsive и a11y | 320, 375, 768, 1440 px без наложений и горизонтальной прокрутки; клавиатура, видимый фокус, подписи, связанные ошибки и сообщения результата; для D — фокус и закрытие диалога. |
