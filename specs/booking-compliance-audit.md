# План проверки соответствия бронирования требованиям

Статус: **Готова к реализации; ожидает одобрения пользователя на старт**.
Здесь реализация означает выполнение проверки и подготовку отчёта, а не изменение
приложения. Подготовлено 17 ноября 2026 года.

## Цель и согласованные границы

Получить два доказательных списка: недостающий функционал бизнес-логики
и реализованный функционал, поведение которого противоречит требованиям.
Итог выполнения проверки — HTML-отчёт. Сам план не требует HTML-формата.

Границу задаёт список требований из пользовательского запроса. По ответу Q2
документы репозитория уточняют соответствующие правила, но не расширяют проверку
до всех функций MVP. Расписание, исключения дат, пауза и модель времени проверяются
в части их влияния на доступность и создание бронирования. Самостоятельный аудит
всех редакторов настроек, адаптивности, доступности интерфейса и архитектуры не входит.

Рабочий код, существующие тесты, контракт, CI и инструкции не исправляются.
Диагностические сценарии разрешается подготовить вне рабочего дерева и выполнить
на изолированной тестовой БД. Данные существующего демо не очищаются.
Коммиты, публикация, создание задач и запуск удалённых workflows в план не входят.

## Источники ожидаемого поведения

- Пользовательский список требований — обязательная основа матрицы покрытия.
- [Спецификация MVP](booking.md), [экраны](booking-screens.md),
  [HTTP API](booking-api.md), [TypeSpec](../api/main.tsp),

- Принятые последующие уточнения, включая [длительность](event-type-duration-90-minutes.md),
  применяются только в относящейся к проверке части. Исторический манифест не считается
  описанием неизменяемого текущего состояния файлов.
- [ADR-0013](../docs/adr/0013-go-api-generation.md),
  [ADR-0014](../docs/adr/0014-postgresql-and-sqlc.md),
  [ADR-0017](../docs/adr/0017-scheduling-feature-boundaries.md),
  [ADR-0018](../docs/adr/0018-mise-development-workflow.md) поясняют принятые границы
  генерации, атомарности и проверок, не добавляя продуктовых функций.

Для используемых требований фиксируются источник, раздел и актуальное уточнение.
Если необходима сверка с канонической GitHub-задачей, читаются её полное описание
и обсуждение с проверкой пагинации. Неоднозначность источников отмечается отдельно;
реализация не используется для выбора удобного толкования требования.

## Матрица обязательных проверок

Повторяющиеся пункты пользовательского списка объединены без потери требований.

| ID | Требование | Проверка и наблюдаемый результат |
| --- | --- | --- |
| R01 | Полный путь гостя | В браузере выбрать тип события, открыть календарь, выбрать свободный слот, ввести данные, отправить запись и увидеть подтверждение с согласованными названием и временем. Ответы API успешного сценария не подменяются. |
| R02 | Страница владельца | Через навигацию открыть список и найти созданную встречу с данными гостя. Несколько типов присутствуют в общем списке. Проверить смысл «предстоящих» по `endsAt > asOf`, сортировку и отсутствие скрытого ограничения списка. |
| R03 | Серверная защита | Отправить прямые HTTP-запросы без UI: сервер заново проверяет актуальную доступность; проверка и сохранение атомарны. После отказа лишняя запись отсутствует. |
| R04 | Общая занятость | Занятый интервал исключается из предложений для исходного и другого типа. Повторная запись, в том числе после ранее прочитанного свободного слота, получает конфликт. |
| R05 | Понятный конфликт | Два клиента выбирают свободное время; один сохраняет раньше. Второй получает понятное сообщение и возможность выбрать другое время. Сохранённые контакты не теряются; ложного успеха нет. |
| R06 | Общая команда проверок | Установить, что одна документированная в AGENTS.md команда выполняет весь требуемый набор локально и в CI, включая настоящий браузерный сценарий. Сопоставить фактическую цепочку запуска, не только названия задач. |
| R07 | Генерация контракта | TypeSpec присутствует; одна команда генерирует OpenAPI и SDK. Подходящий серверный генератор используется; результат воспроизводим и собирается. |
| R08 | Совпадение реализации и API | Сверить пути, методы, поля и обязательность, успешные ответы, ошибки данных и конфликта с TypeSpec/OpenAPI. Проверить существование и реальное выполнение API-тестов соответствующих ответов. |
| R09 | Генерация в CI и инструкции | Проверить повторную генерацию в workflows, актуальность сохраняемых серверных артефактов, запись генерируемых путей и запрета ручных изменений именно в AGENTS.md. |
| R10 | SDK во frontend | Проследить запросы сценариев от компонентов до сгенерированного SDK; выявить обходы SDK ручными запросами, если они относятся к проверяемому API. |
| R11 | Тесты и GitHub Actions | Проверить поведенческое покрытие основного пути и конфликтов; выполнить локальные проверки. Установить статус нужных jobs GitHub Actions для проверяемого коммита, сохранив ссылки и SHA. |
| R12 | Частичное наложение разной длительности | 60 минут в 10:00 и 30 минут в 10:30, разные типы: вторая запись отклоняется; проверить оба порядка создания и конкурентную отправку. Отдельно установить наличие такого теста в репозитории. |

## Порядок выполнения

1. Зафиксировать ветку, SHA, состояние рабочего дерева, версии инструментов и дату
   проверки. Сопоставить R01–R12 с конкретными требованиями, кодом и тестами.
   Статусы «реализовано» в старых документах не считать доказательством.
2. Проверить окружение по корневому README и frontend/README: mise, Docker daemon,
   инструменты, зависимости и браузер. Использовать отдельную БД и фикстуры без
   сезонного перехода часов. Для ручного демо выделить изолированные данные.
3. Прочитать реализацию по пути браузер → SDK → HTTP-адаптер → сценарий → БД.
   Особое внимание: единая занятость всех типов, полуоткрытые интервалы,
   серверное вычисление окончания, транзакция и защита конкурентной записи.
4. Выполнить `mise run check`, сохранив команду, код завершения, полный лог,
   проваленные и пропущенные проверки. При раннем отказе общей команды выполнить
   независимые необходимые проверки отдельно, чтобы получить остальное покрытие.
   Ошибку подготовки окружения отличать от дефекта приложения.
5. Выполнить матрицу бронирований ниже на реальных HTTP/БД, затем браузерный путь
   гостя, конфликт двух клиентов и проверку списка владельца. Предпочесть существующие
   production Playwright fixtures; ручное демо использовать для недостающего наблюдения.
6. Сверить TypeSpec, генерируемую схему, SDK, серверные модели и маршруты.
   Выполнить `mise run api:generate` и `mise run backend:api-generate` в отдельном
   временном checkout проверяемой ревизии; сравнить сохраняемые результаты.
   Учесть локальные изменения, если они были частью проверяемого состояния.
   Основное рабочее дерево не перегенерировать.
7. Проверить команды и workflows статически; получить существующие результаты
   GitHub Actions только для соответствующего SHA. Отсутствующий запуск, недоступный
   GitHub и зелёный запуск другого SHA не считать подтверждением R11.
8. При необходимости применить `$statechart` к небольшим моделям пути гостя
   и конкурирующих записей: TLA+/TLC, исходник Mermaid, ограничения модели и команда
   воспроизведения. Работать вне репозитория. Каждый найденный моделью путь ошибки
   повторить на настоящем коде; ошибка модели сама по себе не является дефектом продукта.
9. Воспроизвести найденные нарушения, убрать дубликаты по общей причине и собрать
   HTML-отчёт с матрицей покрытия, двумя списками бизнес-недостатков и доказательствами.

## Матрица бронирований

На каждой независимой проверке использовать новую изолированную БД либо заведомо
непересекающийся набор данных. Свободное время и длительности задаются явно;
для базовых пересечений пауза равна нулю.

- Свободный слот: успешное создание, согласованное подтверждение, одна встреча
  в списке владельца, занятое время исчезает из актуальных предложений.
- Точный повтор: тот же тип, затем другой тип с тем же началом — конфликт.
- Частичное пересечение: 10:00–11:00 и 10:30–11:00; оба порядка записи.
- Вложение и пересечение с другой стороны: новый интервал внутри существующего,
  существующий внутри нового, новая встреча начинается до занятой и заканчивается внутри.
- Касание: 10:00–11:00 и 11:00–11:30 при нулевой паузе допускаются.
  При ненулевой паузе проверить запрет недостаточного промежутка и допуск точной границы.
- Конкуренция: синхронизированные запросы одного и разных типов к одному времени,
  а также частично пересекающиеся запросы; ожидаются ровно одно создание и конфликт
  у другого клиента. Независимые непересекающиеся встречи допускаются.
- Устаревшая доступность: чтение не резервирует время; после чужой записи сервер
  повторно проверяет интервал и отказывает следующему клиенту.
- Серверные ограничения: прошлое, выход за окно UTC и рабочие часы, блокировка
  даты/дня, пауза, отсутствующий тип, некорректные контакты и попытка передать
  вычисляемое окончание. Ожидаемые статусы берутся из соответствующей операции контракта.
- Список владельца: разные типы, текущая встреча, завершённая встреча и граница
  `endsAt == asOf`; время границы проверять управляемыми часами, если это поддержано,
  иначе честно отметить предел проверки вместо нестабильного ожидания по таймеру.

## Правила доказательности и классификация

Каждое требование получает статус: «соответствует», «отсутствует», «работает неверно»
или «не проверено». Для последнего указываются причина и конкретная недостающая проверка.
Отсутствие теста не означает отсутствие функциональности. Падение линтера не означает
нарушение бизнес-правила. Отсутствие воспроизведения гонки не доказывает её невозможность:
для вывода требуется также анализ серверной атомарности.

Два основных списка содержат только подтверждённые бизнес-находки. Нарушения требований
к контракту, генерации, тестам, документации и CI выводятся отдельным списком
«Контракт и проверяемость» с привязкой к R06–R11. Связанные последствия одной причины
не размножаются в несколько независимых дефектов.

Карточка находки содержит ID, категорию, влияние/приоритет, требование и источник,
предусловия, шаги воспроизведения, ожидаемый и фактический результат, запрос/ответ
или скриншот, ссылку на код/тест и рекомендацию по устранению причины.
Для статической находки сохраняется полный относящийся к ней фрагмент документа
или конфигурации; для наблюдаемого поведения — воспроизводимый сценарий.

## Выходные артефакты и приёмка

- `artifacts/booking-compliance/index.html` — итоговый отчёт на русском языке:
  сводка, границы и SHA, два списка бизнес-недостатков, контракт и проверяемость,
  матрица R01–R12, результаты запусков, ограничения и ссылки на доказательства.
- Рядом — логи, диагностические сценарии, скриншоты и, если использовался `$statechart`,
  TLA+/config/view, вывод TLC и Mermaid. Копии артефактов не включают секреты окружения.
- Основное содержание HTML читается локально без сетевых CSS/JS; диаграммы, если есть,
  сопровождаются читаемым текстом сценариев и исходником Mermaid.
- Каждый пункт пользовательского списка покрыт матрицей; непроверенные пункты видны.
  Нет неподтверждённых дефектов, вымышленных успешных запусков и утверждений о CI
  без привязки к коммиту. Исправления приложения в результат не входят.

План готов к выполнению после подтверждения пользователем общего понимания и старта
проверки по правилу вызванного скилла `grilling`.
