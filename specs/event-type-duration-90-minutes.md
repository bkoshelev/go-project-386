# Длительность типа события: до 90 минут в режиме минут

Статус: **Реализация выполнена и проверена**.

Дата согласования требований: 16 ноября 2026 года. Пользователь подтвердил
Q1–Q4 в обсуждении `grill-with-docs`; старт реализации одобрен пользователем.

Основание: [BLA-002 в отчёте аудита](../reports/business-logic-audit/2026-11-16-d4ac7e3/incorrect-functionality.md).
Объём ограничен этой находкой с уточнением пользователя: повысить предел ввода
в минутах с 60 до 90, сохранив целочисленный ввод в часах. Это не разрешение
произвольной положительной длительности: в частности, 150 минут остаются недопустимыми.

## Ожидаемое поведение

В существующей форме создания типа события остаются одно числовое поле
«Длительность» и список «Единица длительности». Отдельные числовые поля
«Часы» и «Минуты» не добавляются.

| Единица ввода | Допустимое значение | Значение в API и БД |
| --- | --- | --- |
| Минуты | Целое число 1–90 включительно | То же число минут |
| Часы | Целое число 1–23 включительно | Число часов × 60 |

Исходная единица не сохраняется. 60 минут и 1 час равнозначны.
90-минутную встречу задают как `90` с единицей «Минуты»; ввод `1,5` часа
и составной ввод `1 час + 30 минут` не поддерживаются.

Во frontend, HTTP API и БД действует одно правило нормализованной длительности:
целые 1–90 либо 120, 180, …, 1380 минут. Например, 61 и 90 допустимы;
91, 119 и 150 недопустимы. Это расширение минутного диапазона, а не общий
максимум встречи 90 минут: целые часы до 23 сохраняются.

Некорректный ввод показывает ошибку у поля с актуальным диапазоном и сохраняет
черновик. Прямой HTTP-запрос с недопустимой длительностью возвращает существующий
`422 validation_error`, `out_of_range`, поле `/durationMinutes`.

Создание типа не зависит от расписания, занятости, паузы и наличия доступных слотов.
Тип на 90 минут можно создать до настройки расписания или при рабочих интервалах
короче 90 минут. В таком расписании подходящих слотов нет.

Доступность, проверка собственного начала и создание бронирования используют
сохранённую длительность целиком. При открытом интервале 09:00–18:00 встреча
на 90 минут с началом 09:00 заканчивается в 10:30; начало 16:30 допустимо,
16:31 не помещается в рабочее время. Остальные правила окна, блокировок,
общей занятости и паузы продолжают действовать.

## Объём изменений

1. В `frontend/src/features/manage-event-types/creation.ts` повысить минутный
   предел до 90. Существующая форма получает предел и текст ошибки из этой функции.
   Сохранить текущие FSM, сценарий сохранения и выбор единицы.
2. В `api/main.tsp` расширить минутный scalar до 90 и дать ему имя,
   соответствующее новому диапазону. Сохранить перечень целых часов в union.
   Обновить комментарии и пересоздать OpenAPI, Fetch-клиент и сохраняемый Go API.
3. Добавить следующую goose-миграцию, расширяющую CHECK длительности в `event_types`.
   Применение к существующей БД сохраняет типы и бронирования; исходную миграцию
   `00002` не переписывать. Down возвращает прежнее ограничение; при наличии
   значений 61–90 откат завершается ошибкой без удаления или изменения записей.
   Проверить актуальность sqlc-генерации.
4. Обновить проверки, которые закрепляют прежний отказ для 61/90, и добавить
   проверки новых границ и полного гостевого сценария на 90 минут.
   Причина изменения прежних ожиданий — явно согласованное изменение требований.
5. Отразить изменение правила в документации требований, включая AC-03,
   с явной ссылкой на это уточнение. Сохранить исторический отчёт аудита
   и не выдавать его исходные снимки за обновлённую реализацию.

Новые операции HTTP, изменение формата запроса, рефакторинг расчёта доступности
и изменение паузы не требуются. Применяются существующие границы из ADR-0014
и ADR-0017. Новых доменных терминов и архитектурных решений задача не вводит;
отдельные изменения глоссария и новый ADR не требуются.

## Критерии приёмки

| ID | Ожидаемый результат |
| --- | --- |
| DUR-01 | UI принимает 1, 60, 61, 89 и 90 минут. Созданные типы отображаются с точной сохранённой длительностью. |
| DUR-02 | UI сохраняет ввод 1 и 23 целых часов с результатами 60 и 1380 минут. Пустой ввод, 0, отрицательные, дробные значения и 91 минута отклоняются; 24 часа отклоняются. Ошибка показывает диапазон выбранной единицы. |
| DUR-03 | Публичный POST создания принимает 1, 60, 61, 89, 90, 120 и 1380 минут с ответом 201. Чтение созданного типа возвращает точное значение. |
| DUR-04 | POST с 0, -1, 1.5, 91, 119, 150, 1390 и 1440 минут возвращает 422 с ошибкой `/durationMinutes`; не создаёт тип. |
| DUR-05 | Тип на 90 минут создаётся при ненастроенном/закрытом расписании и при рабочих интервалах короче встречи; свободные слоты отсутствуют. |
| DUR-06 | В production UI гость выбирает созданный тип на 90 минут, доступный слот и создаёт бронирование. Подтверждение и список владельца содержат начало и окончание с разницей 90 минут. |
| DUR-07 | При открытом интервале 09:00–18:00 доступность и проверка собственного начала принимают 16:30 и отклоняют 16:31 для 90 минут. Создание повторно применяет те же правила. Проверяемая дата находится в будущем внутри окна, пауза 0, конфликтующих записей нет. |
| DUR-08 | Новая миграция работает на чистой и существующей схеме, сохраняя прежние записи. Цикл up/down/up проверен; down при сохранённых 61–90 минутах безопасно отклоняется. |

## Способ проверки

Поведенческие проверки выполняются через публичный HTTP API и Playwright
с production frontend, реальным backend и изолированной PostgreSQL.
Проверки миграции используют существующее интеграционное окружение БД.

После генерации и изменений выполнить из корня:

```sh
mise run api:check
mise run backend:sqlc-check
mise run backend:check
mise run frontend:check
mise run frontend:test-smoke
```

`backend:check` включает race-тесты без кэша; полные серверные и браузерные
проверки требуют работающий Docker. 17 ноября 2026 года после восстановления
Docker успешно выполнены все перечисленные проверки: `backend:check` прошёл
с интеграционной PostgreSQL, `frontend:test-smoke` — 118 тестов на production
сборке. В том числе проверены цикл миграции up/down/up, сохранение типа и
бронирования, безопасный отказ отката при 90 минутах, границы длительности,
создание независимо от расписания и полный гостевой сценарий на 90 минут.
