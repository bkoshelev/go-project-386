# Линтеры и форматирование frontend

Статус: спецификация по результатам интервью с учётом замечаний ревью;
реализация ещё не начата.

## Цель

Добавить воспроизводимые проверки React/TypeScript, CSS и форматирования для
`frontend/`. Разработчик запускает проверки и исправления явными командами.
Ошибки, предупреждения и расхождения форматирования приводят к неуспешной
проверке локально и в CI.

## Исходное состояние

- Приложение использует React, TypeScript, Vite и Mantine; есть отдельный CSS-файл.
- Линтеры, форматтер и команды их запуска пока не настроены.
- `pnpm build` выполняет `tsc -b` и production-сборку Vite.
- `pnpm test:smoke` собирает приложение и запускает Playwright-сценарий
  открытия и закрытия модального окна.
- Существующий frontend-workflow запускает smoke-тест на push и pull request.
- TypeScript-конфигурация охватывает `src/`, Vite и Playwright config,
  но не файлы самих Playwright-тестов.
- Закреплены Node.js 24.21.0, pnpm 12.4.2 и TypeScript 7.0.2;
  зависимости приложения присутствуют в существующем lock-файле.

## Согласованные требования

### Инструменты и конфигурация

- Добавить `oxlint`, `oxlint-tsgolint`, `oxfmt`, `stylelint` и
  `stylelint-config-standard` в devDependencies frontend.
- Выбрать последние стабильные совместимые версии на момент реализации,
  закрепить точные номера и обновить lock-файл закреплённым pnpm.
- Не обновлять существующие Node.js, pnpm, TypeScript и зависимости приложения
  в рамках этой задачи.
- Устанавливать Oxfmt как npm-пакет, чтобы использовать предусмотренное им
  форматирование HTML через Node.js.
- Разместить конфигурацию внутри `frontend/`: `.oxlintrc.jsonc`,
  `.oxfmtrc.jsonc` и `stylelint.config.mjs`.
- У каждого явно настроенного правила добавить короткий комментарий на русском:
  что оно проверяет и зачем включено. Объяснять также нестандартные параметры
  и отключения. У категорий и presets комментировать назначение набора,
  не разворачивая его в копию всех входящих правил.
- Явно записанные настройки форматирования также снабдить комментариями.

### Охват файлов и анализ типов

- Oxlint проверяет исходники, Playwright-тесты и конфигурационные JS/TS-файлы
  внутри frontend. Разделить браузерное окружение приложения и Node.js-окружение
  конфигурации и тестового runner.
- Включить анализ типов сразу в обычную lint-команду, без отдельного
  необязательного режима глубокой проверки.
- Добавить отдельный TypeScript-проект для Playwright-тестов с `noEmit`
  и ссылкой из корневого frontend-tsconfig. Анализ типов должен охватывать
  приложение, тесты и конфигурационные TS-файлы.
- Существующую проверку `tsc -b` в сборке сохранить. Oxlint не заменяет её.
- Stylelint проверяет обычные CSS-файлы frontend. Поддержку CSS-in-JS и SCSS
  в этой задаче не добавлять.
- Oxfmt форматирует JS/TS/JSX/TSX, CSS, HTML и JSON/JSONC внутри frontend,
  включая конфигурационные файлы.
- Исключить зависимости, сборку, отчёты Playwright, результаты тестов,
  coverage и сгенерированные файлы: в частности, `node_modules/`, `dist/`,
  `playwright-report/`, `test-results/`, `blob-report/` и `coverage/`.
- `pnpm-lock.yaml` исключить из форматирования; обновлять его пакетным менеджером.
- Документацию репозитория не включать в автоматические проверки.

### Правила Oxlint и Stylelint

- Включить категорию `correctness` для плагинов `typescript`, `unicorn`, `oxc`,
  `react` и `jsx-a11y`, а также базовых правил ESLint, встроенных в Oxlint.
- Явно включить `react/rules-of-hooks`, `react/exhaustive-deps`,
  `typescript/no-floating-promises` и `typescript/no-misused-promises`.
- Для `no-floating-promises` установить `ignoreVoid: false`.
  Запись `void save()` сама по себе не считается обработкой отклонения Promise.
- Проверку Promise в JSX-обработчиках не отключать. Для таких обработчиков
  использовать синхронную обёртку с обработкой ошибки асинхронной операции.
- Допустимы `await` с передачей ответственности вызывающему коду или обработка
  отклонения через `catch`. Эти правила не гарантируют обработки всех ошибок
  выполнения приложения.
- Экспериментальные правила React Compiler и массовое включение категорий
  `pedantic`, `style`, `perf` исключить.
- Для Stylelint использовать `stylelint-config-standard`.
- Любая ошибка или предупреждение делает lint-команду неуспешной;
  ознакомительного периода и накопления предупреждений нет.
- Разрешить точечные подавления конкретного правила на минимальном участке
  с объяснением причины. Объяснение проверяется на ревью; отдельный анализатор
  комментариев не создавать.
- Включить обнаружение неиспользуемых подавлений средствами инструментов.

### Форматирование

- Принять стандартный стиль Oxfmt: двойные кавычки, точки с запятой,
  два пробела, ширина строки 100, стандартные завершающие запятые.
- Оставить стандартную сортировку `package.json` включённой.
- Сортировку импортов оставить выключенной. Сохранить порядок подключения
  CSS Mantine и локальных стилей, от которого зависит каскад.
- Привести текущие frontend-файлы к выбранным правилам и форматированию;
  прикладное поведение страницы сохранить.
- Не добавлять второй форматтер или конкурирующий набор правил оформления.

### Доступность

- Включить статические проверки JSX через встроенный плагин `jsx-a11y` Oxlint.
- Документировать ограничения анализа компонентов Mantine, в том числе
  полиморфных компонентов с параметром `component`.
- Не вводить предположительные соответствия всех Mantine-компонентов HTML-тегам.
- Успешный lint не считать доказательством доступности всего интерфейса.
  Браузерный аудит через axe в эту задачу не входит.

### Команды и локальная работа

Все команды выполняются из `frontend/`.

| Команда | Поведение |
| --- | --- |
| `pnpm lint:code` | Oxlint с анализом типов и запретом предупреждений |
| `pnpm lint:css` | Stylelint с запретом предупреждений |
| `pnpm lint` | Последовательный запуск обеих проверок |
| `pnpm lint:fix` | Обычные автоисправления Oxlint и Stylelint без dangerous fixes |
| `pnpm format` | Применение Oxfmt |
| `pnpm format:check` | Проверка форматирования без записи |
| `pnpm check` | `lint`, затем `format:check`; остановка при ошибке |

- Исправления выполняются только явными командами разработчика.
- Git hooks и обязательные настройки редактора не добавлять.
- В README описать команды, исправления, политику подавлений и необязательную
  интеграцию редактора.
- Изменений публичного API приложения нет. Новый интерфейс для разработчика —
  команды в таблице. Существующие команды разработки, сборки и smoke-теста
  сохраняют своё назначение.

### GitHub Actions

- Добавить отдельную job `quality` в существующий frontend-workflow.
- Запускать её параллельно существующей job smoke-теста, без зависимости
  одной job от другой.
- Использовать закреплённые Node.js и pnpm, выполнять
  `pnpm install --frozen-lockfile`, затем `pnpm check`.
- Chromium для job `quality` не устанавливать.
- Сохранить запуск на тех же push и pull request, что и существующий workflow.
- CI только проверяет; автоисправления и коммиты из CI не нужны.
- Настройки защиты ветки GitHub в эту задачу не входят.

## Не входит в задачу

- Backend, прикладные API, новые продуктовые сценарии и изменение UI.
- ESLint или Biome как второй основной линтер.
- HTML-validate, Knip, markdownlint и автоматические проверки документации.
- Браузерный аудит доступности, экспериментальные правила React Compiler.
- Поддержка будущих фреймворков, SCSS, CSS-in-JS и универсальный monorepo-пресет.
- Git hooks, обязательные настройки редактора и защита ветки GitHub.
- Замена существующих сборки, проверки TypeScript и smoke-теста.

## Проверка результата

1. `pnpm check` проходит на исходном коде и не изменяет файлы.
2. `pnpm build` и существующий `pnpm test:smoke` проходят после изменений.

## Ревью спецификации

Спецификация учитывает замечания первого ревью: комментарии к настройкам
и сокращённый раздел проверки результата.

Для ревью сохранённого документа из корня репозитория:

```sh
plannotator annotate specs/frontend-linting.md --gate --json
```

Полученные замечания внести в документ; при содержательных изменениях повторить
ревью. Сохранение спецификации и ADR не означает начала реализации линтеров.
