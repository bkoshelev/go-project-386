# Issue #42: неизвестный исход бронирования

Статус: **Реализация одобрена пользователем и выполнена; итоговое ревью пройдено**.

## Источники и границы

[Задача #42](https://github.com/bkoshelev/go-project-386/issues/42), [родительская #33](https://github.com/bkoshelev/go-project-386/issues/33), [утверждённая ревизия 1 #31](https://github.com/bkoshelev/go-project-386/issues/31), особенно AC-22, AC-23, AC-25 и AC-29. Основа — текущий wizard и контракт TypeSpec. Пользователь отдельно одобрил реализацию указанного объёма.

## Текущее состояние и пробелы

`bookingMachine` уже различает отправку, неизвестный исход, отказ, конфликт и подтверждение; во время `saving` событие `save` не обрабатывается, форма отключена. Сетевой сбой переходит в `unknown`, имя и email остаются в контексте; автоматического повтора нет. На шаге контактов уже есть сообщение и кнопки «Забронировать» и «Назад к времени». При конфликте показывается общая занятость, открывается обновлённый календарь; контакты сохраняются. Подтверждение требует корректного полученного ответа 201.

Сообщение о неизвестном исходе сообщает о возможном сохранении, но не объясняет явно доступные ручные действия и смысл возможной занятости. Существующий Playwright уже прерывает доставку после реального ответа 201 и проверяет одну запись и сообщение о занятости при повторе. Он не проверяет полный путь выбора другого времени с контактами именно после потери ответа, не считает все POST после снятия маршрута и не проверяет код ответа конфликта в этом сценарии. HTTP-тест проверяет успешную запись после отклонённых запросов, но браузерный сценарий потери до сохранения с успешным ручным повтором отсутствует. Эти выводы основаны на чтении кода, а не на запуске тестов.

## Предлагаемое изменение

- Уточнить текст существующего сообщения об неизвестном результате: встреча могла сохраниться или не сохраниться; можно вручную повторить отправку существующей кнопкой либо вернуться к выбору времени; занятость при повторе не устанавливает принадлежность записи. Сохранить существующие элементы формы, кнопки и шаги; новая страница или элемент управления не нужны, поэтому пять HTML-прототипов не требуются.
- Проверить и при подтверждённом несоответствии исправить текущие переходы автомата и workflow в пределах сценария; обновить понятные описания состояний, событий, контекста и экспортируемых workflows при их изменении. Backend и контракт менять только при обнаружении конкретного несоответствия требованиям.
- Расширить поведенческие Playwright и публичные HTTP-проверки на существующей production-сборке с реальным backend и изолированной БД, используя сетевую границу только для управляемой потери доставки/первой попытки. Не подменять успешное сохранение бизнес-API.

## Критерии приёмки

1. Потеря ответа после отправки показывает неизвестный результат без утверждения успеха или гарантированного отсутствия записи; имя и email сохранены, автоматических POST нет. Ручные действия понятны и доступны с клавиатуры.
2. Если сервер действительно сохранил запись, потерянная доставка не показывает подтверждения; публичное чтение показывает ровно одну запись. Ручной повтор получает HTTP 409 `time_occupied`, UI не утверждает принадлежность занятого времени гостю, показывает обновлённый календарь и позволяет выбрать другое время с прежними контактами.
3. Если первая попытка не сохранена, результат остаётся неизвестным; при свободном времени ручной повтор создаёт ровно одну встречу и показывает подтверждение только после полученного успешного ответа. Повтор является новой попыткой, а не воспроизведением прошлого ответа по ключу идемпотентности.
4. На протяжении любой отправки повторная отправка и редактирование формы недоступны, двойное нажатие не создаёт дополнительные POST. Ошибки сервиса сохраняют ввод и не запускают автоматическую запись.
5. Для затронутых чтений различимы загрузка, пустой результат и ошибка, предусмотрен ручной повтор. При ширине 320 px нет наложения и горизонтальной прокрутки страницы; доступны клавиатура, видимый фокус, подписи и сообщения.
6. Генерация TypeSpec → OpenAPI → клиент и независимая от БД liveness сохраняются.

## Ограничения

Не вводить автоматический retry, API идемпотентности, поиск своей встречи, авторизацию, отмену, новые продуктовые функции или тестовые публичные endpoints. Сезонный перевод часов #32 и ретроспективные #104/#105/#107 вне объёма. Повторный конфликт доказывает только занятость, а не принадлежность встречи.

## Проверка

Playwright: доставить реальный POST backend, дождаться 201 и оборвать доставку браузеру; через публичный список проверить одну запись, вручную повторить и наблюдать 409/`time_occupied`, подсчитать все POST, выбрать другое время и проверить контакты. Отдельно оборвать первую попытку до сохранения, убедиться через HTTP в отсутствии записи, вручную повторить и проверить 201, подтверждение и одну запись. Проверить отправку, двойное нажатие, ошибку сервиса, чтения, фокус, клавиатуру и 320 px. SQL и приватные сервисы отдельно не тестируются.

В ходе реализации: `mise run frontend:typecheck`, точечный Playwright после production-сборки, затем необходимые `mise run api:check`, `mise run api:generate`, `mise run frontend:check`, `mise run frontend:build`, `mise run frontend:test-smoke` и `mise run backend:test` в доступном окружении. После реализации — code review, локальный Conventional Commit, видео реального сценария и `plannotator review` на diff от исходного base с ожиданием результата.
