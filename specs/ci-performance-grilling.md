# Ускорение CI по подходу Sphericon

Статус: **В реализации; приёмка CI и замеры не завершены**.

Интервью `$grill-with-docs` начато 18 ноября 2026 года. Документ фиксирует
согласованные решения по девяти предложениям на основе Sphericon.
Согласование решений не является одобрением начала реализации.

## Итог по девяти пунктам

| Пункт | Решение |
| --- | --- |
| 1. Разделение CI | Четыре независимых группы `lint`, `checks`, `test`, `test-frontend` и агрегатор `check` |
| 2. Backend | Lint отдельно от vet/обычных тестов/build; race и govulncheck в nightly |
| 3. Mise | Общий источник команд; локальный `check` означает статические проверки, тесты и генерация запускаются отдельными задачами |
| 4. Генерация | Проверка свежести в `checks`; другие job используют собственные checkout и необходимые локальные генерации |
| 5. Итоговый статус | Успех только при успехе всех обязательных групп; защита ветки отдельно |
| 6. Concurrency | Устаревшие PR отменяются; выполняющиеся main/nightly не отменяются новым запуском |
| 7. Go cache | Условный эксперимент после разделения job; принятие при выигрыше медианы полного CI не менее 10% |
| 8. Playwright shards | Условный эксперимент с двумя runner при критической браузерной ветке; тот же порог выигрыша 10% |
| 9. Диагностика | Артефакты ошибок и краткие отчёты на 7 дней; отдельного workflow для метрик нет |

Для PR и push в main состав одинаков. Nightly включает три независимых job:
govulncheck, весь набор Go-тестов с race и production container smoke.
Расписание — ежедневно `17 2 * * *` (05:17 МСК), также доступен ручной запуск.

Цель дневного CI — медиана пяти заранее назначенных успешных запусков не более
216,7 с. Кэш и шардирование сравниваются последовательно с последним принятым
вариантом; неудачные кандидаты не остаются в конфигурации. Если цель не достигнута,
сохраняется последний принятый вариант и фиксируется невыполнение критерия;
дальнейшие изменения автоматически не предпринимаются.

## Объём реализации

Изменить состав workflow и граф/команды mise в пределах описанной схемы.
Обычные Go-тесты выполняются с `-count=1`; ночная race-задача запускает тот же
полный набор с `-race -count=1`. Кэширование результатов Go-тестов не используется
как способ ускорить интеграционные проверки. Существующие тестовые сценарии
и изоляция их окружения сохраняются.

Обновить README, AGENTS.md, документацию workflow и запуска production smoke
с учётом новых команд и дневного/ночного состава. Явно отразить пересмотр
ADR-0010 (govulncheck ночью), ADR-0011 (группировка frontend quality с lint),
ADR-0018 (уточнение смысла check) и прежних спецификаций единого job и измерения
времени. Исторические замеры и причины решений сохраняются. Нового ADR для
обратимой схемы job не требуется.

Использовать существующие инструменты, браузерное окружение и версии.
Изменения бизнес-логики, API-контракта, тестовых сценариев, подключение новых
анализаторов Sphericon и настройка branch protection в этот объём не входят.
Отдельные назначения hexlet-check, PR title и release-please сохраняются.

## Критерии приёмки и проверка

1. Workflow PR/main реализует четыре группы из Q12 и единый агрегатор Q14.
   Ни одна текущая дневная проверка не потеряна, кроме явно перенесённых Q4–Q6.
   Сбой одной независимой группы не препятствует результатам остальных;
   failure/cancelled/skipped не подменяется общим успехом.
2. Nightly имеет три независимых job выбранного состава, расписание и ручной
   запуск. Ошибки видны в Actions и диагностике; отдельная автоматизация Issues
   и блокирования PR отсутствует согласно Q15.
3. Локальные команды и job используют одни определения mise. Проверены
   самостоятельный запуск генерации, статических проверок и каждого вида тестов.
   Проверки Go читают committed-файлы; проверка актуальности генерации независима.
   Нет общей записи файлов между job, а внутри одного графа общие генерации
   выполняются один раз. Удалённые ранее workflow:test/scripts/tests не возвращаются.
4. В изолированной проверке ошибки генерации/линтера/тестов отражаются в статусе;
   зависимые шаги внутри job не читают незавершённый результат. Проверены правила
   отмены PR и успешное завершение текущих main/nightly при новом запуске.
5. Выполнены соответствующие статические, обычные Go-, browser-, race-,
   vulnerability- и container-проверки, валидация workflow и whitespace.
   Результаты ночных задач подтверждаются фактическим ручным или плановым запуском.
6. До каждой серии зафиксированы вариант, исходники, событие запуска, runner,
   состояние кэша и пять плановых запусков. Для каждого сохранены SHA,
   run_id/run_attempt, URL, выводы job, timestamps, время и итоговый статус.
   Используются новые запуски с первой попыткой; rerun не заменяет плановый замер.
   Неуспех любого из пяти не подменяется удобным повтором и означает отсутствие
   подтверждения приёмки серии. Экспериментальные данные сохраняются в specs/evidence.
7. Базовый дневной вариант проверен по Q16. Ускорение от переноса состава
   отделено в отчёте от ускорения одинакового набора. Для кэша и shard рассчитаны
   `gain = 1 - median(candidate) / median(last_accepted)` и решение по порогу 10%.
   Холодный кэш проверен отдельно; все тесты реально выполняются.
8. При принятии двух shard объединённый набор test IDs соответствует исходному
   полному набору, без потерь и лишних повторений сверх существующих retries.
   Каждый shard использует собственные БД/контейнеры/порты/результаты.
   Успех агрегатора требует успеха всех shard и объединения отчётов.
9. Логи ошибок и небольшие отчёты сохраняются на 7 дней. Отсутствующие из-за
   отмены/раннего сбоя данные явно помечены как недоступные, не как успех или ноль.
   Отчёт работающего job не приписывает себе будущее время завершения.
   Окончательная метрика времени эксперимента получена после окончания check
   из `check.completed_at - workflow.created_at` по GitHub REST API.
10. При недостаточном результате соблюдена граница Q22: последний принятый
    вариант, фактический отчёт, без расширения объёма и ослабления критерия.
    Одного зелёного workflow недостаточно, чтобы объявить цель скорости достигнутой.

## Исходные данные и прежние ограничения

- Текущий workflow `check.yml` запускает один job с `mise run check`.
- [Граф mise](mise-check-task-graph.md) реализован; сохранённый замер — 332 с
  против ранее согласованного порога 216,7 с. Базовое среднее — 197,0 с.
- [Предыдущая спецификация](unified-check-d01.md) требовала отдельно согласовать
  изменение схемы при превышении порога. Настоящее интервью обсуждает это изменение.
- ADR-0010 предписывает обязательный govulncheck на push/PR и отдельный job;
  ADR-0011 описывает отдельный frontend quality job. Текущий общий job расходится
  с этими формулировками. Изменение политики требует явного решения и согласования
  документации; сам факт обсуждения не отменяет прежних требований.
- Mise уже служит общим интерфейсом команд согласно ADR-0018.
- Диагностика ошибок и timings mise уже включены; явный кэш Go и шардирование
  Playwright отсутствуют. Отмена устаревших PR-запусков пока не настроена.

## Согласованные решения

### Q1. Приоритет

Главная цель — сократить время ожидания результата всех обязательных проверок PR.
Рост суммарного потребления runner-минут допустим. Границы измерения,
численный критерий и метод сравнения определены Q16 и Q20–Q21.

### Q2. Перенос в nightly

Пользователь допускает обсуждение переноса части проверок на ночной запуск.
Конкретный состав выбран в Q4–Q6 ниже. Изменение workflow ещё не реализовано.

### Q3. Условия кэширования и шардирования

Обсуждаются все девять пунктов. Кэширование и шардирование включаются в реализацию
только при подтверждённой пользе замерами. Метод эксперимента и достаточный выигрыш
определены Q16–Q18 и Q20–Q21.

### Q4. Проверка уязвимостей

`govulncheck` выполняется только в nightly и по ручному запуску, без обязательного
запуска на каждом PR. Это пересматривает требование ADR-0010 о govulncheck
на push/PR. Перед внедрением потребуется согласовать документацию с этим решением.

### Q5. Go race detector

На PR выполняются обычные Go-тесты; полный набор с `-race` переносится в nightly.
Сокращение самих наборов тестов этим решением не предусмотрено.

### Q6. Контейнерный smoke

Сборка production-образа и контейнерный smoke выполняются только в nightly
и по ручному запуску, без фильтрации PR по изменённым файлам.

Пользователь выбрал отложенное обнаружение уязвимостей, гонок данных и проблем
production-образа до ночного либо ручного запуска. Расписание, реакция на сбои
и политика дневного push в main раскрываются ниже. При сравнении времени
нужно отличать сокращение состава PR от ускорения выполнения одинакового состава.

### Q7. Дневной push в main

На PR и push в main выполняется одинаковый сокращённый набор проверок.
Govulncheck, race и контейнерный smoke остаются ночными и ручными.

### Q8. Схема job по аналогии с Sphericon

Пользователь выбрал аналогию с Sphericon вместо ранее предложенных пяти групп.
Линтеры frontend и backend объединяются в `lint`; проверки актуальности генерации
выделяются в `checks`; Go-тесты и frontend/browser запускаются отдельными job.
В конце общий job агрегирует результаты. Архитектурные анализаторы и другие
отсутствующие в нашем проекте проверки Sphericon этим решением не добавляются.
Шардирование остаётся условным согласно Q3. Точное распределение существующих
проверок и границы генерации определены Q12.

### Q9. Локальные команды по аналогии с Sphericon

`mise run check` становится интерфейсом статических проверок, не агрегатором
всех тестов и ночных задач. Тесты, проверки генерации, race, govulncheck
и контейнерный smoke доступны отдельными mise-задачами, которые вызывает CI.
Команды проверок определяются в mise, без дублирования внутри workflow.
Это пересматривает прежнее требование полного набора одной командой `check`.

### Q10. Независимые ошибки по аналогии с Sphericon

Ошибка независимого CI job не отменяет остальные job; агрегирующий job
учитывает результаты всех обязательных групп. Для возможных матриц
используется `fail-fast: false`. Внутри отдельной mise-задачи сохраняется обычная
остановка при ошибке; продолжение шагов после ошибки их зависимости не требуется.

### Q11. Расписание по аналогии с Sphericon

Nightly запускается ежедневно в 02:17 UTC (05:17 МСК) на main, по cron
`17 2 * * *`, и поддерживает ручной запуск. Перенесённые три группы проверок
выполняются отдельными независимыми job. Плановое время не гарантирует точного
времени старта в GitHub Actions.

### Q12. Распределение проверок и независимая генерация

Применяется схема Sphericon к существующему набору проверок проекта:

| Job | Проверки |
| --- | --- |
| `lint` | TypeSpec; frontend lint, format и typecheck; backend lint |
| `checks` | Свежесть сохраняемых в Git Go API-файлов и кода sqlc |
| `test` | Go vet, обычные Go-тесты и build |
| `test-frontend` | Production-сборка frontend и весь текущий Playwright-набор |

У каждого job собственный checkout. Backend lint и тесты читают сохраняемые
Go-файлы из коммита, а `checks` независимо подтверждает их соответствие генераторам.
Frontend генерирует необходимые игнорируемые Git SDK/OpenAPI в своём checkout.
Job не зависят от артефактов генерации соседних job. Повторение необходимой
подготовки между runner допускается; в пределах одного запуска mise общие
зависимости не дублируются. Ночная сборка контейнера использует исходники коммита
и собственную изолированную генерацию внутри Docker-сборки.

### Q13. Concurrency

Применяется политика Sphericon: новый запуск PR отменяет устаревший запуск
того же PR; разные PR не отменяют друг друга. Для main и nightly отключена
отмена выполняющегося запуска при поступлении нового. Это не гарантия исполнения
каждого промежуточного коммита main: стандартная concurrency GitHub может заменять
ожидающий запуск более новым. Разные workflow имеют разные группы concurrency.

### Q14. Итоговый статус

Как в Sphericon, агрегатор выполняется с `always()` и проверяет результаты
всех четырёх обязательных групп. Успех допустим только при `success` каждой группы;
`failure`, `cancelled` и неожиданный `skipped` не дают зелёного статуса.
Применение политики workflow-level cancellation к устаревшему PR допускает отмену
его агрегатора; такой запуск не должен сообщать об успехе.

Стабильное имя итогового статуса в нашем проекте — `check`. Настройка защиты
ветки остаётся за пределами изменений файлов CI: схема Sphericon заимствуется
как единый агрегатор обязательных результатов, без автоматической смены ruleset.

### Q15. Ошибки nightly

Используется подход Sphericon: красный workflow, штатные уведомления GitHub Actions
согласно пользовательским настройкам и диагностические артефакты для ручного
разбора. Автоматическое создание Issues и блокирование дневных PR по результатам
nightly не добавляются. Ночной сбой не считается успешно пройденной проверкой.

### Q16. Критерий скорости и выборка

Сохраняется абсолютная цель 216,7 с, но вместо прежнего единственного запуска
используется медиана пяти заранее запланированных запусков. Начало измерения —
создание workflow, конец — завершение итогового job `check`; учитываются очередь,
подготовка, проверки и загрузка артефактов. Для приёмки все пять запусков должны
быть успешными; неудобные результаты не исключаются и не подменяются повторами.

Это новый протокол вместо одноразового замера предыдущих спецификаций.
Историческая база 197,0 с и результат 332 с сохраняются как факты старого состава;
их нельзя выдавать за сравнение одинаковых наборов после переноса задач в nightly.

### Q17. Условное Go-кэширование

После разделения job сравнивается та же дневная схема с явным кэшем и без него.
Кандидат — кэш модулей и сборки с разделением сборки по группам job; политика
по аналогии с Sphericon: PR восстанавливает, main сохраняет.
Внедрение допускается при снижении медианы полного дневного CI не менее чем
на 10%. Попадания в кэш и холодный старт измеряются отдельно; кэш не принимается
только на основании ускорения отдельного шага. Выборки подчиняются Q16.

### Q18. Условное шардирование Playwright

Эксперимент с двумя runner проводится, если браузерная ветка остаётся критическим
путём после разделения job. Оставить шардирование можно при уменьшении медианы
всего дневного CI минимум на 10%, включая повторную подготовку приложения и БД,
объединение результатов и итоговый статус. Выборки подчиняются Q16.
Первоначально обсуждался следующий эксперимент с тремя частями; окончательное
решение Q22 исключило его из объёма. Полнота набора тестов и изоляция
не должны ухудшаться.

### Q19. Диагностика и краткие метрики

Имеющиеся логи и Playwright-артефакты сохраняются при ошибке в соответствующих job
на 7 дней. Для запусков сохраняется небольшой отчёт доступных времён job,
доступных cache hit/miss и retries также на 7 дней. Тяжёлые успешные трассы
постоянно не сохраняются. С учётом Q23 автоматический отчёт ограничен завершёнными
job и наблюдениями на момент его формирования; точное общее время эксперимента
собирается отдельно после завершения run. Неизвестные данные не подменяются оценкой.
Задержка до старта не выдаётся за чистое ожидание runner.

### Q20. Последовательность экспериментов

Сначала четыре группы job и nightly, затем пять замеров базового варианта.
После этого эксперимент с Go-кэшем и пять сопоставимых замеров. Если браузерная
ветка остаётся критическим путём, следующим проводится эксперимент с двумя
Playwright shard и пять замеров. Каждый кандидат сравнивается с последним
принятым вариантом при неизменных исходниках приложения и наборе тестов.
Кандидат, не давший требуемого выигрыша, исключается из итоговой конфигурации.

### Q21. Холодный кэш

Работоспособность при отсутствии кэша обязательна; стоимость холодного старта
измеряется и публикуется отдельно. Требование выигрыша 10% применяется
к прогретой выборке. Холодный результат не подменяется прогретым и не смешивается
с прогретой выборкой. Отдельного порога 216,7 с для холодного эксперимента
пользователь не выбрал.

### Q22. Граница изменений при недостаточном результате

Ответ пользователя: «ничего не меняем». После согласованных экспериментов
сохраняется последний принятый вариант по Q20. Если цель 216,7 с не достигнута,
результат фиксируется как не достигший критерия скорости; порог не пересматривается.
Дальнейшие изменения автоматически не предпринимаются: ни ослабление проверок,
ни три shard, ни платные runner, ни дополнительная оптимизация.
Эта граница уточняет Q18: три shard не входят в согласованный объём экспериментов.

### Q23. Граница отчёта по аналогии с Sphericon

Пользователь выбрал «по аналогии с Sphericon». В изученной конфигурации Sphericon
нет отдельного post-completion workflow для метрик. В нашем проекте также
не добавляется отдельный workflow-сборщик: используются штатные журналы GitHub
Actions и небольшие отчёты существующего CI; точное окончательное время
для экспериментов получается через API после завершения `check`.

Это уточняет Q19: автоматический отчёт не обещает собственного будущего
completed_at и полного итогового времени каждого запуска. Отдельного расширения
полномочий workflow для post-completion сбора не требуется. Итоговая интерпретация
включена в документ для подтверждения общего понимания пользователем.

## Факты для окончательной спецификации

- Обычные Go-тесты сохраняют `-count=1`, который уже используется проектом.
  Кэш компиляции не подменяет выполнение тестов прошлым успешным результатом.
  В Sphericon в CI аналогичное отключение result cache обеспечивается `-shuffle=on`.
- Текущие Playwright fixtures изолируют контейнеры/БД/порты; два runner
  не требуют изменений бизнес-логики или тестовых сценариев. На закреплённом mise
  безопасным dry-run подтверждена передача `--shard=1/2` в `frontend:test`.
- Полное время: `check.completed_at - workflow.created_at`, полученное из GitHub
  REST API после завершения агрегатора. `workflow.updated_at` не заменяет время
  окончания job. Для экспериментов фиксируются `run_id`, `run_attempt` и SHA;
  повторная попытка не подменяет заранее назначенный запуск.
- `job.started_at - job.created_at` означает задержку от создания до старта,
  которая для зависимых job может включать ожидание `needs`. Чистое ожидание
  runner этими полями не доказывается. Недоступная метрика обозначается неизвестной.
- Работающий агрегатор не может знать собственное будущее `completed_at`.
  Граница автоматического отчёта выбрана в Q23: отчёт завершённых job
  с отдельным вычислением общего времени для экспериментов.
