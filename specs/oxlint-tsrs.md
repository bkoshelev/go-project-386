# Объединённая проверка frontend через Oxlint и tsrs

Статус: **Реализована и проверена**.

Решения интервью согласованы 18 ноября 2026 года. Согласование требований
не является разрешением менять рабочую конфигурацию.

## Цель и принятые решения

Использовать Oxlint с backend tsrs для линтинга и проверки типов в одном запуске,
заменив отдельный `tsc -b`. Включить `options.typeCheck: true` в общей
`frontend/.oxlintrc.jsonc`; это эквивалент CLI-флага `--type-check`.
Существующий `options.typeAware: true` сохраняется.

Пользователь выбрал замену `tsc -b`, рассмотрев вариант его сохранения.
Основание — локальные измерения и контролируемые проверки ошибок типов.
Это пересматривает требование сохранять `tsc -b` в
[ADR-0010](../docs/adr/0010-frontend-typed-linting.md) и
[спецификации линтинга](frontend-linting.md), но сохраняет политику проверки Promise.

## Зависимости и конфигурация

- Обновить Oxlint с `1.83.0` до проверенной версии `1.94.0`.
- Добавить `tsrs` версии `0.25.0-ts7.1.0-beta` вместо `oxlint-tsgolint`.
  Пользователь выбирает этот backend с учётом его экспериментального статуса.
- Закрепить точные версии в `frontend/package.json` и обновить lock-файл
  пакетным менеджером проекта: pnpm `12.4.2`.
- Включить проверку типов в общей конфигурации с поясняющим комментарием.
  Она применяется к обычному линтингу и явно вызываемым исправлениям.
- Сохранить категории, плагины, правила и их параметры, уровни строгости,
  исключения React Compiler, окружения, overrides и ignorePatterns.
  Проверить эффективный набор правил при обновлении Oxlint.
- Сохранить `strict`, `skipLibCheck`, `noEmit` и состав трёх TypeScript-проектов.
  Не ослаблять проверку ради прохождения нового инструмента.
- Остальные зависимости и продуктовый код не входят в изменение.

## Команды и документация

Единственным источником команд остаётся mise согласно
[ADR-0018](../docs/adr/0018-mise-development-workflow.md).

- `frontend:lint-code` выполняет `pnpm exec oxlint .` с анализом типов
  и диагностикой компилятора из общей конфигурации.
- Удалить задачу `frontend:typecheck`. Для быстрого цикла после генерации API
  использовать существующую `frontend:lint-code`; совместимый alias не нужен.
- `frontend:build` последовательно генерирует API-клиент, запускает
  `frontend:lint-code`, затем Vite. Ошибка линтинга или типов останавливает сборку.
- `frontend:check`, `frontend:test-smoke`, CI и Docker используют общие задачи.
  Не добавлять параллельных определений команд в package scripts или workflows.
- Обновить корневой и frontend README: команды, подготовку API-клиента,
  замену `tsc`, поведение сборки и конфигурацию проверки типов.
  Быстрый запуск использует уже сгенерированный клиент; после изменения контракта
  клиент нужно сгенерировать заново.
- Отразить пересмотр в ADR-0010 и спецификации frontend-linting с указанием
  нового решения и ссылки на этот документ. Новых доменных терминов нет;
  `GLOSSARY.md` не изменяется.

## Охват и условия приёмки

1. Замороженная установка frontend-зависимостей проходит; `oxlint-tsgolint`
   больше не является зависимостью. Oxlint действительно запускает tsrs.
2. На текущем коде линтинг и проверка типов проходят без ослабления правил.
   Временные контрольные примеры подтверждают ошибку завершения для неверного
   типа в приложении, конфигурации Vite, Playwright-тесте и сгенерированном
   API-клиенте. Ошибки использования типов клиента также обнаруживаются.
3. Сохраняется обнаружение необработанных Promise, включая `void promise`
   и Promise в синхронном JSX-обработчике. Проверяется обнаружение
   неиспользуемых подавлений.
4. Проверочный запуск не изменяет исходники; temporary fixtures удаляются
   до обычных проверок. Сгенерированные файлы в реализации вручную не меняются.
   Для контрольных ошибок используется только изолированная копия проекта.
5. В активных задачах нет `tsc -b` и отдельного повторного анализа типов
   перед объединённым Oxlint. Быстрый запуск, сборка, CI и Docker используют
   согласованные точки входа.
6. Проходят `mise run frontend:check`, `mise run frontend:build` и полный
   `mise run check`, включая браузерные тесты. Сценарии запуска задач
   проверяются через `mise run workflow:test`, если изменяется их поведение.

Если установленная версия теряет обязательный охват или меняет диагностики,
исследовать причину до завершения перехода. Изменение правил, исключений
или границ согласованного решения требует отдельного согласования.

## Данные эксперимента

Эксперименты 17 ноября выполнены в изолированной копии на macOS x86-64.
Медианы трёх прогретых запусков; RSS — опрашиваемая сумма дерева процессов.

| Проверка | Время | Пиковая RSS |
| --- | --- | --- |
| `tsc -b` + Oxlint/tsgolint | 3,040 с | 634 МиБ |
| Oxlint/tsrs с `--type-check` | 0,662 с | 251 МиБ |

В обоих случаях на текущем коде диагностик не было. Контрольные ошибки
в исходниках, конфигурации Vite, тестах и исключённом из линтинга
сгенерированном файле обнаружили оба инструмента. Экспериментальная конфигурация
прошла полный набор проверок с 121 тестом Playwright; в том прогоне отдельный
`tsc -b` ещё сохранялся. Полная валидация после его удаления обязательна.
Измерения не гарантируют аналогичного ускорения CI или полной совместимости
с будущими версиями TypeScript и tsrs.

Источник предложения: [Faster type-aware linting with tsrs](https://oxc.rs/blog/2026-11-17-faster-type-aware-linting-with-tsrs),
текст статьи предоставлен пользователем в обсуждении.
