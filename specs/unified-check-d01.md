# Единая параллельная команда проверок — D01

Обновление 18 ноября 2026: схема единого job и протокол измерения пересмотрены в [спецификации CI](ci-performance-grilling.md); исторические данные ниже сохранены.

Статус: **Готова к реализации; ожидает одобрения пользователя на старт**.

Документ фиксирует решения интервью `$grill-with-docs` от 18 ноября 2026 года.
Согласование требований не является разрешением изменять рабочий код.

## Проблема и цель

В [аудите D01](../artifacts/booking-compliance/index.html#D01) установлено, что
`mise run check` не включает проверку свежести Go API, контейнерный smoke
и тесты команд окружения. CI выполняет отдельный набор команд.

Единая команда `mise run check` должна выполнять весь согласованный набор
локально и в одном CI job. Независимые проверки выполняются параллельно внутри
команды. Сокращение числа CI jobs допустимо только при выполнении критерия времени.

## Состав и поведение

Обязательный состав:

1. Генерация Go API и проверка свежести сохраняемых Go-файлов.
2. Текущий `backend:check`: lint, свежесть sqlc, vet, все тесты с race,
   сборка и govulncheck.
3. Текущий `frontend:check`: проверка TypeSpec, генерация SDK, линтеры
   и проверка форматирования.
4. Текущий `frontend:test-smoke`: проверка TypeScript, production-сборка
   и весь существующий браузерный набор с настоящими backend и PostgreSQL.
5. `container:test`: сборка и smoke production-образа.
6. `workflow:test`: тесты команд окружения разработки.

`check` возвращает 0 только при успехе всех обязательных проверок.
Ошибка одной ветки не отменяет остальные независимые проверки: команда дожидается
их результатов и возвращает ненулевой код. Ошибка обязательного предварительного
шага не разрешает запускать зависящие от его успешного результата шаги.
Причина пропуска зависимой проверки должна быть понятна по журналу.

## Генерация и параллельность

По явному выбору пользователя применяется вариант B: Go API генерируется
непосредственно в рабочем дереве, после чего выполняется
`git diff --exit-code -- backend/internal/api/models.gen.go backend/internal/api/server.gen.go`.
Это сравнение с индексом Git, а не с исходным содержимым рабочего дерева.
Генерация может изменить файлы. Незакоммиченные изменения относительно индекса
в этих файлах могут завершить проверку ошибкой даже при соответствии контракту.

Go-проверки и сборка контейнера начинают чтение исходников после окончания
генерации Go API. Ошибка сравнения после успешной генерации сохраняется в общем
результате; она сама по себе не мешает проверить успешно сгенерированный код.

Устранить повторную генерацию в общем графе задач. Сейчас `backend:api-generate`
и `api:generate` обе вызывают `api:build`, чтобы работать самостоятельно;
frontend quality и build также повторно вызывают генерацию SDK.
В рамках одного `check` компиляция TypeSpec с выпуском OpenAPI в рабочее дерево
должна выполняться ровно один раз. Генерация Go и SDK зависит от этого общего
шага и может выполняться параллельно, поскольку записывает разные файлы.
Каждый из этих генераторов также выполняется один раз за запуск `check`.

Самостоятельные команды генерации, проверки и сборки сохраняют необходимые
зависимости и используют тот же граф задач. Повторные обращения к общей зависимости
в рамках одного запуска не должны повторять её выполнение. Нельзя устранять
дублирование лишь последовательным запуском повторных генераций: порядок
устраняет риск гонки, но сохраняет лишнюю работу. Фактическое однократное выполнение
нужно проверить на закреплённой версии mise с выбранным способом координации.
Это требование относится к генерации в рабочем дереве; production-образ собирает
контракт и клиент внутри изолированной Docker-сборки из собственных исходников.

Не допускать одновременной записи в одни и те же файлы и чтения незавершённого
результата генерации. После успешной генерации Go могут начинаться Go-проверки
и сборка контейнера; после успешной генерации SDK — зависящие от него проверки
frontend, затем production-сборка и браузерный набор. Независимые проверки
запускаются параллельно с соблюдением этих зависимостей.

В mise 2026.10.17 экспериментально обнаружено: `mise run --continue-on-error`
может запускать задачу после ошибки её зависимости. Нельзя полагаться только
на граф `depends` вместе с этим флагом для защиты зависимых шагов.
Использовать простейшую явную координацию, обеспечивающую указанные гарантии.

Основной Playwright пишет результаты в `frontend/test-results/`, контейнерный —
в `artifacts/container-smoke/browser/`. Контейнеры, БД и HTTP-порты тестов
изолируются существующими fixtures. Эти два набора допускается выполнять
параллельно; конкуренция за ресурсы оценивается фактическим запуском CI.

## CI и границы изменений

- Заменить дублирующий состав `backend`, `frontend` и `container` workflow
  одним workflow/job, вызывающим полную команду `mise run check`.
- Сохранить запуск проверок для `pull_request` и `push` в `main`.
- Подготовить инструменты, зависимости, Docker и браузер перед `check`;
  сохранить необходимые диагностические журналы и артефакты ошибок.
- Обновить AGENTS.md, README и документацию workflow в части состава,
  требований окружения и поведения общей команды. Сохранить посторонние изменения.
- Сохранить отдельные назначения `PR title`, `hexlet-check` и release-please.
  Изменение защиты ветки и иных настроек репозитория в объём не входит.
- Отдельные команды backend остаются доступны без обязательной генерации TypeSpec,
  согласно ADR-0013; проверка свежести API добавляется в общий набор.
- Изменения бизнес-логики, API-контракта, версий инструментов и доменных терминов
  не входят в задачу. Новая запись ADR не требуется: схема проверок обратима
  и развивает общий интерфейс mise, зафиксированный в ADR-0018.

## Проверка времени CI

Согласованный эксперимент: **10 успешных наборов до изменения и один запуск
после изменения**. Исходная выборка фиксируется до реализации и впоследствии
не пересчитывается по более удобным результатам.

Для старого набора учитываются успешные `pull_request` workflow `backend`,
`frontend` и `container` одного SHA. Начало — минимальный `created_at`
трёх workflow, окончание — максимальный `completed_at` всех их jobs.
Это время до готовности всего набора, включая ожидание runner и подготовку.
Для нового набора начало — `created_at` общего workflow, окончание —
`completed_at` последнего job этого workflow, включая подготовку и загрузку
диагностики. Событийные workflow Q3 в измерение не входят.

По решению Q9 исключён набор SHA `159d688389b6a4e972d20798dcb7a98b5f149b11`:
его длительность по первоначальной оценке — 78 мин 35 с; jobs появились примерно
через 76 минут после создания workflow. Причина задержки не установлена.
Вместо него взят следующий успешный набор. Произвольно исключать другие запуски
или повторять новый замер до получения удобного результата нельзя.

## Критерии приёмки и проверка

1. Локальная команда и общий CI job вызывают `mise run check` и выполняют
   все шесть перечисленных групп без сокращения существующих тестов.
2. Независимые проверки действительно пересекаются по времени; критические
   зависимости и запись общих файлов соблюдены. По журналу одного `check`
   подтверждено однократное выполнение генерации OpenAPI, Go API и SDK
   в рабочем дереве, в том числе при их использовании несколькими ветками.
   Отдельный запуск команд генерации, проверки и сборки по-прежнему обеспечивает
   необходимые им предварительные шаги.
3. Контролируемый сбой одной независимой проверки не отменяет остальные;
   итоговый код ненулевой. При успехе всех проверок итоговый код — 0.
4. Отдельно проверены отказ генерации и несовпадение Go-файлов с индексом:
   ошибка сохраняется, зависимые шаги не читают частично записанный результат.
   Эксперименты с намеренными нарушениями выполнять в изолированной копии.
5. Выполнен полный локальный `mise run check` с Docker и браузером,
   проверены синтаксис workflow и `git diff --check`.
6. Один фактический запуск нового CI успешно выполнил полный набор;
   записаны SHA, URL запуска, время и сравнение с базой 197,0 с.
7. Порог 216,7 с соблюдён либо работа остановлена для пересогласования Q8.
   Без фактического CI-замера нельзя объявлять проверку скорости завершённой.
8. После проверки результата добавить свидетельство устранения D01 в отчёт
   аудита, сохранив его исходные факты. Остальные замечания аудита не изменять.
