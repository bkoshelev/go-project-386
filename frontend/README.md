# Frontend

Основной вход для установки, совместного запуска и команд проверок —
[корневой README](../README.md#установка). Этот документ владеет подробностями
браузерного окружения и устройства frontend.

Главная открывает гостевой выбор типа на `/book` и административную форму
на `/admin`. Начальный профиль — Александр Иванов; вход не требуется.
Типы событий сохраняются в PostgreSQL, одинаковые названия допустимы.
После выбора типа гость видит свободное время на 14 дат UTC, сгруппированное
по местным датам своего браузера. Слоты рассчитываются по сохранённому недельному
расписанию; выбор времени ничего не резервирует.

Установка зависимостей и браузера описана в
[подготовке frontend](../README.md#фронтенд), а генерация клиента и её повторный
запуск после изменения контракта — в [разделе API](../README.md#контракт-api-и-клиент).
Сгенерированные файлы исключены из Git и линтеров; TypeScript проверяет их при сборке.

## Совместная разработка

Порядок запуска PostgreSQL, backend и frontend — в
[корневом README](../README.md#использование). Маршруты прокси разработки задаются
в [vite.config.ts](vite.config.ts). В production Go-сервер сам раздаёт собранный
frontend и HTTP API с одного origin.

## Браузерная проверка

Нужны Go из [backend/go.mod](../backend/go.mod), доступный Docker, зависимости обоих
пакетов и отдельно установленный Chromium. Подготовка браузера — в
[инструкции установки](../README.md#фронтенд), запуск smoke — в
[командах frontend](../README.md#запуск-и-проверки-frontend).

Команда проверяет TypeScript, собирает production-ресурсы и запускает Playwright.
Worker собирает настоящий backend во временный каталог и запускает собственный
PostgreSQL в Docker. Версия образа и жизненный цикл определены в
[tests/fixtures.ts](tests/fixtures.ts). Каждый тест получает отдельную БД и процесс backend;
схема и начальный профиль создаются обычными встроенными миграциями. Проверки
работают через браузер и публичный HTTP API; SQL используется только для создания
и удаления тестовой БД. Перезапуск процесса проверяет сохранность данных.
После тестов удаляются процессы, БД, контейнеры и временные файлы; постоянная
локальная БД не используется. Отказы запуска окружения завершают тесты ошибкой.
При неуспехе журнал backend прикладывается к результату в `test-results/`.
В GitHub Actions тесты используют предустановленный Google Chrome через
`channel: "chrome"`, без скачивания браузера и установки его системных библиотек.
Версия Chrome определяется образом GitHub runner и выводится в журнал workflow.
Локально используется Chromium, установленный при подготовке окружения.

Интеграционные fixtures выбирают свободные порты для PostgreSQL и HTTP backend
и передают URL backend через переопределение `baseURL`. Значение `4173` в
[playwright.config.ts](playwright.config.ts) остаётся fallback для тестов без
этого переопределения; оно не задаёт порт интеграционного окружения.

Для одного файла после сборки: `pnpm exec playwright test tests/event-types.spec.ts`.

## Управление типами событий

`src/features/manage-event-types` предоставляет композиции приложения только
`ManageEventTypes`. Модуль владеет формой, автоматом XState 5, адаптером записи
и обновлением административного каталога. Автомат различает редактирование,
локальные ошибки, сохранение, подтверждённое создание, отказ и неизвестный результат.
Событие `saveRequested` выражает намерение пользователя; `onCreated` сообщает
только о подтверждённой сервером записи и запускает новое чтение каталога.
Ошибка чтения сохраняет подтверждение создания; повтор каталога выполняет только GET.
Неизвестный исход сохраняет ввод и допускает ручную отправку без автоматического повтора.

Остановка экрана останавливает actor и его запрос; это не доказывает откат записи.

## Просмотр каталога типов событий

`src/features/browse-event-types` предоставляет через `index.ts` только
`GuestEventCatalog`, `EventCatalog` и `readCatalog`. Общие чтение и представление
каталога реализованы в `src/features/browse-event-types/catalog.tsx`.
`Booking` подключает самостоятельный гостевой сценарий `GuestEventCatalog`,
который владеет собственным чтением и выбором типа события независимо от профиля владельца.
`manage-event-types` использует `EventCatalog` и `readCatalog` через публичный API
модуля; состояние административного чтения и решение обновить каталог после
подтверждённого создания остаются в `ManageEventTypes`.

`src/shared/useRead.ts` управляет загрузкой, ошибками, ручным повтором и отменой
запросов, подавляя результаты отменённых чтений, без зависимости от предметных модулей.

## Команды качества

Каталог команд качества находится в [корневом README](../README.md#запуск-и-проверки-frontend),
их определения — в [package.json](package.json). Исправления запускаются только явно:
lint и CI исходники не изменяют.

### Быстрая проверка типов

Для короткого цикла между изменениями используйте `pnpm typecheck` из `frontend/`.
Сначала подготовьте зависимости **обоих** пакетов `api/` и `frontend/` по
[инструкции установки](../README.md#фронтенд). В чистом checkout предварительно
сгенерируйте клиент, затем повторяйте проверку типов:

```bash
pnpm api:generate
pnpm typecheck
# После очередного изменения frontend
pnpm typecheck
```

Выполняйте команды последовательно. После изменения контракта API снова запустите
`pnpm api:generate` перед проверкой. `typecheck` использует уже сгенерированный клиент
и не гарантирует его свежесть относительно контракта.

Команда выполняет `tsc -b`: через существующие references в `tsconfig.json` проверяет
`src/`, конфигурации Vite и Playwright, а также `tests/`. Ошибки типов приводят к
ненулевому коду завершения. TypeSpec, Hey API и Vite при этом не запускаются.
JavaScript и декларации типов не создаются благодаря `noEmit`; компилятор может
обновлять `.tsbuildinfo` в исключённом из Git `node_modules/.tmp/`.

Быстрая проверка не заменяет `pnpm check`, production-сборку `pnpm build` и полный
`pnpm test:smoke`; они сохраняют автоматическую генерацию клиента.

### Правила статических проверок

Подавление допускается для конкретного правила на минимальном участке кода. Рядом
нужно оставить комментарий с причиной исключения. Oxlint и Stylelint сообщают о
подавлениях, которые больше не нужны.

Для редактора можно установить расширения Oxlint, Oxfmt и Stylelint. Интеграция
необязательна; источником истины остаётся `pnpm check`. Для Oxlint в редакторе
нужно включить type-aware linting, как в `.oxlintrc.jsonc`.

Oxlint выполняет статические проверки JSX-доступности. Они не знают семантику всех
компонентов Mantine, особенно полиморфных компонентов с параметром `component`.
Конфигурация намеренно не сопоставляет все компоненты Mantine с HTML-тегами.
Успешный lint поэтому не заменяет проверку доступности интерфейса в браузере.
