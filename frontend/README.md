# Frontend

React/TypeScript-приложение запускается и проверяется из каталога `frontend/`.

Главная открывает гостевой выбор типа на `/book` и административную форму
на `/admin`. Начальный профиль — Александр Иванов; вход не требуется.
Типы событий сохраняются в PostgreSQL, одинаковые названия допустимы.

Перед первым запуском установите зависимости обоих пакетов:

```bash
pnpm --dir ../api install --frozen-lockfile
pnpm install --frozen-lockfile
```

`pnpm api:generate` компилирует `../api/main.tsp` через TypeSpec и генерирует
Fetch-клиент Hey API в `src/api/generated/`. Эта команда автоматически выполняется
перед `dev`, `build` и `check`. После изменения контракта при работающем Vite
запустите её повторно. Сгенерированные файлы исключены из Git и линтеров;
TypeScript проверяет их при сборке. Подробнее — [в корневом README](../README.md#контракт-api-и-клиент).

## Совместная разработка

Запустите PostgreSQL и backend согласно [инструкции окружения](../docs/runbooks/production-environment.md).
При запуске `pnpm dev` Vite направляет `/api`, `/healthz` и `/readyz` к backend
на `127.0.0.1:8080`. В production Go-сервер сам раздаёт собранный frontend
и HTTP API с одного origin.

## Браузерная проверка

Нужны Go из `backend/go.mod`, доступный Docker и зависимости обоих пакетов.
Установка Chromium выполняется отдельно:

```bash
pnpm exec playwright install chromium
pnpm test:smoke
```

Команда проверяет TypeScript, собирает production-ресурсы и запускает Playwright.
Worker собирает настоящий backend во временный каталог и запускает собственный
PostgreSQL 18.6 в Docker. Каждый тест получает отдельную БД и процесс backend;
схема и начальный профиль создаются обычными встроенными миграциями. Проверки
работают через браузер и публичный HTTP API; SQL используется только для создания
и удаления тестовой БД. Перезапуск процесса проверяет сохранность данных.
После тестов удаляются процессы, БД, контейнеры и временные файлы; постоянная
локальная БД не используется. Отказы запуска окружения завершают тесты ошибкой.
При неуспехе журнал backend прикладывается к результату в `test-results/`.
CI выполняет ту же команду после отдельной установки Chromium.

Для одного файла после сборки: `pnpm exec playwright test tests/event-types.spec.ts`.

## Команды качества

| Команда             | Назначение                                                |
| ------------------- | --------------------------------------------------------- |
| `pnpm lint:code`    | Проверить JS, TS, JSX и TSX с анализом типов              |
| `pnpm lint:css`     | Проверить обычные CSS-файлы                               |
| `pnpm lint`         | Последовательно выполнить обе lint-проверки               |
| `pnpm lint:fix`     | Применить безопасные автоисправления Oxlint и Stylelint   |
| `pnpm format`       | Отформатировать поддерживаемые frontend-файлы через Oxfmt |
| `pnpm format:check` | Проверить форматирование без изменения файлов             |
| `pnpm check`        | Выполнить lint, затем проверить форматирование            |

Исправления запускаются только явно: lint и CI исходники не изменяют. `pnpm check`
также проверяет форматирование и компиляцию TypeSpec. `pnpm build` выполняет
отдельную проверку TypeScript перед production-сборкой.

Подавление допускается для конкретного правила на минимальном участке кода. Рядом
нужно оставить комментарий с причиной исключения. Oxlint и Stylelint сообщают о
подавлениях, которые больше не нужны.

Для редактора можно установить расширения Oxlint, Oxfmt и Stylelint. Интеграция
необязательна; источником истины остаётся `pnpm check`. Для Oxlint в редакторе
нужно включить type-aware linting, как в `.oxlintrc.jsonc`.

Oxlint выполняет статические проверки JSX-доступности. Они не знают семантику всех
компонентов Mantine, особенно полиморфных компонентов с параметром `component`.
Конфигурация намеренно не сопоставляет все компоненты Mantine с HTML-тегами.
Успешный lint поэтому не заменяет проверку доступности интерфейса в браузере.
