# Запись видео браузера

Используйте скилл только при явном вызове `$record-browser-video` или
`@record-browser-video` пользователем либо по разрешённой цепочке другого скилла.

Результат — проверенный MP4 в `artifacts/` и ссылка на него в ответе. Записывайте
реальное взаимодействие с приложением через Chrome DevTools MCP.

## 1. Подготовить сценарий и приложение

- Прочитайте `AGENTS.md`, актуальный `README.md` и настройки запуска проекта.
  Не вызывайте другие скиллы автоматически.
- Определите сценарий из запроса и текущей реализации. Если названа задача,
  проверьте её содержание по правилам `docs/agents/issue-tracker.md`. Не выдавайте
  функциональность другой задачи за запрошенную; сообщите о расхождении.
- Кратко сообщите пользователю, что будет показано. Уточняйте только данные,
  без которых нельзя продолжить; не запрашивайте повторное разрешение на запись.
- Если приложение уже запущено, проверьте адрес и готовность. Иначе запустите его
  по документации проекта, выбрав свободные порты и закреплённые версии инструментов.
  Для демонстрации сохранения данных используйте настоящий backend и отдельную
  локальную БД с демонстрационными данными. Не подменяйте API моками.
- Зафиксируйте созданные процессы, контейнеры и каталоги. Не останавливайте чужие
  процессы и не очищайте существующие данные ради повторной записи.

## 2. Подготовить браузер и запись

- Проверьте доступность Chrome DevTools MCP и инструментов `screencast_start`,
  `screencast_stop`, `new_page`, `take_snapshot`, `click`, `fill_form`.
  Используйте фактические схемы инструментов текущей сессии: префиксы могут отличаться.
  Конфигурация сервера проекта находится в `.codex/config.toml`.
- Проверьте `ffmpeg` и `ffprobe` через CLI. Если запись недоступна, сообщите
  конкретную причину; снимок экрана или performance trace не заменяет видео.
- Создайте отдельную вкладку через `new_page` с уникальным `isolatedContext`.
  Сохраните возвращённый `pageId` и передавайте его всем операциям этой записи.
  Не используйте захардкоженный ID или чужую вкладку.
- Задайте удобный размер через `resize_page`, например 1440 × 1080. Проверьте,
  что важные элементы доступны; при необходимости включите прокрутку в сценарий.
- Откройте начальный экран, дождитесь готовности через `wait_for` и снимите
  `take_snapshot`. Подготовьте данные до начала записи, если их создание не входит
  в демонстрацию. Не записывайте пароли и другие секреты.
- Создайте уникальный каталог для результата из корня репозитория:

  ```sh
  mkdir -p artifacts
  recording_dir=$(mktemp -d "$PWD/artifacts/browser-video-XXXXXX")
  ```

  Сохраните полученный абсолютный путь для следующих CLI-вызовов: переменные
  оболочки не обязательно сохраняются между ними. `artifacts/` уже исключён из Git.

## 3. Записать демонстрацию

1. Вызовите `screencast_start` с `pageId` без `filePath`. Сервер сам создаст
   временный файл. Это позволяет избежать известной ошибки `Access denied`,
   когда настроенные workspace roots MCP не совпадают с текущим worktree.
   Если пользователь явно задал путь, можно сначала попробовать его; при отказе
   используйте временный путь сервера и затем скопируйте результат через CLI.
2. Проверьте успешный ответ и запомните путь. Не продолжайте сценарий, пока
   инструмент не подтвердил начало записи.
3. Выполните сценарий через инструменты того же Chrome DevTools MCP. Получайте
   UID элементов из последнего `take_snapshot` или ответа с `includeSnapshot`.
   После навигации и изменения страницы обновляйте снимок.
4. Для заполнения нескольких полей предпочитайте `fill_form`. Для нативного
   `select` используйте видимый текст варианта из снимка, например `Часы`,
   если текущая схема инструмента не предусматривает выбор по значению.
5. Проверяйте результат каждого действия перед зависимым следующим шагом.
   При ошибке инструмента обновите снимок и исправьте действие; не отправляйте
   форму с частично заполненными данными.
6. Покажите результат действий: сообщение об успехе, появление данных в каталоге,
   сохранение после обновления или другой наблюдаемый итог сценария.
   Давайте зрителю время прочитать ключевые состояния, избегая длинных пауз.
7. После сценария вызовите `screencast_stop` с тем же `pageId`. При ошибке во время
   демонстрации также остановите запись, прежде чем повторять её. Не оставляйте
   активную запись после завершения работы.

Сохраняйте исходную скорость и звук в том виде, в котором их выдаёт инструмент.
Ускорение, монтаж и озвучку делайте по запросу пользователя и отмечайте в ответе.
Не обещайте запись звука, если инструмент её не поддерживает.

## 4. Сохранить и проверить MP4

- Возьмите фактический путь из ответа `screencast_stop`. Если MCP работает на той
  же машине, скопируйте файл через CLI в каталог результата как `original.mp4`.
  Передавайте пути как отдельные аргументы с корректным shell quoting.
  При удалённом MCP используйте доступный механизм скачивания; не считайте путь
  удалённого сервера доступным локально без проверки.
- Проверьте файл через `ffprobe`: он должен содержать видеопоток, ненулевую
  длительность и ожидаемый размер кадра. Расширение `.mp4` не гарантирует H.264:
  исходная запись может использовать AV1.
- Для удобного воспроизведения подготовьте `demo.mp4` в H.264, сохранив оригинал.
  Из каталога результата выполните:

  ```sh
  ffmpeg -hide_banner -loglevel error -i original.mp4 \
    -vf 'scale=1440:-2' -c:v libx264 -preset fast -crf 20 \
    -pix_fmt yuv420p -c:a aac -movflags +faststart demo.mp4
  ffprobe -v error -show_entries format=duration,size \
    -show_entries stream=codec_type,codec_name,width,height -of json demo.mp4
  ```

  Если `libx264` недоступен, сохраните рабочий оригинал и сообщите о его кодеке;
  не называйте его перекодированным. Не перезаписывайте предыдущие записи.
- Извлеките кадр из середины ролика через `ffmpeg` и откройте его доступным
  инструментом просмотра локальных изображений. Убедитесь, что виден интерфейс,
  текст читается, нет пустого кадра или страницы ошибки. Для длинного сценария
  дополнительно проверьте кадр с итоговым состоянием.
- Проверьте консоль через `list_console_messages` и запросы API через
  `list_network_requests`. Вызов с `includePreservedMessages` или
  `includePreservedRequests` помогает охватить навигации; учитывайте ограниченное
  окно истории инструмента. Отделяйте подтверждённые результаты от непроверенных.
- Проверьте `git status --short`: видео должно оставаться вне Git. Запись сама
  по себе не требует изменения исходников или запуска полного набора тестов.

## 5. Вернуть результат

Дайте пользователю кликабельную ссылку с абсолютным локальным путём к `demo.mp4`,
длительность и краткое описание показанного сценария. Укажите существенные ошибки
и ограничения, наличие звука и любые изменения скорости или монтаж.

Если приложение запущено вами, по умолчанию оставьте его доступным для просмотра,
сообщите URL и какие ресурсы оставлены, а также способ их остановить. Если пользователь
просил остановить окружение, завершите только созданные вами процессы и контейнеры
после сохранения видео. Не публикуйте запись и не создавайте коммит без запроса.
