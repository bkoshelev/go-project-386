# Эксперимент: XState 6 для бронирования

Прототип переносит существующую машину бронирования на `xstate@6.0.0-beta.3`
и проверяет React-интеграцию `@xstate/react@7.0.0-beta.0`. Он расположен в отдельном
пакете: действующая машина, React-экран и зависимости приложения не заменены.
У прототипа собственные точные зависимости и lock-файл. Он использует реальные
функции `validateGuest` и `saveBooking`, включая сгенерированный API-клиент.

Выбран сценарий с наиболее сложной координацией пользовательского процесса:
выбор типа и слота, валидация, блокировка повтора во время записи, шесть исходов
сервера и неизвестный результат при потере ответа. XState управляет интерфейсом;
конкуренция и атомарность бронирования остаются обязанностью backend и БД.
Основание: [AC-18–AC-25](../../specs/booking.md#проверяемые-критерии-приёмки).

## Подготовка и запуск

Из корня репозитория, с инструментами из `mise.toml`:

```sh
mise run api:deps
mise run frontend:deps
mise run api:generate
mise run frontend:browser
mise exec -- pnpm --dir experiments/xstate-v6-booking install --frozen-lockfile
mise exec -- pnpm --dir experiments/xstate-v6-booking run typecheck
mise exec -- pnpm --dir experiments/xstate-v6-booking test
mise exec -- pnpm --dir experiments/xstate-v6-booking run test:browser
mise exec -- pnpm --dir experiments/xstate-v6-booking run build
mise exec -- pnpm --dir experiments/xstate-v6-booking run complexity
```

Для ручного просмотра после подготовки: `mise exec -- pnpm --dir
experiments/xstate-v6-booking exec vite --host 127.0.0.1`. Это минимальная
страница для проверки машины, не копия дизайна или функциональности приложения.

## Проверенное поведение

- `booking.test.ts` выполняет 17 одинаковых сценариев для v5 и v6: локальная
  валидация, успешное сохранение, нормализация, блокировка повторов и изменений,
  conflict, missing, invalid, rejected, unknown, исключение, ручной повтор,
  возврат между шагами и отмена при остановке актора.
- В семи из 17 сценариев проверяется существующий API-адаптер с подменой HTTP:
  ответы 201/409/404/422/500, повреждённый 201 и потеря ответа.
- Два теста Playwright проверяют экспериментальный React-экран в Chromium:
  ожидание успешного ответа без повторной записи и потерю ответа с ручным повтором.
- `types-check.ts` использует `@ts-expect-error` для проверки отсутствующего
  поля, неверного типа и названия события. Фиксирует и оставшуюся nullable-ссылку
  в состоянии `confirmed`: в этом прототипе typestates не реализованы.
- На Node 24.21.0 и pnpm 12.4.2: 34 теста машины, 2 браузерных теста,
  проверка TypeScript и сборка эксперимента прошли. `mise run frontend:check`
  также прошёл для основного проекта.

Это сценарные проверки, а не доказательство эквивалентности всех траекторий.
HTTP-ответы контролируются тестами; эксперимент не проверяет реальную БД,
производственный React-экран и все остальные машины. Он не измеряет
производительность и сопоставимый размер production-бандла. Непосредственное
подключение v6 к приложению потребует отдельной миграции React-интеграции и
остальных машин, а также повторного запуска существующих end-to-end тестов.

## Сложность и типы

`pnpm run complexity` считает стандартные ветвления JavaScript по AST TypeScript:
сложность функции равна единице плюс `if`, тернарные операторы, `case`, циклы,
`catch`, `&&`, `||`, `??`. В существующем `model.ts`: 15 функций, сумма 18,
максимум отдельной функции 2. В `booking.ts`: 8 функций, сумма 15, максимум 7.

Суммы не отражают шесть `guard` в декларативной конфигурации v5 как ветви графа.
Поэтому они не доказывают, что бизнес-логика стала проще: v6 группирует исходы
в один `switch`, а v5 распределяет их между небольшими callbacks. В прототипе
TypeScript сужает `event.output` внутри соответствующей ветви `switch`; при этом
`eventTypeId!` и `selection!` остаются, и гарантии состояний ещё можно усилить.

Отдельный [отчёт об XState 6](../../docs/research/xstate-v6-beta.md) содержит
источники, описание API, ограничения анализа графа и обзор сценариев проекта.
