# Запуск приложения с внешней PostgreSQL

Образ объединяет frontend и Go-сервер; PostgreSQL 18 работает отдельно.
Сборка не требует БД. В финальном образе нет Node.js, компиляторов и shell;
процесс работает от непривилегированного пользователя. Go обрабатывает HTTP,
статику и завершение работы непосредственно как PID 1.

## Локальный запуск

Нужны Docker и Docker Compose версии 2.24.4 или новее. Из корня:

```bash
# Используйте URL-безопасный пароль, например вывод openssl rand -hex 24.
export POSTGRES_PASSWORD="$(openssl rand -hex 24)"
docker compose up --build -d
curl --fail http://127.0.0.1:8080/readyz
```

Откройте <http://127.0.0.1:8080>. `APP_HOST_PORT` меняет опубликованный
локальный порт, `PORT` — порт Go-сервера внутри контейнера. По умолчанию
оба равны `8080`. PostgreSQL не публикует порт на хост.
Сохраните пароль в менеджере секретов и передавайте тот же при следующих
запусках: смена переменной не меняет пароль в уже созданной БД.

```bash
docker compose restart app   # Данные сохраняются.
docker compose logs -f app
docker compose down          # Контейнеры и сеть удалены, том БД сохранён.
# Только если данные больше не нужны:
docker compose down --volumes
```

Ручной Compose использует проект `calendar` и именованный том.
Проверка ниже создаёт отдельный случайный проект и удаляет только его ресурсы.
Не используйте локальный Compose как настройку публичной БД.

## Готовый образ и переменные окружения

```bash
docker build --platform linux/amd64 -t calendar:local .
# DATABASE_URL содержит полную строку подключения и нужные параметры TLS.
export DATABASE_URL='postgres://user:password@database.example:5432/calendar?sslmode=verify-full'
docker run --rm --name calendar-app -p 8080:8080 -e DATABASE_URL calendar:local
```

| Переменная | Назначение |
| --- | --- |
| `DATABASE_URL` | Обязательное подключение к отдельно запущенной PostgreSQL; секрет передаётся при запуске. |
| `PORT` | Целое от 1 до 65535; сервер слушает `0.0.0.0`. В образе задано `8080`. |
| `HTTP_ADDR` | Явный `host:port`, приоритетнее `PORT`. Для доступа извне нужен `0.0.0.0:порт`. |

Для прямого запуска из `backend/` тоже нужен `DATABASE_URL`. Без `PORT` и
`HTTP_ADDR` сохраняется `127.0.0.1:8080`. Такой запуск не требует сборки
frontend; для раздельной разработки остаются команды Vite.

Перед открытием HTTP сервер проверяет конфигурацию, подключается к БД и
применяет встроенные миграции goose. Повторяются временные ошибки подключения,
ошибки авторизации и миграций завершают запуск. Общий бюджет подключения,
ожидания PostgreSQL advisory lock и миграций — 5 минут. Несколько экземпляров
с одной БД сериализуют миграции. При ошибке процесс завершается с кодом 1;
HTTP ещё не принимает запросы. SIGTERM/SIGINT отменяют также подготовку.
После запуска SIGTERM завершает обслуживание активных запросов в пределах
10 секунд и закрывает подключения к БД. Логи идут в stdout/stderr без DSN.

Frontend использует относительные URL на том же origin; адрес платформы
при сборке не задаётся. Go возвращает `index.html` для вложенных страниц SPA.
Неизвестные `/api`, `/api/...`, пути проверок здоровья и отсутствующие
ресурсы в `/assets/` или с расширением возвращают `404`.

- `GET /healthz`: `200 {"status":"ok"}`, жизнь HTTP-процесса без проверки БД.
- `GET /readyz`: `200 {"status":"ok"}` при доступной БД; иначе `503` без
  параметров подключения. Проверка запроса к БД ограничена двумя секундами.

При потере БД процесс остаётся запущенным; после восстановления `/readyz`
снова успешен. Обработчик `/healthz` от БД не зависит.

## Отдельная команда миграций и откат образа

```bash
docker run --rm -e DATABASE_URL calendar:local /app/migrate status
docker run --rm -e DATABASE_URL calendar:local /app/migrate up
# Существующий явный флаг также поддерживается:
go run ./cmd/migrate -dsn "$DATABASE_URL" status # из backend/
```

Обе команды используют те же миграции и блокировку. Сборка образа миграции
не запускает. Новые миграции должны сохранять совместимость с предыдущей
версией приложения: сначала добавляются структуры и переводится код,
удаление выполняется отдельным последующим выпуском. Откат образа не
запускает `down`. Ручной `down` доступен для осознанных операций с БД,
а не как автоматическая часть отката приложения.

## Контейнерная проверка

Нужны Docker, Python 3, Node.js и pnpm из `frontend/.nvmrc` и
`frontend/package.json`. Браузер устанавливается один раз:

```bash
pnpm --dir frontend install --frozen-lockfile
pnpm --dir frontend exec playwright install chromium
make test-container
```

Команда собирает образ, создаёт чистую PostgreSQL 18.6 и запускает два
экземпляра приложения. Проверяет ожидание БД при старте, однократное
применение миграции через SQL, загрузку frontend в Chromium и запросы к
backend из страницы на том же origin, SPA и `404`, порт через `PORT` и
приоритет `HTTP_ADDR`, сохранность данных после перезапуска, потерю БД и
восстановление readiness, SIGTERM после старта и во время подготовки.
Ошибки конфигурации, миграций, ожидание блокировки и общий дедлайн дополнительно
покрыты Go-тестами: `make test`.

Проверка всегда завершается ошибкой при недоступном Docker или невозможности
запустить БД. При завершении, ошибке и SIGTERM/SIGINT удаляются её контейнеры,
сеть, том и локальные теги образов; ручной проект `calendar` не затрагивается.
Диагностика сохраняется в `artifacts/container-smoke/`, пароль и DSN маскируются.
Workflow `container.yml` запускает ту же команду на push и pull request;
при ошибке загружает диагностику как artifact. Существующие workflow
frontend/backend выполняются независимо.

## Render

Эта локальная проверка воспроизводит схему запуска, но не проверяет Render.
Публикация в registry и реальное развёртывание в эту реализацию не входят.
Для последующего запуска:

1. Создайте отдельную PostgreSQL 18 и задайте `DATABASE_URL` из настроек
   подключения с параметрами TLS. Для сервисов одного региона используйте
   доступное им внутреннее подключение. См.
   [подключение Render Postgres](https://render.com/docs/postgresql-creating-connecting).
2. Соберите образ для `linux/amd64` (команда выше). Эта архитектура требуется
   для [готового образа Render](https://render.com/docs/deploying-an-image).
3. Передайте `PORT` платформы: Go привяжется к `0.0.0.0`. Не задавайте
   `HTTP_ADDR`, если нужен порт из `PORT`. Render завершает TLS и направляет
   HTTP на порт приложения: [Web Services](https://render.com/docs/web-services).
4. Задайте HTTP Health Check Path `/readyz`: проверка учитывает доступность
   БД. Политику переключения трафика и перезапуска определяет
   [Render Health Checks](https://render.com/docs/health-checks).

Перед публичным запуском с реальными данными отдельно определяются защита
административных операций, резервное копирование и восстановление БД.
