# ADR-0008: Проверка жизни процесса отдельно от готовности

Статус: принято.

## Контекст

Для минимального эндпоинта обсуждались три разных назначения: проверка живого
HTTP-процесса, пример прикладного API с ответом pong и проверка готовности сервиса
обрабатывать бизнес-запросы. Сейчас БД и бизнес-логики нет, поэтому эти варианты
могут выглядеть одинаковыми, но при появлении зависимостей их смысл расходится.

## Решение

Использовать `GET /healthz` как проверку жизни процесса. Успешный ответ `200`
с JSON `{"status":"ok"}` означает, что сервер способен обработать HTTP-запрос.
Эндпоинт не проверяет внешние зависимости и не обещает готовность календаря
выполнять операции. Он доступен без авторизации и не раскрывает окружение.

Отдельный readiness-эндпоинт сейчас не добавляется. Появление БД само по себе
не должно менять смысл `/healthz`; проверка готовности потребует отдельного
решения и контракта.

## Последствия

- Минимальный эндпоинт остаётся простым и независимым от будущей инфраструктуры.
- Его нельзя использовать как доказательство полной работоспособности продукта.
- Разделение предотвращает ситуацию, когда недоступность БД ошибочно трактуется
  мониторингом как необходимость перезапуска исправного HTTP-процесса.
- После подключения мониторинга изменение семантики потребует пересмотра
  потребителей, поэтому назначение фиксируется до такого подключения.

## Почему решение сохранено

Пользователь выбрал liveness вместо примера API и readiness. Без контекста
положительный ответ health-эндпоинта можно ошибочно принять за готовность всего
сервиса; это различие важно сохранить при последующем добавлении зависимостей.
