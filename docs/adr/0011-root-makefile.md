# ADR-0011: Корневой Makefile для проверок backend

Статус: принято; реализовано.

## Контекст

Backend находится в отдельном модуле, и существующие инструкции запускают
Go-команды из backend/. В интервью рассматривались прямые команды в README,
Makefile и собственный скрипт-обёртка. Пользователь выбрал Makefile, а на ревью
явно уточнил, что файл должен располагаться в корне проекта.

## Решение

Добавить Makefile в корень репозитория. Пользователь запускает make tools,
make lint, make fmt, make lint-fix, make vuln и make check из корня. Все эти цели
в рамках текущей задачи обслуживают только backend. Рецепты сами переходят
в backend/ и вычисляют пути относительно расположения Makefile.

Версии инструментов и команды установки определять в этом Makefile. Локально
и в CI использовать те же цели. В CI явно запускать make из корня, несмотря
на существующую рабочую директорию backend/ для Go-шагов.

Разделить проверку и изменение файлов: lint не исправляет исходники, fmt и
lint-fix меняют их только по явному вызову. CI использует проверяющие команды.
Каждую цель и значимую настройку снабдить поясняющим комментарием.

Поддерживаемые среды — macOS и Linux на amd64/arm64; Windows через WSL.
Нативный Windows без Unix shell в эту задачу не входит.

## Последствия

- Корневая команда make check пока означает проверку backend, а не всего
  продукта. Это ограничение должно быть явно описано в README.
- Backend остаётся самостоятельным Go-модулем; расположение Makefile не меняет
  границы модуля и не требует frontend для его проверки.
- Добавляются требования make и Unix shell, но команды установки и CI
  получают общий источник вместо нескольких расходящихся инструкций.
- Автоисправления доступны отдельно и не могут незаметно менять код в CI.
- Позднее подключение frontend к корневым целям требует явного пересмотра
  их контракта и документации.

## Почему решение сохранено

Это результат выбора между прямыми командами, Makefile и скриптом, уточнённый
на ревью. Корневые цели только для backend могут удивить читателя монорепозитория.
После использования команд в документации и CI их перенос или переименование
затронет потребителей; решение обратимо, но представляет интерфейс разработки.
