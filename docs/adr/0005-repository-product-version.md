# ADR-0005: Репозиторный файл версии продукта

Статус: принято.

## Контекст

У продукта одна общая версия для frontend и будущего Go-backend. Номер версии
планируется использовать в интерфейсе, логах, диагностических ответах и
метаданных сборки. Он должен быть доступен и при локальной сборке без Git-тега,
GitHub API и переменных CI.

В интервью рассматривались два варианта:

- использовать release type `go` без `version-file` и хранить версию только в
  manifest release-please, Git-тегах и GitHub Releases; для приложения передавать
  её из CI;
- использовать release type `simple` и хранить общую версию в корневом
  `version.txt`, который release-please обновляет в release PR.

Первый вариант уменьшает число представлений версии, но локальная сборка не
может надёжно определить релизную версию без Git или внешних параметров. Второй
вариант добавляет репозиторный контракт, доступный всем компонентам.

Использование `frontend/package.json` также не подходит: frontend является
приватным приложением, его техническая версия не должна определять версию всего
продукта, включая backend.

## Решение

Использовать release type `simple` и хранить версию продукта в корневом
`version.txt`.

- До первого релиза файл содержит `0.0.0`.
- Первый release PR обновляет его до `0.1.0`.
- Последующие release PR обновляют файл вместе с manifest и `CHANGELOG.md`.
- Файл содержит только SemVer и завершающий перевод строки.
- `frontend/package.json` сохраняет техническую версию `0.0.0` и не обновляется
  release-please.
- Commit SHA может добавляться во время сборки отдельно и не заменяет релизную
  версию.

`version.txt` является представлением версии для исходного дерева и сборки.
Manifest нужен release-please для отслеживания выпущенных компонентов, а Git-тег
и GitHub Release фиксируют опубликованный релиз.

## Последствия

- Локальная сборка может получить номер версии без обращения к Git и CI.
- Frontend и backend получают нейтральный общий источник, не принадлежащий
  конкретному языку или пакетному менеджеру.
- Код сборки и приложения может со временем начать зависеть от расположения и
  формата `version.txt`; удаление или перенос файла потребует миграции этих
  потребителей.
- В репозитории существует несколько согласованных представлений версии:
  `version.txt`, manifest, тег и GitHub Release. Изменять `version.txt` вручную
  вне release PR нельзя.
- На ветке release PR файл уже содержит предлагаемую версию, а в `main` до
  слияния остаётся последняя принятая версия. Это соответствует модели
  release-please.
- Различие между общей версией в `version.txt` и техническим `0.0.0` в
  `frontend/package.json` требует документации.

## Почему решение сохранено

Решение удовлетворяет всем критериям для ADR:

- После подключения frontend, backend, логов и сборочных сценариев к
  `version.txt` отказ от файла или изменение его формата потребует миграции.
- Корневая версия, отличающаяся от версии приватного `package.json`, может
  удивить читателя без знания границ продукта и пакетной модели.
- В интервью был сделан реальный выбор между версией, внедряемой только через
  Git/CI, и версией, хранящейся непосредственно в репозитории.
