# ADR-0011: Обязательные проверки frontend в CI без Git hooks

Статус: принято.

## Контекст

Проверки можно вводить как обязательные сразу, допускать предупреждения
или сначала использовать ознакомительный режим. Текущего frontend-кода мало,
поэтому пользователь выбрал обязательность всех замечаний с первого дня.

Для локальной работы сравнивались явные команды, проверка перед коммитом
и автоисправление staged-файлов. Выбраны явные команды и CI без Git hooks.
В CI обсуждались отдельная job и шаг перед smoke-тестом; выбрана отдельная job.

## Решение

- Любая ошибка, предупреждение или расхождение форматирования приводит
  к ненулевому коду завершения соответствующей проверки.
- Привести текущий frontend к правилам сразу; переходного периода не вводить.
- Предоставить явные команды проверки, автоисправления и форматирования.
  Общая команда `pnpm check` выполняет lint, затем проверку форматирования.
- Не устанавливать Git hooks и не навязывать конфигурацию редактора.
- В существующем frontend-workflow добавить job `quality`, запускающую
  `pnpm check` параллельно smoke-тесту на push и pull request.
- Установку зависимостей выполнять отдельно для каждой job;
  Chromium нужен только smoke-тесту.
- CI не изменяет исходники и не создаёт коммиты.
- Разрешить локальное подавление конкретного правила с объяснением причины.
  Объяснение проверяется на ревью, а не отдельным анализатором комментариев.
  Использовать встроенное обнаружение неиспользуемых подавлений.

## Последствия

- Замечания линтера сразу делают CI неуспешным; разрешённого запаса
  предупреждений нет.
- Разработчик сохраняет контроль над моментом изменения файлов;
  Git-коммит не запускает скрытое автоисправление частично staged-изменений.
- Результаты статических проверок и браузерного теста видны отдельно;
  ошибка в одной job не препятствует запуску другой.
- Параллельные job требуют повторной установки зависимостей
  и могут расходовать больше ресурсов CI.
- Неуспешный CI сам по себе не настраивает запрет слияния PR:
  защита ветки GitHub остаётся вне этой задачи.
- Ложные срабатывания можно объяснить локально без ослабления правил
  для всего проекта; обоснованность подавления остаётся предметом ревью.

## Почему решение сохранено

Это явный выбор строгости, локального рабочего процесса и устройства CI.
Он объясняет отсутствие Git hooks, отказ от допуска предупреждений
и отдельную установку зависимостей для параллельных проверок.
