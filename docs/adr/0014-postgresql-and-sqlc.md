# PostgreSQL и типизированные SQL-запросы через sqlc

Статус: принято; итоговый дизайн утверждён пользователем 19 октября 2026 года.

Для backend выбраны PostgreSQL и внутренний Go-пакет, генерируемый sqlc из
SQL-запросов и схемы. SQL остаётся явно написанным источником запросов;
генерируемый пакет служит для обращения к БД внутри backend и не является
отдельным публичным SDK. Выбор закрепляет SQL-подход вместо ORM и позволяет
проверять запросы и типы при генерации кода; смена СУБД потребует пересмотра SQL.

Первое внедрение ограничено инфраструктурой и одним сквозным примером:
миграция схемы, генерация Go-кода и выполнение запроса к реальной тестовой БД.
Полная схема приложения добавляется при реализации соответствующих функций.
Окружение БД в этой задаче запускается только на время тестов; постоянная
локальная БД и Docker Compose в объём не входят.

Выбраны PostgreSQL 18 с закреплённой patch-версией образа, goose для миграций,
pgx/v5 для подключения и testcontainers-go для временной тестовой БД. Проверки
используют уже установленный testify. Сгенерированный Go-код хранится в Git,
чтобы обычная сборка не требовала sqlc; CI проверяет актуальность генерации.

Полный запуск `make test` и CI включает тесты БД и требует доступный Docker.
Ошибка запуска контейнера делает проверку неуспешной, а не пропущенной.
Отдельный `make test-unit` позволяет запускать тесты без Docker. Это уточняет
окружение полного запуска тестов из ADR-0011, сохраняя его назначение.

SQL-миграции goose служат единственным источником схемы для sqlc. Встроенные
SQL-файлы использует общий Go-пакет миграций, доступный тестам и отдельной
команде `cmd/migrate`; операции также доступны из корневого Makefile.

Обычные тесты используют общий контейнер на пакет и отдельную транзакцию
на тест с явным откатом в `t.Cleanup`. Дополнение, согласованное пользователем
20 октября 2026 года: после миграций и до запуска тестов testfixtures один раз
загружает общий исходный YAML-набор. Каждый тест читает и меняет его в своей
откатываемой транзакции; загрузчик не очищает таблицы между тестами.
Общий контейнер сокращает число запусков БД. Транзакция на тест
не подходит для будущих проверок, которым нужен реальный `COMMIT`
или взаимодействие нескольких соединений. Сам цикл миграций проверяется
в отдельной временной базе общего контейнера без внешней тестовой транзакции.

Связь: [окружение БД](../../specs/database-environment.md).

## Первый сохраняемый предметный сценарий

В задаче [#34](https://github.com/bkoshelev/go-project-386/issues/34) существующая
инфраструктура расширена таблицами единственного владельца и типов событий.
Миграция `00002` воспроизводимо создаёт профиль «Александр Иванов». Ключ singleton
не позволяет создать второй профиль. Типы получают UUIDv7 через табличный
`DEFAULT uuidv7()`; запрос создания не содержит ID. Длительность хранится в целых
минутах, допустимые значения дополнительно ограничены CHECK. Каталог читается
полностью и упорядочивается по UUID.

PostgreSQL сохраняется как выбранная СУБД: он уже обеспечивает постоянное хранение,
табличный генератор UUID и транзакции с блокировками, нужные для последующей
атомарной проверки и записи бронирования. В этом сценарии атомарность будущего
бронирования ещё не реализуется. Запросы остаются в sqlc, схема — в goose;
альтернативное хранилище или отдельная копия схемы не вводятся.

Предметное поведение проверяется через публичный HTTP API и Playwright с production
frontend и реальным backend. Для каждого браузерного теста создаётся отдельная БД
в disposable PostgreSQL-контейнере worker; очистка не затрагивает локальные данные.
Эти проверки дополняют существующие инфраструктурные тесты миграций и sqlc.

## Недельное расписание и первый пояс владельца

В задаче [#35](https://github.com/bkoshelev/go-project-386/issues/35) миграция
`00003` добавляет singleton-настройки расписания. Пояс изначально отсутствует,
пауза равна нулю, семь местных дней заблокированы с пустыми интервалами.
Вся неделя хранится одним JSONB-документом принятой модели TypeSpec; правила
входных данных проверяются HTTP-слоем до записи. Один `UPDATE ... RETURNING`
заменяет неделю целиком и допускает запись только при сохранённом поясе.
Дни перед записью упорядочиваются с понедельника по воскресенье по контракту.
Чтение и конкурирующие записи не наблюдают частично заменённые дни.

Инициализация использует `UPDATE` с `COALESCE(time_zone, ...)`: блокировка строки
PostgreSQL сериализует конкурирующие первые запросы, каждый получает первоначальный
сохранённый пояс. Чтения, гостевые экраны и изменение паузы его не инициализируют.
Отдельный запрос изменения паузы обновляет только её столбец и не принимает пояс.
Редактор отображает и сохраняет местные часы без преобразования в текущий пояс
браузера; флаг блокировки независим от сохранённых интервалов.

Предметные проверки остаются на публичном HTTP API и production UI с изолированной
реальной БД; отдельные тесты внутренних запросов или сервисов не добавляются.
Поиск свободных слотов, настройки дат и влияние паузы на доступность остаются
в последующих задачах; сезонный перевод часов — в отложенной задаче #32.

## Уточнение границ при рефакторинге #35 и #36

22 октября 2026 года пользователь согласовал самостоятельные модели расписания
и расчёта слотов согласно [ADR-0017](0017-scheduling-feature-boundaries.md).
После рефакторинга семантическими правилами дней, интервалов и часового пояса
владеет модуль расписания; HTTP-слой сохраняет проверку формата и схемы запроса
и отображение ошибок в контракт. Это уточняет прежнее размещение всех проверок
в HTTP-слое, сохраняя их выполнение до записи. Формат JSONB, sqlc-запросы,
атомарная замена недели и однократная инициализация пояса остаются прежними.

Ограничение на добавление внутренних тестов уточнено: разрешены точечные проверки
переходов FSM и чистого расчёта слотов в дополнение к HTTP- и браузерным тестам
с реальной БД. Существующие тесты не меняются, кроме случаев, когда без изменения
нельзя обойтись; причина такого изменения должна быть объяснена. Отдельное
тестирование каждой внутренней функции или обёртки хранилища не требуется.

## Атомарное бронирование выбранного времени

В задаче #37 миграция `00004` добавляет встречи с UUIDv7, генерируемым БД,
ссылкой на тип события, UTC-началом/окончанием и контактами гостя. Длительность
берётся из типа. Ограничение PostgreSQL `EXCLUDE` на полуоткрытый `tstzrange`
дополнительно защищает от пересечений любых типов.

Сценарий создания начинает транзакцию и берёт `FOR UPDATE` на singleton-строке
`scheduling_settings`. Под этой блокировкой он читает текущие настройки и занятость,
повторно проверяет начало через общий `availability.Snapshot.Check`, вставляет
встречу и подтверждает транзакцию. Серверные часы фиксируются после получения
блокировки. Изменения недели и паузы обновляют ту же строку; настройки конкретных
дат должны придерживаться этой границы. Обычный уровень Read Committed после
ожидания блокировки видит последнюю сохранённую неделю и записи предыдущего
бронирования. Идемпотентности и автоматического повтора записи нет.

`Snapshot.Check` используется и для предложенных четвертей часа, и для создания,
включая минутные начала. Порядок причин отказа соответствует контракту. Общая
занятость читается для всех типов с запасом на паузу у границ окна; публичный ответ
не раскрывает контакты и ID встреч. Административное чтение фиксирует серверный
`asOf`, возвращает весь список с `endsAt > asOf` по началу и UUID. Его UI остаётся
отдельной задачей.

Проверки добавлены на публичном HTTP API и production Playwright с настоящими
изолированными БД. Тест цикла миграций обновлён только для новой последней версии
и таблицы, которую удаляет один шаг down; бизнес-проверки не обращаются к SQL. Проверка регистрации обновлена для двух
реализованных маршрутов; проверка 404 перенесена на ещё не реализованную
операцию ручной проверки начала.

## Исключения местных дат

В задаче [#38](https://github.com/bkoshelev/go-project-386/issues/38) миграция
`00005` добавляет разреженный JSONB-объект `date_availability` в ту же
singleton-строку настроек. Ключ — местная дата владельца; значение содержит
отдельный флаг блокировки и необязательные собственные интервалы. Отсутствие
интервалов наследует неделю, пустой список явно задаёт отсутствие часов.
При возврате к наследованию ключ удаляется; копии недельных интервалов не создаются.
Блокировка даты удаляет её часы, недельная блокировка сохраняет приоритет.

Замена даты выполняется одним `UPDATE ... RETURNING`, поэтому конкурентные
изменения разных дат не теряются. Обновляется та же строка настроек, которую
создание бронирования может блокировать `FOR UPDATE` перед повторным расчётом:
исключения не получают отдельного, несогласованного механизма записи.
Общее чтение расписания получает неделю и исключения одним снимком строки.
Модуль доступности применяет исключение к каждой затронутой местной дате перед
объединением соприкасающихся интервалов. Семантическая валидация интервалов остаётся
общей с недельным расписанием в модуле `scheduling`; HTTP-слой проверяет формат
и схему контракта. Предметные проверки проходят через публичный HTTP и production
UI с изолированной реальной БД; сезонные переходы остаются в задаче #32.
