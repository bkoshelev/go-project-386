# Единый контейнер приложения с Go-сервером для frontend и API

Статус: принято по ответам пользователя 20 октября 2026 года;
реализовано 20 октября 2026 года.

Для размещения на Render или аналогичной платформе frontend и backend
поставляются одним Docker-образом, а PostgreSQL запускается отдельно.
Собранный frontend и API обслуживает один Go-сервер: это сохраняет один origin
и позволяет обойтись без управления двумя серверными процессами в контейнере.
Рассмотренный вариант с Caddy потребовал бы отслеживания обоих процессов,
передачи сигналов и согласованного завершения при падении любого из них.

Это закрывает отложенный вопрос совместного запуска из
[ADR-0001](0001-standalone-frontend.md) и
[ADR-0006](0006-standalone-backend.md); независимые команды разработки
сохраняются. Для локального воспроизведения окружения выбран Docker Compose
с отдельной PostgreSQL 18 и браузерной проверкой готового образа.

В дополнение к liveness `/healthz` из
[ADR-0008](0008-backend-liveness-endpoint.md) вводится отдельный `/readyz`,
проверяющий доступ backend к БД. Успешная загрузка frontend сама по себе
не считается доказательством готовности всей связки.

Временная недоступность БД делает `/readyz` неуспешным, но не завершает
Go-процесс и не меняет `/healthz`. Доступность БД проверяется с таймаутом
2 секунды; после восстановления соединения готовность возвращается.
Платформа может независимо перезапускать экземпляр по своей политике.

Frontend использует относительные адреса API; неизвестные API-маршруты
и отсутствующие статические файлы не попадают под SPA fallback.
Один и тот же контейнерный smoke-сценарий запускается локально и в отдельном
workflow CI, дополняя существующие проверки компонентов.

Связь: [спецификация](../../specs/production-environment.md).
