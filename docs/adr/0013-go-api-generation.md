# ADR-0013: Генерация HTTP-слоя Go из контракта API

Статус: принято пользователем 19 октября 2026 года; первый этап реализован.

Контракт приложения описан в [TypeSpec](../../api/main.tsp), из которого
генерируются OpenAPI 3.1 и клиент Hey API для frontend. Для backend согласовано
сохранить Gin и генерировать модели, регистрацию маршрутов, разбор запросов,
сериализацию ответов и интерфейсы обработчиков с типизированными вариантами
HTTP-ответов. Это сокращает ручное дублирование принятого
[HTTP-контракта](../../specs/booking-api.md) по сравнению с генерацией только моделей.

Правила расписания, проверка доступности и сохранение бронирований реализуются
отдельно за интерфейсами обработчиков. Смена генератора после появления реализаций
затронет сигнатуры обработчиков и преобразования типов, поэтому граница генерации
фиксируется до начала реализации.

Выбран `oapi-codegen v2.8.0` с настройками `models`, `gin-server`, `strict-server`
и `embedded-spec`; версия генератора закрепляется. На текущей схеме OpenAPI 3.1
проверены генерация и сборка, сериализация объединений в ответах, различие между
отсутствующим `intervals` и пустым массивом, а также проверка ограничений схемы
через `kin-openapi`. Пробная генерация `ogen v1.24.0` завершилась ошибкой
`complex anyOf is not implemented yet`. У `go-gin-server` из OpenAPI Generator
документация не заявляет поддержку используемых контрактом `anyOf` и `allOf`.

Сгенерированный Go-код со встроенной схемой хранится в Git и обновляется отдельной
командой. Отдельная задача CI проверяет соответствие результата исходному TypeSpec.
Обычные сборка и проверки backend выполняются без Node.js и frontend, сохраняя
[ADR-0006](0006-standalone-backend.md) и [ADR-0011](0011-root-makefile.md).
Цена этого выбора — объёмные изменения сгенерированных файлов в PR; взамен
Go-разработчику не требуется запускать TypeSpec для обычной сборки и тестирования.

Запросы проверяются по встроенной схеме через `kin-openapi` после нормализации,
предписанной HTTP-контрактом, и до декодирования в сгенерированные типы. Дополнительные
правила расписания и бронирования проверяются в Go. Адаптер ошибок сохраняет
различие между `400 bad_request` и `422 validation_error` с массивом `fields`.
Это требует отдельного этапа обработки запроса, но позволяет использовать ограничения
схемы вместо полного ручного дублирования проверок.

Операции подключаются по мере реализации. Первый этап включает генерацию и перевод
существующего `/healthz` на сгенерированный интерфейс; остальные маршруты пока
не регистрируются. Полный исходный контракт и встроенная схема сохраняются.
Пробная генерация двух конфигураций подтвердила сборку такого пакета, наличие всех
16 операций во встроенной схеме и регистрацию только `GET /healthz`.

Детали конфигурации, валидации и критерии проверки записаны
в [спецификации генерации Go API](../../specs/go-api-generation.md).
