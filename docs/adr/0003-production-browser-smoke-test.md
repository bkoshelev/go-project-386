# ADR-0003: Smoke-тест production-сборки локально и в CI

Статус: принято.

## Контекст

Проверочная страница должна подтверждать работоспособность Vite, Mantine и
TypeScript. В интервью пользователь выбрал сохраняемый браузерный тест вместо
только разовой ручной проверки. Затем были согласованы объект проверки,
подготовка браузера и запуск в GitHub Actions.

Рассмотренные альтернативы:

- Проверять dev-сервер или production-сборку.
- Устанавливать браузер отдельным шагом или автоматически из команды теста.
- Ограничиться локальным запуском или добавить CI.

## Решение

- Проверять production-сборку в браузере.
- Одной тестовой командой проверять типы, собирать приложение, запускать
  локальный сервер собранных файлов и выполнять smoke-сценарий.
- Управлять жизненным циклом сервера автоматически.
- Устанавливать браузер отдельным шагом первоначальной подготовки после
  `pnpm install`.
- Добавить отдельный workflow GitHub Actions, запускающий ту же проверку
  в чистом окружении; существующий workflow Хекслета сохранить.
- Проверить dev-запуск отдельно при выполнении задачи.

Предлагаемый инструмент реализации — Playwright с Chromium. Выбор этого
инструмента не был отдельным сравнением тестовых фреймворков в интервью.

## Последствия

- Проверка охватывает типы, сборку, загрузку страницы и взаимодействие с Mantine.
- Тест выполняется дольше, чем сценарий на уже запущенном dev-сервере,
  поскольку сначала создаётся новая сборка.
- Для первого запуска нужно отдельно подготовить браузер; CI также должен
  устанавливать его системные зависимости.
- Обычная команда тестирования не должна неожиданно скачивать браузер.
- Появляется автоматическая проверка в чистом окружении GitHub Actions.
- Smoke-тест не доказывает работу HMR, всех браузеров или будущего production-хостинга.

## Почему решение сохранено

Это явный выбор между несколькими вариантами проверки. Он объясняет,
почему даже минимальный фронтенд включает сборку перед браузерным тестом,
отдельную установку браузера и workflow CI.
