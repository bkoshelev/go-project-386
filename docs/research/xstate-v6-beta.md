# XState 6 beta: исследование и применимость к проекту

Дата исследования: **17 ноября 2026 года**. Исходный материал:
[Announcing XState v6 beta, 5 ноября 2026](https://dev.stately.ai/blog/2026-11-05-xstate-v6-beta).

**Рекомендация:** XState 6 заслуживает отдельного эксперимента на существующей
frontend-машине. Основная польза для проекта — совместное сужение типов, ветвление
и обновление контекста в одной функции. Массовый переход на beta пока преждевременен:
есть изменения поведения, ограничения анализа графа и экспериментальные API.
Для рабочего приложения сейчас разумно сохранить XState 5, который продолжает
поддерживаться. Статус и рекомендация авторов по стабильной версии описаны в
[FAQ](https://prod.stately.ai/docs/xstate/v6/faq).

Это исследовательский отчёт. Миграция приложения, изменение зависимостей и
подключение новой инфраструктуры в рамках исследования не выполнялись.

**Дополнение:** после подготовки этого отчёта выполнен изолированный
[прототип машины бронирования](../../experiments/xstate-v6-booking/README.md).
Результаты раздела 9 относятся к первоначальному этапу исследования; свежие
проверки и ограничения прототипа описаны в его README.

## 3. Главные изменения модели программирования

### 3.1. Переход объединяет условие, данные и описание эффектов

В v6 переход можно описать функцией `(args, enq)`. Она проверяет условие обычным
`if`, возвращает `target` и частичный `context`, а эффекты ставит в очередь через
`enq`. Простой переход по-прежнему можно записать объектом `{ target: 'saving' }`.

Условие и обработка данных находятся в одной ветке TypeScript. Например, после
`if (event.output.kind === 'confirmed')` можно сразу читать
`event.output.confirmation`, не повторяя проверку внутри отдельного `assign`.
Это непосредственно относится к существующей машине бронирования.

`enq` описывает работу для последующего исполнения актором. Сетевой вызов или
мутация внешнего состояния прямо в теле перехода нарушают чистоту; функциональная
запись сама по себе её не обеспечивает. Чистые вычисления переходов существовали
и в v5. Источники:
[transitions](https://unpkg.com/xstate@6.0.0-beta.3/docs/transitions.md),
[data and effects](https://unpkg.com/xstate@6.0.0-beta.3/docs/data-and-effects.md).

Пример нового синтаксиса, созданный для отчёта:

```ts
import { setup, types } from 'xstate';

const formMachine = setup({
  schemas: {
    context: types<{ name: string; attempts: number }>(),
    events: { submit: types<{ name: string }>() },
  },
}).createMachine({
  initial: 'editing',
  context: { name: '', attempts: 0 },
  states: {
    editing: {
      on: {
        submit: ({ context, event }, enq) => {
          const name = event.name.trim();
          if (!name) return;

          enq(() => console.info('Accepted:', name));
          return {
            target: 'submitted',
            context: { name, attempts: context.attempts + 1 },
          };
        },
      },
    },
    submitted: {},
  },
});
```

Возврат `undefined` **без поставленных в очередь эффектов** отказывает в переходе.
Проверки отказа следует выполнять до `enq`. Обновления `context` объединяются
поверхностно; вложенные объекты по-прежнему нужно обновлять явно.
Источники: [actions](https://unpkg.com/xstate@6.0.0-beta.3/docs/actions.md),
[context](https://unpkg.com/xstate@6.0.0-beta.3/docs/context.md).

### 3.2. Схемы вместо `types: {} as ...`

`schemas` описывают контекст, события, вход и выход. Можно использовать библиотеку
с поддержкой Standard Schema либо `types<T>()` для одних TypeScript-типов.
При объявленных `schemas.events` проверяются также имена событий в `on`.
Появляется типизированный `actor.trigger.<event>(...)`; `actor.send(...)` сохраняется.

**Runtime-валидация включается отдельно.** Даже настоящая схема Zod сама по себе
не означает проверки входящих данных: нужен `standardSchemaValidator()` из
`xstate/validation`. Этот API экспериментальный. Валидация синхронная, проверяет
значения без применения результатов преобразования; `types<T>()` не валидирует
данные во время исполнения. Источник:
[TypeScript и runtime validation](https://unpkg.com/xstate@6.0.0-beta.3/docs/typescript.md).

Для проекта разумно начать с существующих типов сгенерированного API и
`types<T>()`. Добавление отдельной библиотеки схем следует обосновать конкретной
границей проверки данных.

### 3.3. Typestates и локальный вход состояния

Typestates задаются через `schemas.context` отдельных состояний. Например,
`confirmed` может требовать непустой `confirmation`; проверка
`snapshot.matches('confirmed')` сужает тип контекста. Переход в такое состояние
должен обеспечить его контракт. Это позволяет выразить часть инвариантов,
которые сейчас представлены nullable-полями и операторами `!`.
Источник: [typestates](https://unpkg.com/xstate@6.0.0-beta.3/docs/typestates.md).

State input — отдельные данные, передаваемые при входе в состояние и живущие
пока оно активно. Они полезны для временных параметров отдельного шага.
Их не следует применять к пользовательскому черновику, который должен сохраняться
при возврате между шагами.
Источник: [state input](https://unpkg.com/xstate@6.0.0-beta.3/docs/state-input.md).

## 4. Несовместимость с XState 5

Это обновление требует изменения исходников. Основные замены:

| XState 5 | XState 6 |
| --- | --- |
| `assign(...)` | Возврат `{ context: ... }` |
| `raise`, `sendTo`, `emit`, `spawnChild`, `stopChild` | Методы `enq.raise`, `enq.sendTo`, `enq.emit`, `enq.spawn`, `enq.stop` |
| `enqueueActions(...)`, списки `actions` | Одна функция с `enq` |
| `guard`, `and`, `or`, `not`, `stateIn` | Условия в функции, обычные JS-операторы, `snapshot.matches(...)` |
| `entry` / `exit` в виде массива или имени | Одна функция `(args, enq)` |
| Строковый переход `onError: 'failed'` | `onError: { target: 'failed' }` |
| Массив альтернативных переходов | Ветвление внутри одной функции |
| `types: { context: {} as C, ... }` | `schemas` |
| `systemId` | `registryKey` |
| `interpret(...)` | `createActor(...)` |

Источник: [руководство миграции, разделы 1–4 и 16](https://unpkg.com/xstate@6.0.0-beta.3/docs/xstate-v5-to-v6.md).

Асинхронная логика также меняется: `fromPromise(fn)` заменяется на
`createAsyncLogic({ run: fn })`. Другие адаптеры получают имена
`createCallbackLogic`, `createObservableLogic`, `createEventObservableLogic`
и `createStepLogic`. Последний имеет другой интерфейс, поэтому одной замены
импорта недостаточно. Источник:
[actor logic](https://unpkg.com/xstate@6.0.0-beta.3/docs/actor-logic.md).

Восстановление акторов вынесено в `restoreActor(...)` из `xstate/persist`.
Для сохранённых снимков предусмотрены версии и миграции. Наличие схем контекста
не заменяет проверку недоверенных сохранённых данных перед восстановлением.
Источник: [persistence](https://unpkg.com/xstate@6.0.0-beta.3/docs/persistence.md).

### Изменения поведения, которые могут пройти проверку типов

- **React:** хуки используют первую машину на протяжении жизни компонента.
  Передача другой машины при следующем рендере больше не заменяет работающий актор.
  `input` читается при создании; последующие изменения передаются событиями.
  Для нового экземпляра можно сменить React `key`. `useMachine` остаётся устаревшим
  псевдонимом `useActor`.
- **Параллельные состояния:** переход внутри одного региона больше не сбрасывает
  соседние регионы; могут измениться последовательности `entry` и `exit`.
- **Promise из эффекта:** rejection функции, поставленной через `enq`, теперь
  наблюдается и может привести к `onError` либо ошибке актора.
- **Дочерние акторы:** завершившиеся дети удаляются из `snapshot.children`;
  остановленный актор нельзя повторно запустить — нужен новый экземпляр.

Источники: [миграция, разделы 18 и 30](https://unpkg.com/xstate@6.0.0-beta.3/docs/xstate-v5-to-v6.md),
[parallel states](https://unpkg.com/xstate@6.0.0-beta.3/docs/parallel-states.md),
[create actor](https://unpkg.com/xstate@6.0.0-beta.3/docs/create-actor.md).

## 5. Проверки, графы и ограничения автоматизации

### CLI работает с определениями как данными

В пакете есть команды `inspect`, `validate`, `simulate`, `test`, `replay`, `diff`
и `docs`. Отдельные команды миграции делегируются `@xstate/codemod`.
Проверенный CLI beta.3 читает JSON, не загружает приложение и не исполняет эффекты.

Существенные ограничения:

- `validate` проверяет определение машины; это не runtime-проверка payload событий.
- JSON с выражениями `@code` отклоняется с `EVALUATOR_REQUIRED`.
- `test` проверяет свойства на устойчивых состояниях и заданных представителях
  событий в пределах обхода. В успешном ответе явно указано **`proof: false`**.
  Результат не является доказательством для всех данных и вариантов исполнения.

Источник: [реализация CLI beta.3](https://unpkg.com/xstate@6.0.0-beta.3/bin/agent.js).
Поэтому нельзя просто экспортировать произвольную TypeScript-машину и считать,
что CLI автоматически проверит всю её бизнес-логику.

### Граф не обязательно содержит все переходы

Runtime-функция `toDirectedGraph(...)` не анализирует тела функций переходов.
Такие рёбра отсутствуют в графе; `analysis.transitionTargetsComplete` становится
`false`, а `analysis.diagnostics` сообщает непрозрачные переходы.

Проверка корректности имени `target`, полнота извлечённого графа и достижимость
состояния — разные свойства. Предложение строгого извлечения графа описано
в документации, но **не является готовой настройкой или lint-командой**.
Источник: [graph analysis](https://unpkg.com/xstate@6.0.0-beta.3/docs/transition-functions.md).

Для проекта это аргумент сохранять буквальные имена целей в ветках и проверять
полноту перед использованием графа как основы ревью или CI.

### Поведенческие тесты и генерация сценариев

Базовые проверки можно выполнять через `initialTransition` / `transition` без
исполнения эффектов либо через работающий актор. Доступны подмена внешних акторов
через `provide`, `SimulatedClock` и проверки сохранения/восстановления.
Источник: [testing](https://unpkg.com/xstate@6.0.0-beta.3/docs/testing.md).

`@xstate/test` предоставляет обход путей, генерацию последовательностей через
`propertyTest`, сокращение контрпримеров и повтор через `replayTest`, а также
проверки покрытия. Для генерации нужен peer dependency `fast-check`.
По умолчанию invoked-акторы и таймеры не выполняются; для их моделирования
предусмотрен `mode: 'executed'` с заданными исходами сервисов и виртуальным временем.
Обход ограничен представителями payload и выбранными границами пространства
состояний. Источник:
[model-based testing](https://unpkg.com/xstate@6.0.0-beta.3/docs/model-based-testing.md).

Существующие Playwright-проверки API и браузера остаются необходимыми: модель
не проверяет реальный сервер, запись в БД и пользовательский интерфейс автоматически.

## 6. Маленькие FSM и долговечное исполнение

### `xstate/fsm`

Встроенный entry point предназначен для плоских автоматов без собственного
actor runtime, эффектов, таймеров, вложенных состояний и дочерних акторов.
Он возвращает `[snapshot, effects]`, где эффекты пусты; beta.3 поддерживает `always`.
Источник: [FSM beta.3](https://unpkg.com/xstate@6.0.0-beta.3/docs/fsm.md).

В анонсе заявлен размер около **0,5 КБ minified + gzip**. Это оценка маленького
FSM-модуля, а не всего XState, и в исследовании она не перепроверялась.
Источник: [анонс](https://dev.stately.ai/blog/2026-11-05-xstate-v6-beta).

Для существующих машин проекта с `invoke` и вложенными состояниями нужен полный
XState. Уменьшение API через `xstate/fsm` не является прямой заменой этих машин.

### Durable execution

`xstate/durable` и `createDurable(...)` экспериментальны. Они позволяют связать
чистые переходы с хостом, который отвечает за сохранение прогресса, повторы,
таймеры и обмен сообщениями. Готовые адаптеры конкретных workflow-платформ
в составе XState не поставляются.

Эффекты выполняются с семантикой **at least once**; адаптер должен обеспечивать
идемпотентность по стабильным ID эффектов. Детерминизм требуется и от порядка
эффектов: прямые `Date.now()`, случайные значения или I/O внутри вычисления
перехода могут нарушить replay. Источник:
[durable execution beta.3](https://unpkg.com/xstate@6.0.0-beta.3/docs/durable-execution.md).

Для проекта эта возможность пока не даёт достаточного основания вводить отдельный
JS-сервис рядом с Go backend. Короткие операции сохранения уже имеют явные
результаты и серверные гарантии. Сбой ответа после записи по-прежнему означает
неизвестный результат; библиотека сама по себе не предотвращает повторную запись.
Это согласуется с [принципами workflow](../architecture/workflow-based-architecture.md)
и [ADR-0017](../adr/0017-scheduling-feature-boundaries.md).

двух версий в manifest без изменения машин недостаточно.

Наиболее заметная потенциальная польза — в машине бронирования: сейчас guards
проверяют дискриминатор `event.output.kind`, а `assign` повторяет ту же проверку.
В v6 это можно выразить одной веткой с сохранением сужения типа.
Typestates могут дополнительно описать наличие `selection` и `confirmation`.
Фактическое устранение всех `!` требует отдельной проверки типов на мигрированном коде.

Для первого эксперимента удобнее небольшая машина создания типа события:
она уже содержит вложенные состояния, асинхронное сохранение, валидацию,
callback и неизвестный результат. После неё можно оценить более сложное бронирование.
Такая последовательность сохраняет границы features и разделение FSM и I/O,
принятые в [ADR-0017](../adr/0017-scheduling-feature-boundaries.md).

### Оценка по критериям принятия

| Критерий | Оценка для проекта |
| --- | --- |
| Количество API-конструкций | Базовые переходы проще; сложность полного набора возможностей остаётся значительной |
| Типобезопасность | Перспективное улучшение ветвлений и контрактов состояний; нужна компиляционная проверка на реальных машинах |
| Тестируемость | Чистые переходы удобны, инструменты генерации богаче; полного покрытия всех interleavings автоматически нет |
| Сложность кода | Может уменьшиться дублирование проверок; снижение цикломатической сложности не измерено |
| Документация | Плюс — файлы точной версии внутри пакета; при beta важно сверять их с сайтом |
| Производительность и размер | Данных для вывода об улучшении всего приложения нет |
| Развёртывание | При обычной frontend-миграции новую серверную инфраструктуру добавлять не требуется; durable-вариант требует отдельного проектирования |
| Зрелость | Подходит для ограниченного эксперимента; стабильный v5 остаётся доступным |

## 8. Предлагаемый порядок дальнейшей оценки

Это предложение для отдельной задачи, не выполненная миграция.

1. Зафиксировать точные prerelease-версии ядра и React-интеграции и выбрать одну
   машину. Проверять результат по документации установленного пакета.
2. Получить предварительный diff codemod и разобрать все места ручной миграции.
   Для воспроизводимого запуска инструмента доступна команда:

   ```sh
   npx @xstate/codemod@0.1.0-beta.3 migrate 'frontend/src/**/*.{ts,tsx}' --dry
   ```

   Это команда для просмотра изменений во всём frontend; для пилота glob следует
   сузить до выбранного файла. Сам codemod в рамках исследования не запускался.
   Автоматизация не гарантирует эквивалентности поведения. Источник:
   [README опубликованного codemod](https://unpkg.com/@xstate/codemod@0.1.0-beta.3/README.md).
3. Проверить типы, frontend quality checks и относящиеся к сценарию Playwright-тесты
   через существующие задачи [mise.toml](../../mise.toml). Отдельно проверить
   повторное сохранение, сохранность черновика, неизвестный результат, отмену
   и запоздалые ответы.
4. Сравнить читаемость diff, повторяющиеся условия, необходимость assertions,
   реальную полноту графа и размер production-бандла. Решение о расширении миграции
   принять по этим результатам и доступности стабильного релиза.

Для регрессий уже есть опорные проверки:
[scheduling-machines.spec.ts](../../frontend/tests/scheduling-machines.spec.ts),
[date-availability-machine.spec.ts](../../frontend/tests/date-availability-machine.spec.ts),

## 9. Что проверено непосредственно

Пакет beta.3 скачан и распакован во временный каталог без установки в приложение.
Проверки выполнены на **Node.js 26.0.0**; проект закрепляет Node.js 24.21.0.
Следовательно, эти опыты подтверждают перечисленные свойства пакета, но не
совместимость всей сборки проекта на его штатном toolchain.

| Проверка | Наблюдаемый результат |
| --- | --- |
| `initialTransition` и `transition` с пустым именем | Состояние осталось `editing`, эффекты отсутствуют |
| Валидный переход с частичным `context` | Получено `submitted`; имя нормализовано; незатронутое поле контекста сохранено |
| Эффект через `enq` | При чистом расчёте callback не вызван; при отправке события работающему актору вызван один раз |
| `toDirectedGraph` с функциональным переходом | `transitionTargetsComplete: false`, диагностика `dynamic-target` |
| CLI `validate` на JSON-машине | `valid: true`, `runtimePayloadValidation: false` |
| CLI `simulate` для события `GO` | Переход `idle → done`, `effectsExecuted: false` |
| CLI `test` с `reachable`, `never` и одним событием | `passed: true`, `scope: stableSnapshots`, `proof: false` |
| CLI `inspect` на JSON с `@code` | Отказ `EVALUATOR_REQUIRED` с путём к выражению |

Не выполнялись: проверка TypeScript-примера компилятором, миграция реальной машины,
тесты приложения на v6, запуск Editor Sync, проверка runtime-валидатора и durable-хоста.

Практический критерий перехода: подтвердить на существующем сценарии выигрыш
в типах и читаемости при сохранении всех исходов и запретов, прежде чем обновлять
остальные машины.
