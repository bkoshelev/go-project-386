# Адресное чтение контекста

Эта инструкция применяется при чтении задач, больших спецификаций и ответов GitHub.
Она доступна без вызова навыка. Цель — получать законченные требования без усечения
вывода и сохранять возможность проверить полный источник.

## Найти источник и границы

Сначала найдите файлы, затем посмотрите размер и текущие заголовки выбранного документа:

```sh
rg --files specs docs
wc -lc specs/booking.md
rg -n '^#{1,6} ' specs/booking.md
```

Заголовки внутри блоков кода могут давать лишние совпадения: проверьте границы по
самому Markdown. Прочитайте вводную часть о статусе и каноническом источнике документа.
Для GitHub сначала выбирайте метаданные, а body и обсуждение выбранной задачи
получайте по [правилам issue tracker](issue-tracker.md#reading-selected-issues).

## Читать законченные разделы

По текущим заголовкам определите начало и конец нужного раздела, включая вложенные
подразделы, таблицы и примечания. Выводите его через `sed -n 'START,ENDp' <файл>`,
заменив `START` и `END` найденными номерами строк. Не храните номера строк как
постоянный индекс: документ может измениться.

Нужные критерии можно сначала найти по ID, например:

```sh
rg -n 'AC-(07|08|09|10)' specs/booking.md
```

Совпадение — указатель на требование. Прочитайте критерий целиком, включая продолжение
строк и общие условия раздела. Перейдите к связанным определениям, ограничениям,
инвариантам и указанным источникам. Например, критерии расписания требуют также
правил наследования, блокировок и пустых интервалов, а не только строк таблицы AC.

Фиксируйте путь или URL, прочитанные разделы и ID критериев, а также оставшиеся
части. Это может быть краткая рабочая заметка; отдельный постоянный индекс или
копия требований в репозитории не нужны. Повторно выводите источник при изменении
или обнаруженном пробеле, а не весь набор документов после каждого поиска.

## Проверять полноту и усечение

Следите за предупреждениями инструмента (`truncated output`, `tokens truncated`),
обрывом строк, таблиц или JSON и отсутствием ожидаемого конца раздела. Такой ответ
не считается прочитанным полностью. Уменьшите порцию до целой секции или подсекции
и дочитайте пропущенное. Если даже подсекция велика, делите её по абзацам или группам
полных строк таблицы, сохраняя заголовок и общие условия; проверьте стык и конец.

Не объединяйте вывод нескольких больших файлов или body всех задач в один ответ.
Размер файла помогает выбрать порцию, но универсального числа строк или token budget,
которое гарантирует отсутствие усечения во всех инструментах, нет.

Выбранный фрагмент не заменяет полную спецификацию. Если задача или разрешённый навык
требует полного чтения, последовательно прочитайте весь обязательный источник
адресными порциями и сверьте покрытие разделов и AC. Для обсуждения GitHub это также
означает все комментарии со всех страниц. Полный оригинал сохраняйте доступным:
файл в репозитории либо временный локальный артефакт ответа, путь к которому указан
в рабочей заметке. Для API-ответа проверяйте успешность запроса и полноту пагинации;
отсутствие вывода из-за ошибки не означает отсутствие требований или комментариев.
